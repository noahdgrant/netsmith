# Add a part to the JLCPCB catalogs

Entry point: `AGENTS.md`. The rules and every past source are in `data/jlcpcb/README.md`. Read it first. The format of the files is ADR 0022 and the "Catalog files" section of `docs/language/12-catalogs-and-how-the-solver-picks-parts.md`.

## The sourcing rule

- Never write an LCSC number from memory. Part names are search keywords only.
- A row exists only if a fetched record returned that exact C number with the expected value and package.
- Put the evidence in the row's `source` cell and in `data/jlcpcb/README.md`: the LCSC record (manufacturer number, package) and the part's library type as a person read it on JLCPCB's parts page (do not script JLCPCB's parts library, ADR 0039), cross-checked, and the manufacturer datasheet for every number the model uses. The loader refuses a row with an `mpn` and no `source`, and an offer with no `source`.
- If you cannot fetch the evidence, stop and say so. Do not add the row.

## `data/jlcpcb/catalog/<catalog>.csv`

One file for each catalog, named by it (`resistor.csv`, `capacitor.csv`, `led.csv`, `ldo.csv`, `diode.csv`, `schottky.csv`, `zener.csv`, `tvs.csv`, `ferrite_bead.csv`, `inductor.csv`, `fuse.csv`, `n_mosfet.csv`, `crystal.csv`, `header.csv`; `sn74lvc1g04.csv` and `attiny13a.csv` hold the one row each of the ICs of `std/parts/logic.nsm` and `std/parts/mcu.nsm`; `p_mosfet.csv` holds three, the AO3401A, AO3407A and AO3415A; `level_translator.csv` has a header and no row yet, because no part of its has a recorded source: the first real row is added after the header, Basic first). A new catalog is a new file: `build.rs` embeds the directory, so no Rust changes. The header names the columns of the part's `catalog X { ... }` declaration in `std/` (the field path without the dot: `resistance`, `vout.voltage`) and the fixed columns `lcsc,mpn,name,label,library,price,stock,date,source,notes`. Copy the header of a neighbouring row. Cells use the language's syntax with units: `10kohm +/- 1%`, `1.8V..2.4V`, `0.68V`; text such as `package` is bare.

- Every row in a file is offered, whatever its `stock` cell says (the solver does not read stock, ADR 0047). The standard files ship no `price`, `stock`, `date` or `checked`: leave them empty in a row you add to `data/jlcpcb/catalog/` (a project's own file may state them; the `source` cell says when the record was read).
- `name` is what a message calls the row (`10kΩ 1% 0402 C25744`) and `label` the schematic's value field (`10k`). Both default to the `mpn`.
- `manufacturer` is an optional fixed column: who makes the part, as its datasheet spells it. A part is its `manufacturer` and `mpn` (ADR 0143), so two rows of one `mpn` from two manufacturers are two parts, and a row with an empty `manufacturer` is its `mpn` whoever makes it (the same part as any row of that `mpn`). Fill it from the datasheet, with the document in `source`; never from memory, and do not fetch it for existing rows from a supplier. A row that names a manufacturer needs an `mpn`.
- A row holds no supplier's number (ADR 0143): it is the part, its `manufacturer` and `mpn`. The LCSC number and JLCPCB's library type are one offer, a row of `data/offers/lcsc.csv` (`sku` the LCSC number, which JLCPCB's parts library assembles by too; `class` the library type from JLCPCB's parts page, `Basic`, `Extended` or `Preferred`, empty when JLCPCB's library does not list the part), with `manufacturer`, `mpn`, `source`, `checked` and `notes`. A new standard row needs its offer, with its class; `cargo test -p netsmith-solve --test main offers::` fails while a standard row has no offer, an offer names no row, or a standard offer has no class. An offers file named `jlcpcb.csv` is refused: its classes belong in `lcsc.csv`. A catalog file with an `lcsc` or `library` column is refused. A project's own offers go in its `offers/<supplier>.csv`, each with a `source`; `netsmith project migrate-offers` moves a project's old columns there.
- A part you looked at and decided against goes in `data/jlcpcb/considered.csv` with its reason, not in a catalog.
- A catalog keyed by a column (`catalog mcu by .mpn`) has one row per orderable part, and the design names it with `.mpn` when several rows fit (one fitting row is taken without a name).

## Starting a row

`netsmith catalog add --lcsc C123 --to <catalog.csv>` asks LCSC's record of the number (never JLCPCB's) and appends a row with `mpn`, `package` and a `source` that names the record and the day it was read, and `manufacturer` as LCSC spells it when the file has that column (check it against the datasheet's spelling), and the number as an offer in the project's `offers/lcsc.csv` (made when there is none). It leaves every other cell empty and prints what to fill: the ratings and curves from the datasheet (add `datasheet:<url>` to `source`), and the offer's `class` in `offers/lcsc.csv` (the library type from JLCPCB's page) for a part JLCPCB assembles. A row with an empty cell a part reads is never offered, so the row does nothing until you fill it. Check the `package` against `std/kicad.toml`; LCSC spells some packages its own way. Without `--to` it prints the record and writes nothing.

## Finding a part to add

`netsmith catalog search <words> --format json` (or `--mpn <number>`, or `--filter <attribute>=<value>` with Octopart's attribute short names, `case_package=0402`) asks the project's search provider, Nexar (Octopart's API, `[supply.nexar]`) or Digi-Key's own API (`[supply.digikey]`, `--provider digikey`, which has only Digi-Key's offers and no `--filter`), for parts: each with its `manufacturer` and `mpn` as Nexar spells them, and for `lcsc`, `digikey` and `mouser` its sku, stock (a count, or null with the reason) and price breaks. It needs `[supply.nexar]` in `netsmith.toml` with the names of two environment variables that hold a Nexar application's client id and secret (never the values), and a person who has read Nexar's terms of use; without them it says how to set it up and asks nothing. `netsmith catalog add --from <supplier> <sku or mpn> --to <catalog.csv> --details` then asks for the record of one part again, checks it names that part (the sku of that supplier, or exactly that `mpn` with one offer of it), and appends the row with `manufacturer`, `mpn`, the `package` as Nexar's `case_package` spells it (with `--details`, a plan that includes it) and a `source` that names the record and the day, and an offer for each supplier the record names in `offers/<supplier>.csv` (a supplier with two packagings is listed, not written). It leaves the ratings empty and lists them, like `--lcsc`: fill them from the datasheet whose address it puts in `notes`. A search result is where a part was found, never the evidence for a rating, and a standard row still needs its LCSC offer with JLCPCB's class from JLCPCB's page. Tests never ask a provider: `crates/netsmith-cli/tests/catalog_search.rs` and `catalog_search_digikey.rs` run both commands against a fake on 127.0.0.1 (`NETSMITH_NEXAR_URL`, `NETSMITH_NEXAR_TOKEN_URL`, `NETSMITH_DIGIKEY_URL`, `NETSMITH_DIGIKEY_TOKEN_URL`).

## Refreshing the numbers

`netsmith catalog refresh --dry-run --lcsc C5446` (or `--only resistor`) checks LCSC's offer of a part (`offers/lcsc.csv`) against LCSC's product record (never JLCPCB's): the offer's `mpn`, and the `package` of the part's row. It prints what it would write: only the day in the offer's `checked` column, for an offer that agrees; no catalog file is written. It never writes `price`, `stock`, `price_breaks`, a `class` or `date`: those are JLCPCB's numbers, which you read from its parts page by hand, and LCSC's differ. A new row leaves `checked` empty. A `CONFLICT` (LCSC names another `mpn` or package) or `MISSING` (the number is gone) offer is left as it was: look at it, then fix or move it to `considered.csv`. When it notes that LCSC lists stock 0, read JLCPCB's stock on its page; if that is 0 too, the solver does not offer the row and the std tests want stock above 0, so move it to `considered.csv`. `netsmith catalog age` lists rows whose `date` is older than 90 days. Do not run it over a whole catalog without being asked: it makes one request for each row to an unofficial endpoint whose terms of use are unread (ADR 0039). For a project, the same command checks the files its `netsmith.toml` lists.

## Order is the policy

The solver takes the first row that works and nothing sorts the file. The standard files are Basic first, then in the order of the unit prices read on a past date, then ascending value. Put a new row after the Basic rows and where the price you read puts it; `cargo test -p netsmith-solve --test main data::` checks only that Basic rows come before Extended ones. To change the policy itself, ask the user (`netsmith-dev-decision`).

## Where the model fields come from

- Resistors: 1%, from the supplier's value, with `max_power` from the record's `Power(Watts)` (check it on the LCSC record too). A 0 ohm link is left out. A row with an empty `max_power` is never offered, so do not add a resistor whose rating you cannot read.
- Capacitors: value, tolerance and rated voltage from the supplier's record. `effective_capacitance` is `derate capacitance by bias: 0:1 ...`, the manufacturer's DC-bias curve: `volts:fraction` pairs from 0 V (`0:1`) to the rated voltage, volts rising, fractions between 0 and 1, lowered by a margin. Say where the curve is in `source` after `bias-curve:`. A part with no published curve gets `derate capacitance by bias:` with nothing after the colon. Do not estimate a curve, and do not add a class-level fallback.
- LEDs: color and forward-voltage range from the datasheet; say how in `notes`.
- Curves over current and temperature (a diode's forward voltage; issue #1260): a file `data/jlcpcb/catalog/curves/<catalog>/<mpn>.csv` whose first line names the axes (`temperature`, `current`) and then the column (`forward_voltage`), one point per line with units (`25degC,100mA,0.42V`). The row keeps its single figure. Read the points from the datasheet's figure (numbers the maker gives, or the drawn line by pixel position), say where in the row's `source` after `curve:` and whether it is typical in `notes`, and add a point at `0A` when a design's current starts at zero. No curve from a family or memory. The format is the module doc of `crates/netsmith-solve/src/curve.rs`.
- Diodes, TVS, ferrite beads, inductors, fuses, MOSFETs and crystals (ADR 0025): the worst case of the datasheet table for each rating (maximum forward voltage at the rated current, minimum to maximum Zener voltage, largest RDS(on), an inductor's Isat and maximum DC resistance, a crystal's whole range over temperature), the package name of `std/kicad.toml` so the pick can be exported, and the JLCPCB and LCSC records agreeing on the model. When the record and the datasheet disagree, leave the part out and put it in `considered.csv`. `catalog` lines are in `std/parts/*.nsm`; `crates/netsmith-solve/tests/data.rs` lists the columns.
- Regulators: output voltage, dropout, current, power and package from the datasheet; say how in `notes`. The `dropout` cell is the maximum at the rated current; a datasheet's dropout over the load (a table at several currents, or a figure) goes in a curve file `curves/ldo/<mpn>.csv` with the axes `temperature` (optional) and `output_current` and the column `dropout` (issue #1259), with a point at `0A` only where the datasheet gives one (a curve that starts above zero leaves a row unused by a board whose load starts at zero). A buck IC's `high_side_resistance` is the datasheet's largest high-side RDS(on), stated only where the datasheet says the IC runs at 100 % duty cycle. The pads are not a column: the part's `pins` table in `std/` has a block for the package (ADR 0016), so a row for a new package needs its table too.

## ICs in `std/` with datasheet numbers

A part in `std/` that states logic levels or ratings (`std/parts/logic.nsm`, ADR 0046) puts the datasheet's number, revision and table next to each value in its doc comment, and a paragraph in `data/jlcpcb/README.md`. Read the numbers from the PDF text (`pdftotext -layout`), not from a summary. A value that depends on the supply is stated only for the datasheet row it comes from, and the part refuses supplies outside that row. If you cannot fetch the datasheet, do not write the part.

## Footprints and placement

A new package needs a footprint in `crates/netsmith-kicad/src/mapping.rs` (the row in `std/kicad.toml`). If the footprint is a chip, SOT-23, SOIC/TSSOP/MSOP, QFN/DFN or pin header, netsmith generates it by the KiCad name (ADR 0043, `crates/netsmith-pcb/src/generate/`): a name in `generate::names()` needs no library. For another package add a row to the generator that fits (its parameters are a table in that file), run `cargo test -p netsmith-pcb --test main generated_vs_kicad:: -- --nocapture`, and make it agree with KiCad's footprint of the same name or record why in `DIFFERENCES`; otherwise the footprint comes from a library file. Its pick-and-place rotation is unverified until a board with it has been assembled, so `crates/netsmith-fab/src/rotation.rs` leaves it out and `fab-notes.txt` flags it.

## Tests

Run `cargo test -p netsmith-solve` first. It checks that every row has its source, the file order, every curve, and that nothing in `considered.csv` is offered. Update counts in those tests when you add rows. Then run the gates in `netsmith-dev-verify`.

Then run `cargo test -p netsmith-tools --test main guide::`. A new row changes the counts in the guide's messages (`the closest of the 6 that fit`): run it with `GUIDE_BLESS=1` and read the diff. A guide example that is meant to fail must fail for a reason no row can remove (a rating or a value far beyond any real part, or a requirement that contradicts itself), never because the catalog happens to lack a row; if a new row makes one build, change the example (in `docs/language/`), not the row.

## Refuse

- A number you cannot cite.
- A curve you read from nowhere.
- Marking a part Basic that the API lists as Extended.
- A part JLCPCB shows with zero stock.
