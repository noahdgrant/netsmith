# Write `.nsm`

Read the language guide (`docs/netsmith/LANGUAGE.md`) for any construct you are unsure of. It has the syntax, an example and the real error for each construct, and a catalogue of the standard library at the end.

## Shape of a file

```nsm-fragment
import std::parts::passive::{Resistor, Led}
import std::sources::Rail

board Name {
    .supply: Rail { .voltage &= 5V +/- 5% }   // a member with values set
    .r1: Resistor {}                           // the solver picks it
    .supply.pos ~> .r1 ~> .supply.neg          // a series chain
}
```

## Rules

- A member is `.name: Type`. `.name` is local. A bare `name` looks outward through enclosing blocks.
- `&=` narrows a field to a constant or range. `==` is an equation that must hold in the worst case. `>=` and `<=` are bounds, checked in the worst case. There is no `=`. `min(.f)` and `max(.f)` are the least and the greatest value of a field's range, as one number, for a `<=` or `>=` statement only (`min(.bias) <= max(.zener_voltage)`, ADR 0098): they take one field, never narrow it, and wait when it has no value. `nominal(.f)` reads the value a field is stated at, without its tolerance (the centre of its range: `2kohm +/- 1%` is 2 kohm), in the same places, for a datasheet limit on a part's value (`nominal(.rprog) >= 2kohm`).
- `.f ?= value` is a default a module or part offers for a field: it applies only if no `&=` states `.f` (a value reached through `==` or `~` does not count), a board's `&=` drops it without needing to overlap it, and two `?=` on one field are an error.
- `.x: Resistance optional` (ADR 0074) declares a value that a design may leave open: a check that reads it is skipped, with no note and no finding, when nothing states it (`&=`, an applied `?=`, an equation, or a bound against numbers, also across a `~` join), and made when something does. It is for values, not pins, interfaces or boards.
- `unused .processor.usb` (ADR 0083) is a board's statement that nothing on it uses an interface of a part or a module (a USB port the part limits unconditionally): the part's limits for it are not evaluated, its rails have no `has no source` note, its levels do not run. The board may not also use it (a net with a pin of another part that is not passive, a `~` to an interface, a function chosen on a pin): that is an error with both lines. Test pads and the ground return are not uses.
- A part says what it is to the DC analysis with one `dc` statement (ADR 0076): `dc resistor .a .b .resistance`, `dc diode .anode .cathode .forward_voltage`, `dc nmos`/`dc pmos .gate .drain .source .gate_threshold .on_resistance`, `dc linear_regulator`, `dc switching_regulator`, `dc source .rail` (a connector that gives the supply). The standard parts already state theirs; write one for a part of your own that is a resistor, a diode, a switch or a regulator, or the analysis stops at it (a part with a `bridge` and no `dc` statement and no `.current` ends the network, and the note names the part and pin). A load behind a pin that nothing models is a stated `.current`. See the guide's "What a part is at DC" and "DC analysis".
- State what a part's value or a declared value needs. A resistor, capacitor or inductor picked with nothing limiting its value is an `unconstrained pick` warning (an error with `--strict`), and a value a module or board declares that a check reads and nothing states is an `unstated value` warning (ADR 0065). Write the value (`.r.resistance &= 4.7kohm +/- 5%`), bound what the part decides (a current or voltage check), or say that any value will do with a range (`&= 10kohm..100kohm`). A bound on a member that a part is held to by `&=` reaches the part. A `?=` default in a module is its statement.
- An `enum` is a type with a fixed list of variants (`enum Mode { Run, Sleep }`), and a variant is written with its enum, `Mode::Sleep`, where the enum is in scope (declared, imported or in the prelude), or bare only where the file imports the variant (`import src::m::Mode::Sleep`, or `import src::m::Mode::{Run, Sleep}`; ADR 0118); a member takes it with `.m: Mode` and `&=`, `?=` or `==`. An LED's colour is the enum `Color`: `import std::parts::passive::{Led, Color}` and `.led: Led { .color &= Color::Red }` (`Red`, `Green`, `Blue`, `White`, `Yellow`), never `"RED"`. Who assembles a part is the built-in `.assembly` of every part, of the enum `AssemblyMode` (`Fab`, `Hand`, `None` and `Consigned`, in scope in every file with no import): `.j1.assembly &= AssemblyMode::Hand`; `Consigned` is a part you buy and ship to the board house to place (ADR 0084), which needs no supplier part number. Never write it as text (`"hand"`): that is an error that names the variant. A module offers the choice as `.assembly_mode: AssemblyMode` and ties its parts with `.j.assembly &= .assembly_mode`. The manifest and catalog files (not source) still write the word in lower case.
- Ranges are `1.8V..2.2V` and `3.3V +/- 5%`. A range may have a member at an end, `.vcc.current &= 0A .. .max_supply_current` (put a space after `..` before a name with a leading dot): it is read when both ends have a value, claims nothing before then and is listed as not evaluated; a tolerance still needs numbers. A part whose draw is a catalog column states it this way. Prefixes: `p n u m k M G`. `m` is milli and `M` is mega.
- `a ~ b` puts pins on one net, or joins two interfaces of one kind. `a ~> part ~> b` runs a chain through parts that have a `bridge`. A chain from a rail's `pos` back to its `neg` through resistors and diodes (an LED) sets its own current, so `.led.current &= 5mA..15mA` picks the resistor: write no Ohm's-law equation for it (ADR 0113).
- `.headers ~ .module` between two parts, modules or interfaces of different kinds joins each pin or interface of one to the member of the other with the same name (ADR 0117); `.headers ~ .module { gpio4 = io4 }` pairs names that differ and `except { gnd }` leaves members out on both sides. The join is strict: a member with no partner is an error, so pair or except every one.
- Only a board names nets (`.pos.net &= "VCC"`). Modules never do. Ground is the exception that needs no statement: a `Rail` is on `GND` unless the board states another (`.analog: Rail { .neg.net &= "AGND" }`, ADR 0121), so never write `.neg.net &= "GND"`.
- A module is set only through its rails, pins and declared values.
- A part's pins are its `pins "PACKAGE" { .pin kind "NAME" "pad" ... }` table, with `tie`, `fn`, `optional`; the board connects them and chooses a pin's function with the bare name its `fn` list has (`.u.pa2.function &= UART1_TX`, no quotes; ADR 0118). A package is quoted text that must be one of the part's `pins "..."` headers and of its catalog's packages (`.package &= "SOT-23-5"`, `.package &= "0603"`); a misspelling is an error at the line that names the nearest. A function may carry its own direction after a colon with no spaces, `fn GPIO:bidirectional UART1_TX:output UART1_RX:input`; write it only where the datasheet says which way the function goes. A kind is one of `power`, `input`, `output`, `bidirectional`, `passive`, `no_connect`, `tri_state`; write `tri_state` (an output that is high impedance while its part is not selected, so several may share a net) only where the datasheet says so, with the page in a comment, and `output` for a pin it draws and is silent about. A pin has no `.pad`.
- A part states which functions belong together with `peripheral UARTE0 { UARTE0_TX:output UARTE0_RX:input }` and which hardware peripherals share with `shared SERIAL0 { UARTE0 TWIM0 }` (`shared UARTS limit 2 { ... }` allows two; a member may also be a function or a pin `.p10`): at most one member is in use at a time, and the functions a board chooses are what is counted (ADR 0071). A peripheral `on APP_GPIO` is offered on every pin whose row lists `APP_GPIO` (a class is a function rows list; a core that owns a pin is a class), so the table keeps one row for each pin; a peripheral with no `on` needs each function listed by the rows of its dedicated pins, written without a kind. Both are only in a part, never in a generic, module, interface or board. A peripheral that is the end of a bus says so: `peripheral SPIM0 on APP_GPIO as Spi SpiRole::Master { SPIM0_SCK:output as sclk ... }`, and a pin whose function the board chose is then a line of that bus for the bus rules.
- Every part has `.lcsc` and `.mpn`, the numbers of its catalog row: a narrowing of either (`.c1.lcsc &= "C307331"`) is a hand pick, which holds the part to that row before the pick lock (ADR 0122); there is no picks file. Write one only for a part the user named.
- Every part has `.designator`, the letters of its reference (`R1`, `BZ1`): a standard kind states them; a part you define states its own (`.designator &= "BZ"`) or is `U`; a board may narrow them on a part of its own that has none. Capital letters only. A connector of your own says `part X provides Connector` (`import std::parts::connector::Connector`): it gets the letters `J`, the schematic and the placer treat it as a connector, and a name like `HeaderBuffer` does not make a part one.
- A digital line is a `Logic` (`.line` pin, `.reference` rail); a part states `.vih`, `.vil`, `.voh`, `.vol` and `.line.abs_min`/`.abs_max` from its datasheet. Join lines pin to pin (`.a.out.line ~ .b.in.line`) and each part's `.reference` to its own supply. Never invent a level: a missing one is "not evaluated".
- A board needs `.process: TwoLayer { .stackup.thickness &= 1.6mm }` to become a PCB.
- A board's circuit source holds `.min_track` on a `Rail` and `.process.top.net &= "GND"` for an outer pour. Physical intent is in the board's **physical file**, `<stem>.physical.nsm` beside the source (ADR 0048): `physical for Board { case { .outline: Outline { .width &= 60mm; .height &= 40mm } } .usb.place.left &= 1mm +/- 0.1mm }`. `case { }` holds the `Outline`, `Cutout`, `MountingHole`, `Fiducial` and `Label` (`std::pcb`, `std::parts::mechanical`), a `Keepout` may be anywhere in the unit, and a path may reach a part inside a module (`.radio.row_a.place.left`) only to state `.place`, `.height` or `.pin_protrusion` (how far the pins of a through-hole part protrude out of the far side, ADR 0045 section 15). A keepout forbids `.tracks`, `.vias`, `.copper` and `.parts` unless a field says `"allow"`. The same statements in the board's own source are an error that names the file. No solved coordinates anywhere: they are in `<stem>.pcb.toml`. From an enclosure's DXF: `netsmith dxf import case.dxf --layer EDGE --holes-layer HOLES` prints the members for `case` and `--write board.nsm` puts them, and the holes' places, in the physical file (ADR 0045).
- A row of numbered parts on a pitch is one statement in the physical file, `row .pads.tp1 .. .pads.tp12 along x pitch 2.54mm +/- 0.05mm` (every number between the two names must be a part of one module; the row statement is not valid in the circuit source). A part's designator number counts the parts with the same letters in the order they are declared, never by the number in the name: declare `.pads.tp1` to `.pads.tp12` in that order and they are `TP1` to `TP12`.
- A `generic G { ... }` states what any provider must have (values, `pins { .a passive required }` with no names or pads, checks); a `part X provides G` or `module X provides G` stands for it and does not declare G's members again (narrow them). A board writes `.rf: G { .max_frequency >= 1.61GHz }` and the solver picks the first provider, in the files the board's file imports, for which the design holds; `.rf: G { .mpn &= "..." }` picks by part number, `.rf: X` forces X with no pick. A use reaches only what G declares (ADR 0068).
- A module takes a part as a type parameter bounded by a generic of parts (ADR 0115): `module Buck<Ic: BuckIc> { .ic: Ic ... }` reaches only `BuckIc`'s members of `.ic`. A board names the part, `.reg: Buck<Lt8641> { .vout.voltage &= 3.3V +/- 4% }`, or uses a generic the module provides and the solver tries `M<P>` for each provider `P`. What one part alone needs (a bootstrap capacitor, an RT resistor) goes in that part's `support { ... }` section, the only place a part declares parts.
- `Resistor`, `Capacitor`, `Led`, `Inductor`, `FerriteBead`, `Crystal`, `Fuse`, `Schottky`, `Zener`, `Tvs`, `TvsBidirectional`, `NMosfet`, `PMosfet`, `LevelTranslator` and `LinearRegulator` are generics that are their own first provider, so `.r: Resistor { ... }` is read and picked as ever. To add a part that a use of one can pick, write `part X provides Resistor` with its own `pins` table (a row of the generic's kind for each of its pins), its own one-row `catalog`, and no `.package: Package` of its own (the generic declares it); import its file from the board's file. The standard rows and series are tried first. `PMosfet` and `LevelTranslator` have a standard catalog with no rows: a project adds rows in `p_mosfet.csv` or `level_translator.csv`, or writes a provider. `LevelTranslator`'s `.a` and `.y` are `Logic` lines (join `.a.line`, `.y.line`; a provider's pin table names `.a.line` and `.y.line`): the solver judges the driver of `.a` against the row's thresholds with no statement, and `.vcc.current` is the row's own `0A .. .max_supply_current`.
- Attributes say what a `generic` or `part` is to the tools, on lines above it: `#[kind(resistor)]` (how the placer, the schematic and the 3D view treat it), `#[series(E12, E24)]` (the E-series the solver may make values from for its `catalog`), `#[bank]`, `#[value("LED")]`, `#[assembly(hand)]`; and above a member, `#[role(current)]`, `#[role(bias)]` and the other roles of the guide's "Attributes". A member gets the chain's current, a rail's bias or a peak only through its role, never through its name: a part of your own with a `bridge` writes `#[role(current)]` above `.current: Current` (ADR 0123).
- A bus interface (`std::bus::Spi`, `I2c`, `Swd`, `Usb2`; a `Uart` has none) has a role: a part states it (`.spi.role &= SpiRole::Slave`, import `SpiRole`; one that is joined to another end and states none gets the `bus role` guideline; a connector that the bus goes through states `UsbRole::Passthrough`, as `std::parts::connector::UsbC2` does, and is judged by the end behind it), its pin table is what its datasheet says (a slave's data out is `tri_state` only if the datasheet says so, else `output`), and `~` joins two interfaces (a `Uart`'s `~` crosses `tx` to `rx`). A part's bus clock is a bound (`.spi.frequency <= 10MHz`), the board states the clock (`.cpu.spi.frequency &= 8MHz`; a bus with limits and no clock is a note). A part that supports exactly one SPI mode states it (`.spi.mode &= SpiMode::Mode3`), a part with several states none. A bus interface also has `.levels` like a `Logic`: `.spi.levels.reference ~ .vdd`, `.spi.levels.vih &= 0.7 * .vdd.voltage` (vil, voh, vol), and an input's `.spi.sclk.abs_max`, each from the datasheet; `~` between two interfaces joins none of them. The reference rail draws nothing (`Levels` states `.reference.current &= 0A`), so a part states no current for it; its draw is the supply's `.vdd.current`.
- A resistor from a rail to one line (a reset, an enable, an open-drain output) is `std::bus::PullUp`, not a plain `Resistor` on the rail's `pos`: the module states what it draws, so the net is solved and the checks on it run. State `.pull.resistor.resistance &= 10kohm +/- 5%`, join `.pull.supply ~ .rail` and `.pull.line ~ .u.reset_n`; `.pull.line_low &= 0..0.1` narrows the share of time the line is low.
- A resistor from a line to ground (a boot-mode pin, an enable, a gate) is `std::bus::PullDown`, not a plain `Resistor`, which has no current: state `.pull.resistor.resistance &= 100kohm +/- 5%`, join `.pull.reference ~ .rail` and `.pull.line ~ .u.enable`; `.pull.line_high &= 0..0.1` narrows the share of time the line is high, and `.pull.line_top` states how high a stronger driver holds it. It draws nothing from the rail.
- A system joins ports of boards with `~` and nothing else.
- Statement order does not matter. Separate statements with a newline or `;`.
- Comments: `//`, `///` for the next declaration, `//!` for the file or definition.
- Use `&=` for constants and `==` for equations. Do not write `.x = 5V`: there is no `=`.

## Standard library

`std::parts::passive` (Resistor, Capacitor, Led, Inductor, FerriteBead, Crystal, Fuse, Switch), `std::parts::diode` (Diode, Schottky, Zener, Tvs, TvsBidirectional), `std::parts::transistor` (NMosfet, PMosfet), `std::parts::logic` (LevelTranslator, Sn74lvc1g04), `std::parts::regulator` (LinearRegulator, BuckIc, Buck, Lt8641), `std::parts::connector` (headers, sockets, Coax, UsbCPower, UsbC2, UsbCSink, Obd2M, ProgrammingPads6), `std::parts::mechanical` (MountingHole, PlatedHole, Fiducial, TestPoint, Label), `std::pcb` (Outline, Cutout, Keepout), `std::bus` (Uart, Spi, I2c, Swd, Usb2, PullUp, PullDown, I2cPullups), `std::sources::Rail`, `std::logic::Logic`, `std::mfg::jlcpcb::{TwoLayer, FourLayer, SixLayer}`, `std::mfg::acme::{EightLayer, TenLayer}` (a fictional fabricator: not for ordering). Fields and pins of each are in the guide's catalogue.

## Catalogs

A part with `catalog X { .a, .b }` gets its real part from the rows of `X.csv`, first fitting row first. Your project adds files in its `catalogs/` folder (`catalogs/ldo.csv`, named after the catalog; every `*.csv` there is read, `catalog_dirs` in `netsmith.toml` can name more folders). A header of the field names without the dot plus `lcsc`, `mpn`, `library`, `price`, `stock`, `date`, `source`; cells like `3.3V +/- 2%`, text bare. A row that names a part needs a `source`. A keyed catalog (`by .mpn`) with one row that fits needs no name; with several, choose with `.mpn &= "..."`. See the guide's Catalog files.

## Capacitors

Say what you need after derating: `.effective_capacitance >= 4.7uF`. Use `.capacitance &= 100nF +/- 20%` only where you mean the marked part. A capacitor between a rail's `pos` and `neg` gets its bias from the rail.

A `Capacitor` is one part and has no `.count`. When no single capacitor meets a requirement, use a `CapacitorBank`, identical capacitors in parallel, and state what you need of the bank as a whole: `.bulk: CapacitorBank` with `.bulk.total_effective_capacitance >= 47uF` lets the solver choose the count (1 to 8, fewest first; `.count &= 1..4` limits it) and the row. `.total_effective_capacitance` is what the bank keeps at the voltage across it; `.total_capacitance` is the marked sum (`4 x 22uF`), not a capacitance to design with. A rating (`.max_voltage`) is per capacitor. `Buck` does this for each side: state `.reg.output_cap.count` or `.reg.output_cap.total_effective_capacitance`. A number you know is `3 x Capacitor`, not a bank (a fixed `.count` on your own bank is refused); the bank's capacitors are `bulk[0]`, `bulk[1]` in a layout file. Never write capacitors side by side to get a larger value.
