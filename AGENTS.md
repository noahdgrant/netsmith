# netsmith

A language and tools for designing electronics as code. `README.md` says what it is and how to run it.

## Build, test, lint

- Test with `cargo test --workspace`, lint with `cargo clippy --workspace --all-targets`, and check formatting with `cargo fmt --all --check`. Each passes with no warnings. CI runs fmt, clippy and the tests on every pull request, and the editor's browser recipes (`scripts/editor-verify-all`) in a `recipes` job, whose first slice also runs the web app's unit tests (`npm test` in `crates/netsmith-editor/web`: the Rust test that runs them skips where the page's packages are not installed, as in `test`). The `test`, `kicad` (the tests that can ask for KiCad, with KiCad 9 installed, after `test` passes) and `recipes` jobs are slices that run side by side (4, 3 and 2); `scripts/ci-kicad-tests` says which tests `kicad` runs and fails `test` when a test looked for KiCad outside them, and `scripts/ci-test-slices` and `scripts/ci-recipe-slices` prove that every test and every recipe runs in exactly one slice, and `scripts/ci-recipe-slices` says how to rebalance the recipes. One `build` job compiles the workspace (on a pull request, only the packages its change can reach: `scripts/ci-rdeps`, which `clippy` also follows; `scripts/ci-rdeps-test` pins it) and hands the archive of the tests (`cargo nextest archive`) and the `netsmith` binary to the other jobs, which compile nothing. A pull request runs only the jobs its change needs (`scripts/ci-changes` has the rules and `scripts/ci-changes-test` pins them, in the `changes` job; a push to main runs everything; a change to `scripts/` runs everything except a recipe or a helper of the recipes in `scripts/editor-verify-js`, which runs only `recipes` and builds only `netsmith-cli`, and a fixture or the driver there, which runs the tests of the crates that read them, `netsmith-cli` and `netsmith-workspace`, `kicad` and `recipes`; `Cargo.lock` and the workspace manifest still run everything; the skills, the editor's too, are read by the tests of `netsmith-tools` alone), and `ci-ok` is the one check to require. The `no-kicad` job (a runner with no KiCad) runs `scripts/check-no-kicad.sh`, which builds and fabs every example with KiCad hidden: `build`, `fab` and the editor need no KiCad install (ADR 0097). KiCad 9 and Chromium's system libraries are installed from a cache of .deb files (`.github/actions/apt-cache`, `scripts/ci-apt-cache`, filled daily by `.github/workflows/apt-cache.yml`), so a job passes when Ubuntu's mirrors are down. The `locks` job runs `scripts/check-example-locks.sh`, which runs `netsmith project lock --check` over every example (with no KiCad) and fails when a committed pick lock (`<stem>.lock.toml`) is stale or missing: a change to a catalog, std or the solver that moves a pick of an example needs `netsmith project lock --update` in the example and a reviewed diff of the lock (ADR 0100); the job also runs `scripts/check-example-lint.sh`, which runs `netsmith project lint --strict` over every example and fails on a finding of the linter (issue #1104: change the source, or turn the rule off on that line with `// lint: off <rule>`). The `designs` job runs `scripts/check-example-designs.sh`, which builds every example with `netsmith board build --emit-design` and fails when a committed design file (`<stem>.design.json`, what the design stage hands the placer) is stale or missing: a change that moves a design needs `scripts/check-example-designs.sh --update` and a reviewed diff of the design files.
- The desktop shell (`desktop/`, a Tauri window around the editor) is a Cargo workspace of its own, excluded from the root one, so no build, test or job of the main workspace needs WebKit or GTK. Its library (the project folder, the `netsmith` program, starting `netsmith view editor --port 0` and reading the address it prints, stopping it) needs no window and is tested with `cargo test --manifest-path desktop/Cargo.toml` (set `NETSMITH_BIN` to a `netsmith` binary to also test against the real editor); the window is the binary, behind the `window` feature. CI's `desktop` job lints, builds and tests it on Linux when `desktop/` or the editor's server changes (`scripts/ci-changes`, the `desktop` flag), with WebKitGTK from the package cache (`install: tauri`).
- CI's `kicad-lookup` job runs the KiCad library lookup (`crates/netsmith-kicad/src/install.rs`) against a real KiCad 9 on ubuntu, macos and windows runners (KiCad from the package cache, the official disk image and the official installer, pinned by SHA-256 in the job's `env`). It runs `cargo run -p netsmith-kicad --example locate` and the lookup's tests with `NETSMITH_REQUIRE_KICAD_LIBRARIES=1`, where `tests/real_install.rs` fails instead of skipping. It compiles only that crate and runs only when the lookup, its example or its test changes (`scripts/ci-changes`, the `kicad_lookup` flag).
- `rust-toolchain.toml` pins the Rust version, here and in CI, so local clippy is CI's clippy. A new Rust release changes nothing until a pull request raises the pin and fixes what the new clippy finds.
- A test build is heavy: in a crate with no `tests/main.rs` every file of its `tests/` folder is its own executable (#190: every crate with a `tests/` folder has one executable, `tests/main.rs`, with the files as modules, found by `automod::dir!("tests")`: a new file is a module with no list to edit, a folder of helpers (`common/`) still needs its own `mod` line, and one file's tests run with `cargo test -p netsmith-tools --test main guide::`). The dev profile keeps line tables only (see `Cargo.toml`; `CARGO_PROFILE_DEV_DEBUG=2` brings the full debug information back for a debugger, `=0` drops it for the smallest build). Where memory is short, or several builds run at once, limit the linkers with `CARGO_BUILD_JOBS=3` and take turns with `flock /tmp/netsmith-heavy.lock cargo test ...` (one heavy build at a time; a machine ran out of memory with three).
- The commands are in `netsmith --help`; `cargo run -p netsmith-cli -- board build examples/led.nsm --out out` builds a sample board.
- The command line is the `netsmith-cli` crate (its binary is `netsmith`). The commands are grouped under nouns, `netsmith <noun> <verb>` (`project`, `board`, `layout`, `routes`, `view`, `catalog`, `import`, `dev`; issue #1090). A command is one file, `crates/netsmith-cli/src/commands/<name>.rs`, with its clap `Args` (the doc comments are its help) and its `run`, plus a variant of its noun's enum and a match arm in `commands/mod.rs`, and a row in the table of `docs/language/27-commands.md` (`tests/cli_table.rs` holds the table to clap's model, and checks that every `netsmith ...` the guide and the skills name parses). The first paragraph of a command's or a flag's doc comment is its line in the MCP server's tool list, which is limited in size (`tests/mcp.rs`: 120 bytes a line, 2,000 of help a command, 90,000 the list): keep it to what an agent needs to use it, and put the detail after an empty `///` line. A command or flag that moves or is renamed adds its old spelling to `commands/moved.rs`, which makes it an error that names the new one. A test that starts the binary goes in `crates/netsmith-cli/tests`; a test of what a command calls goes in the crate that holds it (a stage crate, or `netsmith-tools`).
- The linter (`netsmith project lint`, issue #1104) is the `netsmith-lint` crate: its rules read the parser's syntax tree and the checker's models (and the catalogs, for a row that gives a narrowing), never a later stage, and it changes no file. Each rule has a page in the guide, in the chapter of its construct, and a test with a source that has its fault and one that does not (`crates/netsmith-lint/tests/rules.rs`); the standard library lints clean (`tests/standard_library.rs`), and so does every example of the guide (`crates/netsmith-tools/tests/guide.rs`).
- The placer is the `netsmith-placer` crate and the router `netsmith-router`. The router takes a placed board and does not depend on the placer (only its tests place their boards with it); what both use, the board model and the measure of a placement (`quality`), is in `netsmith-pcb`.
- `netsmith-pipeline` is the build driver (`outcome_with`, check, solve and design, the schematic) and what it hands on (`Built`, `Outcome`, `Problem`); `netsmith-fabricate` is the fab driver (`fab`, `order`, the project manifest and the files beside a source) and depends on the pipeline, not the other way round. `netsmith-workspace` is the editor's backend (`Workspace`, the implementation of `netsmith_editor::Backend`) and depends on both; its tests are in `crates/netsmith-workspace/tests`. `netsmith-tools` holds the support the command line builds on them (`init`, `findings`, `compare`, `parity`, `reference_table`, the `port*` files, `dxf`, the symbol gallery) and the tests that need it: the ports' board tests and the guide's runner. `netsmith-cli` depends on the stage crates and on `netsmith-tools` directly, and nothing re-exports them. Each crate keeps the tests of its own stage in its `tests/`.
- The editor's page is not committed (ADR 0114): `build.rs` builds it from `crates/netsmith-editor/web` with Node 20 or newer when Node is present, and embeds a placeholder page that says it was not built when not (`cargo build` still succeeds, with a warning). Releases and CI always have Node, so they ship and test the real page: `NETSMITH_REQUIRE_BUNDLE_CHECK=1` makes the page tests fail on a placeholder instead of skipping. `scripts/web-bundle build` builds the page by hand into `crates/netsmith-editor/web/dist`; never commit `crates/netsmith-editor/web-dist` (it is ignored).

## Tests

- A test that needs a folder takes it from `netsmith_testkit::TempDir` (or `TempFile`; the crate `netsmith-testkit` is a `[dev-dependencies]` entry only), which removes it when the test ends, also on a panic. Bind the guard to a name, never to `_`. `NETSMITH_KEEP_TEST_DIRS=1` keeps the folders of a failing run.
- No test passes or fails by the speed of the machine it runs on. A browser recipe (`scripts/editor-verify-js/recipes`) waits on what the page signals (`whenIdle(page)` from `settle.mjs`, which waits on the page's own `window.__netsmith.idle()`, `crates/netsmith-editor/web/src/idle.ts`) or on the thing the step expects, never for a time: no `waitForTimeout`, no `timeout:` of its own. A timeout is a hang guard only (`HANG_MS` in `settle.mjs`, the default of every wait, set once) and its failure says the page hung. No assertion compares a duration with a limit: a duration that is useful is printed. Where the page gives no signal, add one in the page. `scripts/editor-verify waits` checks the recipes' text and CI runs it.
- No Rust test compares a duration or a CPU time with a limit. A test that wants to say how much work was done counts the work: the checkpoints a call reached (`Cancel::checkpoints`, and `Cancel::at_checkpoint(n)` for a cancel asked at a known place, `netsmith_core::job`), the work a stage reports (`job::reporting`), or a count the code exposes (the solver's `trials` and `work` and the router's `tries`). A cancel test asserts that the stage reports cancelled and that no more work follows the cancel; a scaling test compares counts between two sizes. A speed that is useful is printed by an `#[ignore]`d `measured` test (`mixed::measured`), never asserted. A time limit that a test passes is a hang guard of a minute or more (`time_limit: Some(120 s)`), and its failure message says the code hung. Where the code exposes no count, add a small, documented one.
- A test should take under about 2 minutes on CI (nextest names a test past a minute as SLOW, `.config/nextest.toml`). A board that needs longer becomes several tests, one per seed or case, or a `measured` test that is `#[ignore]`d, as `mixed::measured` is.
- The language guide is one file for each chapter, `docs/language/NN-topic.md` (`docs/LANGUAGE.md` is its index), and `crates/netsmith-tools/tests/guide.rs` runs the examples of every chapter. Change the guide with the language, in the chapter of the construct.

## Data

## Vocabulary and decisions

- Use the terms in the glossary and avoid the ones listed under _Avoid_. It is one file for each first letter, `docs/glossary/<letter>.md`, the terms in alphabetical order (`GLOSSARY.md` is its index); `grep -h '^_Avoid_' docs/glossary/*.md` lists the words to avoid.
- `docs/adr/README.md` says what an ADR is and is not (one page, no stage plans or progress, no amendments); `scripts/adr-check` enforces the size and the status words.
- Decisions that are hard to reverse are in `docs/adr/`; the language's design rules are in `docs/DESIGN-RULES.md`.
- Language-design choices (syntax, semantics) are the owner's. Present options and ask.
- Open work is in GitHub issues.

## Git

Stage files by explicit path when committing, so other people's in-progress files stay out.
Write commit messages (and pull request titles) as [Conventional Commits](https://www.conventionalcommits.org): `type(scope): summary`, with a type such as `feat`, `fix`, `docs`, `refactor`, `test`, `ci` or `chore`, and `!` after the type for a breaking change. A change that makes source, a file beside it or a command line that worked on the last release an error has `!` after its type and adds an entry under _Unreleased_ in `docs/MIGRATING.md` (the error, the old and the new spelling, the ADR) in the same pull request; the `PR title` workflow fails a `!` title without one (ADR 0134). Pull requests are squash-merged, so the title is the commit on main: the `pr-title` check (`.github/workflows/pr-title.yml`) fails a title that is not a Conventional Commit, and release-please (`.github/workflows/release-please.yml`) reads the commits on main to open the release pull request with the next version and the changelog.

## Orchestrating issue work

- Each agent finishes its whole issue, with a pull request that closes it (`Closes #N`). It stops short only when the rest needs the owner's decision or a design it can't settle alone, and then it opens a `status:ready-for-agent` issue that states exactly what is left.
- Merge many issues' pull requests in batches. Let 5 to 10 open, merge them together, and let the run on main, which runs everything, check them. Between merges, rebase the next pull request onto the new main and merge it without waiting for its CI, checking only `cargo check` or the CLI table tests locally; conflicts in the shared command table are usually adjacent added lines, so keep both. Agents work on the next batch while main runs, and it merges once main is green. A red main is fixed first, and a pull request that fails on its own waits for its fix.
