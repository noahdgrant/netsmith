# The editor is a local web app served by the netsmith binary

`netsmith editor` is the front end of netsmith: a project tree, a source editor with the real compiler and solver messages inline, and views of the board the source describes (schematic, power tree, system, bill of materials, PCB), with buttons for the build and for `fab`. It replaces `netsmith view`, which showed the schematic and nothing else, and is removed (ADR 0001: one way to look at a design). It takes the same arguments: no file acts on the project's `top_level` files from anywhere under the root (ADR 0011), a file is edited on its own, with the project's modules if it is in one. The language stays text (ADR 0003): the editor writes `.nsm` files and never a second copy of the design.

**It is a web app, served locally.** The binary listens on `127.0.0.1` (port 8787 unless `--port`), the user opens the address in a browser (on WSL, the Windows browser reaches it), and everything the page needs is embedded in the binary: no CDN, no request leaves the machine at run time. The Host header must be `127.0.0.1:<port>` or `localhost:<port>` (a rebinding page is refused), an `Origin` header, if any, must be the server's own, and a request that changes anything (`PUT`, `POST`) must carry `X-Netsmith: 1`, which a page on another origin cannot send without a preflight the server never answers. The server reads and writes only files that the project names (below).

**The stack is Rust and TypeScript.** The back end is `axum` on `tokio`, with JSON endpoints and one WebSocket. The front end is TypeScript with Preact (and `@preact/signals`), built by Vite, with CodeMirror 6 as the source editor; its source is `crates/netsmith-editor/web/` with a `package.json` and a lockfile. We chose CodeMirror over a small editor of our own (a `<textarea>` painted over by a `<pre>`) because the editor is the product: undo that survives a file switch, selections, search, a gutter that scrolls with the text, squiggles and bracket matching are work that CodeMirror has done well. The cost is that building all of netsmith needs Node 20 or newer once, where the rest of it needs only Rust. The grammar for `.nsm` is ours in either case (`web/src/nsm.ts`, written from `docs/LANGUAGE.md` and the lexer).

- *The bundle is built by `build.rs`.* `crates/netsmith-editor/build.rs` (the work is in `build_web.rs`, which `tests/build_web.rs` runs against fake `node` and `npm`) runs `npm ci && npm run build` in `web/` when the bundle is missing, unfinished or older than the sources, with a Node of at least 20 that it finds on `PATH` or in `~/.nvm/versions/node/*/bin` (`web/.nvmrc` says 22). `web/dist` and `node_modules` are not committed. Packages are installed again when `node_modules` was not installed by this build, from this lockfile and under this Node major, or lacks `tsc` or `vite`. A finished bundle has a marker file, so a `dist` that a killed build left half written is never embedded. Every step that writes `web/` holds an exclusive lock on `web/.build.lock`, so two cargo builds with different target directories wait for each other, and the finished bundle is copied into `OUT_DIR` under that lock before it is embedded with `include_bytes!`. When a step fails, the build records why (the command, the directory, the Node and npm versions, the start of `PATH`, the exit code and the last 15 lines of its output), prints it as cargo warnings, and compiles it into the binary: `netsmith editor` prints that reason and the manual command (`cd crates/netsmith-editor/web && npm ci && npm run build`), and the build runs again next time even if no file changed. `NETSMITH_SKIP_WEB=1` skips the web build. Building needs the npm registry once; running never does.
- *The types are written once, in Rust.* The request and answer types are in `crates/netsmith-editor/src/api.rs`, and `web/src/api.ts` is generated from them with `ts-rs` (`NETSMITH_WRITE_API_TS=1 cargo test -p netsmith-editor` writes it, and an ordinary `cargo test` fails if it is out of date). We took `ts-rs` over `specta` because it is a derive on the plain serde types, with no registry to keep in step. The page does not hand-copy a schema.
- *The crate does not know the compiler.* `netsmith-editor` holds the server, the types and the page, and a `Backend` trait with a method for each thing the page asks. `netsmith` implements it (`crates/netsmith/src/editor/`, a `Workspace` over a `Target`), because the work is the pipeline that lives there (`build_with`, `fab_with`, `Project`), and a crate the binary uses could not use the binary's library back. The split lets the server be tested with no compiler behind it, and keeps `axum` out of every crate but one. `netsmith-view` keeps its layout and SVG drawing, which are unchanged; its one-page viewer is deleted with `view`.
- *Later, not built.* A desktop shell (Tauri) around the same page is a later option: the page already talks only to a base URL. Refreshing price and stock online would be an opt-in `netsmith catalog refresh` that writes dated data into `data/jlcpcb/`; the solver never needs the network, and the editor shows the dates it has.

**The API.** One request answers one question, and the server keeps no editing state: the page holds the text of each open file, and the server holds the last build of what is on disk.

| Request | Answer |
|---|---|
| `GET /` and its files | the page, from the binary |
| `GET /api/project` | the title and the tree: top-level files, modules under `src/`, the manifest and the standard library (read-only), each with the definitions in it and their lines |
| `GET /api/analysis` | `{version, errors, warnings, problems, boards, systems}` of the files on disk |
| `GET /api/file?path=` | `{text, stamp, readonly}` |
| `PUT /api/file?path=` with the text and the `X-Stamp` it was read at | writes the file atomically (a temporary file beside it, then a rename); `409` if the file changed on disk since the stamp, so a save never overwrites another program's edit |
| `GET /api/board?name=` | the parts and nets of a board, with where each part is declared |
| `GET /api/schematic.svg?board=` | the drawing from `netsmith-view`, whose parts and nets carry `data-ref` and `data-net` |
| `GET /api/power?board=` | the power tree of a board, or of a system by its name |
| `GET /api/system?name=` | the boards and joins of a system, or the members and shared nets of a board |
| `GET /api/bom?board=` | the bill of materials, grouped as `bom.csv` is, with each pick's package, LCSC number, library, price and stock |
| `POST /api/pcb/route?board=`, `POST /api/pcb/cancel`, `GET /api/pcb/scene?board=` | place and route on demand (the answer says whether it stopped and how long it took); cancel stops the router and keeps what it routed; the scene has the drawing (a group for each layer, `data-net` on pads, tracks and vias, `data-ref` and `data-path` on parts, no key: the page lists the nets) and the parts, pads, keepouts and cutouts as data (ADR 0030) |
| `POST /api/pcb/edit` with `{board, stamp, changes}` | writes changes to the layout file beside the board's source (atomic); `409` if the file or an entry is not as the page saw it, `400` if the board does not take the result; the answer is the scene |
| `GET /api/pcb/findings?board=`, `POST /api/pcb/drc?board=` | what is wrong with the board, each finding with a point and a box; the second also runs KiCad's design rules check and keeps its result until the layout changes |
| `POST /api/build` | write the KiCad schematics, as `netsmith build` does |
| `POST /api/fab?board=` | run `fab` for the file of the board; the answer has its summary, `fab-notes.txt`, the design rules result and its output as the command line prints it |
| `GET /api/download?board=&file=` | a file `fab` wrote: `gerbers`, `bom`, `cpl`, `notes` or `pcb` |
| `POST /api/definition` with `{path, text, offset}` | where the name under the cursor is defined |
| WebSocket `/api/events` | the server sends `rebuilt` with the new analysis when a file changes, `analysing` when an analysis begins, and `progress` with `{task, board, message}` while a route, `fab`, build or analysis runs (the lines the command line prints to stderr; an analysis adds `stage`, `done` and `total`); the page sends `check` with `{id, path, text}` and gets `checked` with the same `id` |

A path is a name in the tree (`src/main.nsm`, `std/sources.nsm`): the server accepts only those, so a request cannot read or write another file, and `..` means nothing. The editor does not create, rename or delete files.

**Live diagnostics are a check of the text on the page.** A moment after typing stops the page sends `check` over the socket with the text of the file. The server builds the project with that text in place of the file's (and of a module in place of its file, through `Loader`), in memory, and answers with the problems; nothing is written. Saving (`Ctrl+S`) writes the file, the server sees the new modification time, builds again and pushes `rebuilt`. The server tells the page about changes by polling modification times every half second (the manifest, the top-level files and the modules): on WSL the files are often on the Windows side, where inotify events do not arrive. The watcher's baseline is the version read before the server accepts its first connection, and a socket subscribes to the pushes before its handshake is answered; with either taken later, a change made right after a page connects could go unannounced (the page then waited for a push that never came).

**A diagnostic is a value, not text.** The checker and the solver already report each mistake with a file, a span and a message. The pipeline's mistakes are now a list of `Problem` (message, optional location, and the text the command line prints), and `build_with` prints them as before. A problem in a module is reported at the module's file, wherever the importing board is. The page puts a squiggle under the span in the editor and lists the real message in the problems dock, a panel under every section (`Ctrl+J`, and `F8` and `Shift+F8` step through it from anywhere); a click goes to the place in the source and selects what it is about. What the build does not stop for is either a warning (a part not chosen: the design has a hole) or a note (a relation not evaluated, a balance left incomplete: what the solver left alone, mostly expected). The dock lists errors, then warnings, and the notes only once their toggle is pressed; each note is placed at the instance it is about. It lists as well what the views find: the PCB's findings and the power tree's issues. The status bar and the dock's header count errors and warnings, and a note gets no squiggle. While the source has a mistake the page keeps drawing the last board that built, dimmed, under a strip that says so and names the first error.

**Source and elements are tied by declaration spans.** Every instance in the checked model records the member declaration that made it (`.r1: Resistor`, with its file and span), and lowering numbers the design's parts from the instances, so the pipeline returns for each part of a `Built` board the instance it came from. The page gets for each part the line of its declaration, and the lines of the declarations of the instances that contain it (`.stage: LdoStage` for the regulator in the stage). A click on a part in the drawing opens the file at the innermost declaration; the cursor on a line highlights every part whose declarations include that line. Nets are tied to their parts, not to a line: only the board names them (ADR 0005) and the statement that names a net may be one of several.

**The views are computed from the model and not from text.** The power tree reads the solved model, as ADR 0007 and ADR 0014 define it: a node for each net that a rail draws from through `pos`, with the voltage the rails there agree on; the draws on it, each with its range and the part it belongs to; their sum, the demand; and the capacity, the `max_current` of the part whose rail supplies the net, where it has one. An edge joins the input rail's net of a part (or a module) to its output rail's net, labelled with the part, and a join in a system joins two ports' nets. A node is red when the demand's top is above the capacity, with the numbers. The system view reads the system's model: its boards, their declared ports and the joins. The bill of materials is the lowered sourcing grouped by `bom_entries`, so what is shown is what `fab` would write, and the price and stock are the `price` and `stock` of the catalog rows (`data/jlcpcb/catalog/` and the files the project lists, ADR 0022) as they were checked (the row says when; they move), found by LCSC number across all of them.

**Verifying it is part of the work.** `scripts/editor-verify` launches the editor over a scratch project, drives it in headless Chromium with Playwright, and keeps screenshots under `/tmp`; the skill `netsmith-dev-verify-editor` describes the lifecycle (launch, doctor, drive, evidence, cleanup) and has a page for each feature. Here Playwright 1.64 and the Chromium it installs run under WSL with Node 22 (`source ~/.nvm/nvm.sh && nvm use 22`); the default Node is 18, which is too old for Playwright and for recent Vite. `doctor` checks the Node version, that Playwright imports and that Chromium launches.

**Schematic layout stays automatic, and moving a symbol is decided but not built.** A moved symbol would be a sidecar `<file stem>.layout.toml` beside the top-level file, never inside the `.nsm` (statement order never matters and a position is not circuit): one table for each board, `[Board.parts]`, keyed by the part's path in the board (`stage.regulator`), each `{x, y}` an offset in millimetres from where the layout puts it. A part with no entry stays where it is put; an entry for a part that is gone is reported and ignored. It needs the layout to place wires after the offsets, which is a change inside `netsmith-view`, so it waits.

**Big boards.** A board of more than 16 parts is drawn by module (`netsmith-view`'s `sheets`): a box for each instance of a module of the board, laid out on its own as a small board is, the boxes in rows about 1.6 times wider than tall; the parts in no module are a box named for the board, and a box of more than 20 parts is cut into numbered boxes along the connections. A net between boxes is a stub and its name at each pin, ground is drawn in each box, and the layout is a pure function of the design. The page has an outline of the boxes, zooms to one on a click, and fits the whole. The power tree puts a rail one column right of the rails that feed it (each converter feeds every rail it makes from every rail it takes), cuts a column of many cards into lanes, sizes each card to its content and lists loads heaviest first. A quantity is shown with four significant digits and outward rounding (`3.584V..3.766V`), and a value below a femto-unit, or a million millionth of the larger end of its range, is `0` (`netsmith-quantity`, so the compiler's messages read the same). The PCB drawing has no key; the page lists the nets, lights one on hover and picks it on a click.

**Long jobs do not hold the server.** Routing, `fab` and a build run on a thread of their own and keep no lock on the editor's state while they do, so every other request, the watcher and the checks of typed text are answered; the state is locked only to read what the job starts from and to store what it made, and a board placed or routed for files that have changed meanwhile is dropped. The router and `fab` report through the functions they already take; the editor forwards those lines to the page over the socket with the board and task, and the page shows the last in the toolbar and the status bar with a clock, and the time taken when it ends. Cancelling is only for the router (a flag it checks where it checks its time limit); `fab` has no cancel.

**The analysis is told to the page, not only its result.** These additions are all optional fields or new messages; a page written before them reads the rest as it did.

- *A problem says which stage found it.* `Problem` has `stage` (`syntax`, `check`, `solve`, `lower` or `guideline`), `board` and `path`, and the page reads them and no longer takes them out of the message. The stage is where the pipeline made the problem: a parse error is `syntax` (the checker marks the diagnostics that the parser made), the checker's other mistakes and a file with nothing to build are `check`, the solver's mistakes and its notes and not-chosen warnings are `solve`, lowering's mistakes and notes and the schematic and footprint checks are `lower`, and a guideline finding is `guideline` (a warning, or an error under `guidelines = "error"`). `board` is the board as `BoardSummary.name` has it (`Demo/main` for a board of a system) for everything the build made of one board, and for a checker error written inside the definition of a board (a board a system places is its member; a board the system places twice has none); a parse error and a mistake in a module or a system, which several boards share, name none. `path` is the instance the server knows the problem is about, and only for notes, not-chosen warnings and guideline findings: the spans the checker and the solver report cover a declaration's header and not the block under it, so the server does not guess an instance from a statement's place, and the `at` of such a mistake is the place.
- *The socket says that an analysis runs.* `analysing` with `{since}` (milliseconds since the Unix epoch) is pushed when an analysis of the files on disk begins: the first one, and each that a change made by another program starts when the watcher next looks. `progress` is the message the jobs already use, with `task: "analyse"` and three more fields, `stage` (`check`, `solve`, `lower`, `draw` or `modules`), `done` and `total`; the counts are of what the stage works through (the top-level files for `check`, the boards and systems of the file for `solve` and `lower`, its boards for `draw`, the modules for `modules`), so a page shows "solving 3 of 7" and not a percentage of the whole, which is not known before the checker has found the boards. `rebuilt` ends it and has `elapsedMs`, which is also `analysis.elapsedMs` of every analysis, so `GET /api/analysis` says how long the last one took. A check of typed text is not announced. The analysis reports through `Backend::observe`, whose events the server turns into messages; the long jobs' `Say` and `progress.rs` are unchanged, because a job's line is text and the analysis has a stage and counts. A page that connects while an analysis runs is sent `analysing` and the last `progress` at once, from the state the server keeps for it, and the buffer of a socket is 256 messages, so a slow page does not lose `rebuilt` among a big project's lines.
- *The server listens before the first analysis.* The binary opens the workspace without analysing (`Workspace::open_deferred`), and the server's watcher makes the first analysis behind the listening socket, as it makes each later one. Until it ends, the page and its files, `GET /api/project`, `GET /api/file`, `PUT /api/file`, `POST /api/definition`, `POST /api/pcb/cancel` and the socket are answered at once: none of them needs the analysis. Every other route reads the analysis or changes files and reads it again (`/api/analysis`, the views, the PCB, `fab`, `build`, the orders, the file operations under `/api/fs/`). A request that sends the header `X-Netsmith-Pending: 1` is told at once, `503` with `Retry-After: 1` and the body `{"pending":true,"elapsedMs":12345}`, and nothing was done; that is the status the server already uses for a page that is not there, and a client that ignores the body fails where it would have taken a `202` for success. A request without the header waits until the analysis is done and is then answered as before, so a page that does not know of pending works, only later. A page that sends the header can show the file tree and the source from `/api/project` and `/api/file` while it waits, and load the views on `rebuilt`. The watcher announces the first analysis as a change from version 0, so `rebuilt` arrives on every socket that connected early. A `check` over the socket waits for the first analysis like any request; the socket does not wait with it, because each socket answers its checks on a task of its own, one after the other, and goes on carrying `progress` meanwhile. `Backend::pending` (lock-free, `Some(milliseconds)` until the first analysis ends) is what the server asks; the analysis holds the state's lock for as long as it runs, so the server could not ask anything else.
- *A requirement's line is data.* `PowerNode.at` and `Stage.at` and `PcbFinding.at` are places in the source, as `Draw.at` and `Edge.at` already were. A node's `at` is where the part or stage that gives its capacity is declared (the one `capacityFrom` names), else its first supply, else its first load; a stage's is its converter's declaration. A finding's `at` is the line of the physical file that states what it quotes (a `constraint` finding, the line that states a pin protrusion, the requirement that allows an overhang), as a point at the start of that line, in the file's name as the checker gives it; the first line if the finding quotes several. The findings that have no structure behind them (the precheck's) have it read from their sentence, which quotes the line.
- *What the page does with them.* The status bar's clock runs from `analysing.since` (the server's own start, so an edit made outside the editor shows it too) and not from the page's request, and says the stage of the last `progress` with its own count (`Solving Beta, 1 of 1`): never a percentage of the whole, which the server cannot give. `rebuilt.elapsedMs` is the time the page then shows, `Analysed in 46 s`, for twelve seconds, with the stages it saw in the tooltip. The page's first request for the analysis sends `X-Netsmith-Pending: 1`; on the `503` it paints its skeleton with `Analysing the project… N s` and waits for the socket's `rebuilt`, asking again only as a safety (every 30 s with the socket open, 1, 2, 4, 5 s without it: each is a failed request in the browser's console), so a project that takes half a minute to analyse shows a page in a quarter of a second and fills it without a reload. The dock's Stage column, its stage chips and its Module column are `Problem.stage`, `board` and `path`; a power issue and a PCB finding take `at` from the server, and a click shows that line in the source. The message is read for a stage, a board or an instance only for a problem that has no `stage`.
- *A running analysis cannot be cancelled, and this is not built.* The router can be, because it checks a flag where it checks its time limit; the checker, the solver and lowering are each one long call with no such place, in three crates, and the analysis holds the state's lock throughout, with the version and the file stamps already advanced, so stopping it in the middle would leave a state that claims a reading it does not have. What can be done is to start the next analysis when the files change again, which the watcher does after the running one ends; a project that takes half a minute is waiting for that. A flag checked between boards would help only a file with many of them, and the slow files are those with one big board. It needs a place in the solver's loop to check, and that is the solver's to add, with the state made safe to abandon.

**Fields added for the UI.** Each is an optional field, left out of the JSON when it has nothing to say, so a page written before it reads the rest as it did.

- *`Project` says what serves it.* `version` (the netsmith crate's), `gitDescribe` (`git describe --tags --always` when the build script last ran, so a commit made later is seen only at the next build, and uncommitted edits are not marked), `root` (the project folder, absolute; for a single file, its folder), `kicadPath` (where `kicad-cli` was found) and `bundleHash` (the `SOURCE-HASH` of the page embedded in the binary: that of the committed bundle, or of the sources when Node built it). The server fills `bundleHash` and `gitDescribe` itself, because they are facts of the binary and not of a backend.
- *A plane's rectangle names its layer.* Each `<rect>` in the PCB drawing's `l-planes` group has `data-layer` (`In1.Cu`) next to `data-net`, so a page can colour planes by layer exactly. The classes and attributes it had are unchanged.
- *A definition says where it ends and what is declared in it.* `Def.endLine` is the line of its closing brace, and `Def.children` lists the declarations written directly in its body (`name`, `typeName`, `line`, `endLine`, and `kind`, the kind of the definition the type names, read through the file's own definitions and its imports and left out when the type is not found). A declaration inside another declaration's block is not listed. All of it comes from the parser's spans, so the outline and the breadcrumbs read no text. Standard library files have it too.

Limits. One user, one browser: the server has no accounts and a second tab edits the same files. Diagnostics and the views describe the whole project at the last check and are not incremental; a project of hundreds of parts will feel the solve. The editor does not complete names. `netsmith.toml` is shown and not edited, and is read once: after changing `top_level`, restart. A `system`'s boards show their power trees together, not an end to end tree through connectors, which are not modelled (ADR 0010).
