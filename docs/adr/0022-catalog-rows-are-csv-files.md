# Catalog rows are CSV files, one per catalog, and a project can add its own

The owner reviewed this on 2026-11-04 and accepted it (the status line it had said "accepted (owner review 2026-11-04)"). It answers the question ADR 0016 left open, whether a catalog can hold rows in `.nsm` or CSV so that adding an IC stops being a Rust edit. The text before the cut is `git show 8a15457:docs/adr/0022-catalog-rows-are-csv-files.md`. Meets the first test (the file format that projects write) and the third (a second way to say a row would break ADR 0001). The reasons for each rule below, the loader's checks and the API are the header of `crates/netsmith-solve/src/table.rs`; the user's view is `docs/LANGUAGE.md` ("Catalog files"); the evidence rules are `data/jlcpcb/README.md`.

Every catalog row was Rust code in `crates/netsmith-solve/src/jlcpcb.rs`: a function for each part kind, with the engineering decisions in its comments. Adding a regulator meant editing the public repository and the solver crate. A private project could not have a part of its own, and a new kind of part needed a Rust function before it had one row. Nothing here changes what the language says: a part still declares `catalog X by .key { .a, .b }`, and the solver still takes the first candidate that works.

A catalog is one CSV file named by the catalog (`resistor.csv` is the `resistor` catalog). The standard ones are `data/jlcpcb/catalog/<name>.csv`, embedded in the binary by `build.rs`, so a new part or a whole new catalog is a change to `data/`. A project's catalogs are `catalogs/<name>.csv`, found in the folders of its manifest's `catalog_dirs` (default `["catalogs"]`; an owner decision of 2026-11-07, issue 193) and in the single files of `catalogs = [...]`. A file named like a standard catalog adds its rows after the standard ones.

The first line names the columns. A column is a field path without its leading dot and must be in the `catalog X { ... }` declaration of the part that uses the catalog. The file alone cannot say what a cell means (`0402` is a number or a package), so a part reads the cells as the kind of its fields. A quantity cell is the language's own syntax (`10kohm +/- 1%`, `1.8V..5.5V`), read by the language's parser. A text cell is bare. The fixed columns are about the row and not the part: `lcsc`, `mpn`, `library`, `source`, `name`, `label`, `notes`, and the columns later ADRs added (`assembly`, `height`, `checked`, `temp_min`, `temp_max`).

A row with an `lcsc` or an `mpn` must have a `source`, the place where its numbers were read: the rule that no part number comes from memory, enforced by the loader. The order of the rows is the selection policy, and nothing sorts it: the solver takes the first candidate that works, so the file decides which part a design gets. A part is in a catalog once; the same `lcsc` or `mpn` twice, in one file or across the standard file and a project's, is an error that names both places. A `.csv` in a catalog folder that is not named like a catalog is an error, not a skipped file: a forgotten or misnamed catalog would otherwise be a silent "no catalog" at the part that needs it. Every mistake names `file:line` and says what to change.

What stands after ADR 0047, which this ADR does not repeat in its own words. The `price`, `stock` and `date` columns are a provider's snapshot: the standard files ship them empty and the solver never reads them. The rule that a row with a `stock` of 0 is not offered is gone: every row is offered, and a part that is not wanted is removed from the file (it goes to `data/jlcpcb/considered.csv` with the reason). The order of the rows stays the policy, but a price read on a past date is no longer something a person can check.

Rejected: rows in `.nsm`. CSV was chosen because a spreadsheet and a diff both read it, and a second way to say a row would break ADR 0001. Rejected: text in quotes as the task first wrote it (`"SOT-23-5"`). In a CSV a quote needs doubling, and a forgotten quote would silently never match, so a cell that starts with a quote is refused with the fix. Rejected: a generic rule for the names and labels messages and schematics show (`10kΩ 1% 0402 C25744`, a value of `4.7k`); the `name` and `label` columns exist because no rule could make them.

The cost: the part's `catalog` statement and the file must agree on the columns, and the file's order is a policy that a person keeps by hand. A private project keeps its parts in its own repository and never in netsmith's. The standard candidates did not change with the move (checked by dumping every candidate before and after).

Left open, from the text: a shared catalog of several projects (a company parts library), which is a directory of files that several manifests list. Filtering by stock or price at build time. The units of `price`, which are not checked. A catalog name shared by two part kinds with different columns: the first file would need the union of the columns, the checker does not forbid it, and it has not come up. ADR 0047's question whether file order stays the policy once a preferred-parts list exists.
