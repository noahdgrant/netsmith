# Layout knowledge lives in the part, placement is derived, and the layout file holds only decisions

Meets tests 1 (a `layout` block in the part is a language construct, and a routes file is a file format) and 3 (a library file, doc comments only, and a chat panel in the editor are the obvious alternatives). The status line said "accepted (user review 2026-11-02)"; I relied on the four "User decisions (2026-11-02)" it covers. The text before the cut is `git show 3e54ce1:docs/adr/0030-layout-knowledge-and-the-pcb-editor.md`. It is 319 lines: the vocabulary, three worked examples, the regeneration plan, the agent commands, the editor stages E0 to E6, the catalog of first constraints and a staged plan. Those are a plan, kept in issue #59 and in that text; the built parts are in ADRs 0029, 0032, 0033, 0036, 0037 and the headers named below.

**Decision.** Everything about layout goes in exactly one of three places, judged in this order. (1) *Derived from the circuit, nothing written*: grouping by module path, connectivity, decoupling pairs from rail topology, connectors to edges. It carries weights and never a number that needs a source. (2) *Knowledge of a part, written once in the library with a source*: a datasheet number that the circuit does not imply and that holds in every design (a distance, a keepout, a via count). The test is three questions: does a datasheet say it, can the tool not derive it, does it hold in every design. (3) *A decision of this design, in the layout file*: positions, locks, keepouts the board draws, a waived constraint with its reason. Never in `.nsm`. A fact moves from 3 to 2 when agents keep writing it for every design, and from 2 to 1 when a rule derives it. The owner decided on 2026-11-02:

1. Layout knowledge lives in a `layout` block in the part, not in a library file: "the fewer places to find the information the better". Its constraints name the part's own pins and are found on the board by topology, so the part names no part and no net, and a mandatory `source` names the document and section. The sketch was a closed list of seven statements (`near`, `away`, `loop`, `keepout`, `edge`, `vias`, `route`), each a term of the placer's cost and a check at once, reported as a finding with the measured and the allowed number and never an error that stops `build`. The statements are a sketch and not accepted syntax.
2. Routes are kept in a committed file next to the layout file, so that a rebuild never changes an accepted layout and only an explicit regenerate does. The proposed form is `<stem>.routes.toml`, one record per net with its segments, its vias and a hash of its pad positions; a record whose hash no longer matches is dropped and routed again, and a missing file is routed from scratch, deterministically.
3. A violation of a manufacturing rule blocks `fab` by default, and a violation of a datasheet's layout guideline only warns, each with a default key in `netsmith.toml` and a flag that overrides it for one run. Built by ADR 0036 (`guidelines = "warn" | "error"`, `--strict`); ADR 0045 applies the first half to a requirement of the case.
4. Derived placement is built first and the `layout` block after it, because a block with nothing to run it on is speculation. Placement is built (ADR 0033); the block is not.

**What was rejected.** A library TOML per part (`std/layout.toml`, like `std/kicad.toml`): no language change, but a layout fact is not a tool name (ADR 0016's reason for TOML), the knowledge sits away from the `pins` it names, the compiler cannot check the pin names, and a library part would have two files (ADR 0001). Doc comments only: read by every agent and checked by nothing, so the placer cannot use them and a violation cannot be reported; kept as the complement, the datasheet's sentence is the doc comment above the constraint. A `layout set` command: the file is plain TOML that an agent edits, one way to say it. A chat panel in the editor: the agent is any agent and works through commands with JSON and the files, and the editor shows what it changed because it watches the file.

**The cost.** One new block in the language, a second file beside the layout file (the routes cache), a router that must take the copper already on the board as obstacles and route a chosen set of nets, and a placer that had to become much better than the rows before any of it showed. A constraint is a finding, so a design that cannot meet a datasheet number says so with a reason and the report shows it. The layout file's format, the placer and the editor's PCB view are built and live in their headers: `crates/netsmith-pcb/src/layout.rs` (the file, and why it is apart from the schematic's `<stem>.sch.toml`), `anneal.rs` and `place.rs` (the placer), `crates/netsmith/src/editor/pcb.rs` (the PCB view and its edit protocol) and `crates/netsmith-editor/src/server.rs` (the routes).

**Choices of the text before the cut, and what is not built.** Accepted as built by the owner, 2026-11-11, where the code has them:
- Where a datasheet's layout fact lives: A1, a `layout` block in the part with a mandatory `source` (decision 1). The owner chose A1; the spelling of the block and of its seven statements (`near`, `away`, `loop`, `keepout`, `edge`, `vias`, `route`) is decided when the block is built (issue #59).
- How strict constraints are: findings that never stop `build`, shown by `fab`, and refused by `--strict` (ADR 0036) when unwaived. A separate `--strict-layout` is not built; it is decided with the `layout` block (issue #59).
- A rasteriser: none. The board is drawn as SVG (`crates/netsmith-pcb/src/svg.rs`) and netsmith takes no PNG renderer or headless browser as a dependency.
- Module layouts as reusable sub-layouts (A4) are not wanted; a regenerated layout belongs to the board.
- No agent chat in the editor: the agent works through the CLI and the files, and the editor shows the result.
- Not built: regenerating one module (every part outside it locked for the run, the nets of its parts ripped up and routed again, a preview with the findings before and after, one undo step), partial routing, `netsmith place`, `route` and `layout check`, and the routes cache `<stem>.routes.toml` (issue #59).
- Decided since: one layout file apart from the schematic's (ADR 0032, ADR 0061); DRC with coordinates (ADR 0037); two-sided placement (ADR 0031).
