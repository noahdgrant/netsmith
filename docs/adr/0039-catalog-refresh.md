# `netsmith catalog refresh`: an opt-in check of catalog rows against the live record (first built as an update of price, stock and library)

Extends ADR 0022 (catalog files) and ADR 0019 (the editor). Nothing here changes what the solver reads: its input is still the CSV files, and it never needs the network.

## The problem

A catalog row's `price`, `stock` and `library` are a snapshot (`date` says when). They go stale: a part sells out, JLCPCB moves it between Basic and Extended, a price changes. Until now the only fix was a person repeating the fetches in `data/jlcpcb/README.md` for each row, and nothing said which rows were old. The user suggested an online pricing feature, opt-in.

## Decision

**1. A command, never a side effect.** `netsmith catalog refresh` is the only thing that touches the network. `build`, `fab`, `compare`, the solver, the editor's live checks and the tests do not. It is also what the editor's "Refresh prices" button runs (below).

**2. What it reads.** *(Superseded: the JLCPCB request below is no longer made; see the 2026-11-02 decision.)* For each row with an `lcsc` number, the two records the row's `source` cites (`data/jlcpcb/README.md`):

- the JLCPCB parts library, searched by keyword. The search also returns parts that merely mention the number, so the record taken is the one whose `componentCode` is exactly the number. It gives the library (`componentLibraryType` `base` is Basic, `expand` is Extended, and Extended with `preferredComponentFlag` is Preferred), `stockCount` and `componentPrices`;
- LCSC, `GET https://wmsc.lcsc.com/ftps/wm/product/detail?productCode=C25104`, for the manufacturer's number (`productModel`) and the package (`encapStandard`).

**3. What it writes.** *(Superseded: since the second 2026-11-02 decision a refresh writes only a `checked` date and no price, stock, `price_breaks`, library or `date`.)* Only `price` (the first quantity break, `componentPrices` from 1 piece, as the rows have always had it), `stock` (JLCPCB's own), `library` and `date` (the day the answer was got, UTC), and `price_breaks` if the file has that column. Never an electrical column, a name, a source or a note. A cell that already says the same number is not touched (`0.0010` stays `0.0010` when the record says `0.001`). A file without a column is not given one.

**4. A row that does not match is not changed.** *(Amended: only LCSC's record is compared, and a part LCSC does not list is MISSING.)* If either record's manufacturer's number differs from the row's `mpn` (case apart), or either record's package is not the row's `package`, the row is reported `CONFLICT` with both values. The suppliers spell packages their own way (`SOT-23-3L` for `SOT-23`, `SMA(DO-214AC)` and `DO-214AC(SMA)` for `SMA`), so the row's package must be the supplier's, or one of its words, with a trailing `-<digit>L` removed. The manufacturer's number is the real check that the part is the part; the package only catches a number reissued for another package, and it will pass `SOT-23` against `SOT-23-3L` as well as against a 3-pin part of another name. If JLCPCB lists no part with the number, or LCSC has no record (`"result": null`), the row is reported `MISSING`. Neither is ever deleted: removing a row is a person's decision, and `considered.csv` is where it goes.

**5. The file is rewritten by editing cells in place.** The file's text is kept; the cells to change are replaced by their byte spans, and everything else (row order, quoting, line endings, the final newline) is as it was. A new cell is quoted if the old one was or if it has to be. A refresh therefore shows as a diff of the cells it changed and nothing else. The rows are never reordered: the order of the rows is the selection policy (ADR 0022). When the new prices put rows that were Basic first and cheapest first out of that order, the command says so, with the first pair; it does not move them. Files are written only after every row has been looked up, each by a rename of a finished temporary file, so a run that stops writes nothing.

**6. Dry run, selection, age.** `--dry-run` prints the diff, cell by cell (`-price: 0.0011` / `+price: 0.0012` under the row's file and line), and writes nothing. `--only <catalog>` and `--lcsc <C123>` (each may repeat) choose catalogs and rows. With no path the files are the ones the project's `netsmith.toml` lists under `catalogs` and, in the netsmith repository, `data/jlcpcb/catalog/`; a path is a catalog file or a directory of them. The standard catalogs are also inside the binary, which cannot be written, so they are refreshed in the repository and reach users with a release. `netsmith catalog age [--days N]` (default 90) lists the rows whose `date` is older, or missing, and is the way to know when to refresh. The exit code of `refresh` is 1 when a row is `CONFLICT` or `MISSING`, and 2 when the run had to stop.

**7. Polite, and honest when it cannot be.** *(Amended: one endpoint now, LCSC's; `NETSMITH_JLCPCB_URL` is gone, and an address of JLCPCB's or under `/api` in `NETSMITH_LCSC_URL` is refused.)* The endpoints are unofficial: they are the ones the jlcpcb.com and lcsc.com pages call, and the repository has never agreed anything with either company. So: one request at a time, 500 ms apart (`--delay`); a User-Agent that says what it is (`netsmith-catalog-refresh/<version> ... one request at a time`) and not a browser's; a cache of the answers (`$NETSMITH_CACHE_DIR`, else `$XDG_CACHE_HOME/netsmith`, else `~/.cache/netsmith`, in `catalog-refresh/`) used for 24 hours (`--cache-ttl`, `--no-cache`) so a part is not asked for twice in a day; `--offline` asks nothing and uses kept answers of any age, dating each row by when its answer was got, and reports the rows it has none for as `SKIPPED`; a retry with a doubling wait (2 s, 4 s, ...; a `Retry-After` is honoured up to a minute) after a dropped connection, a 429 or a 5xx, three times; and a stop, naming the endpoint, on a 403 or another refusal, a web page where JSON should be (a block or a captcha), or JSON of another shape (the message names the field that is missing). On a stop nothing is written, and the message says the endpoint may have changed or may be blocking this client and points here. An LCSC number is sent only if it is `C` and digits. `NETSMITH_JLCPCB_URL` and `NETSMITH_LCSC_URL` point the command at other addresses (a mirror, a proxy of your own, the tests' fake server).

**8. The terms of use are not settled.** *(Still true of LCSC's; for JLCPCB the question is answered, see below.)* Neither site published terms for these endpoints that this work found, and the work did not read the sites' general terms of service. `data/jlcpcb/README.md` already records that the rows were fetched from them, once, by hand. A command that anyone can run over several hundred rows is more than that, and whether it is allowed is unknown. The mitigations above (opt-in, sequential, a pause, a cache, an honest User-Agent) are what a considerate client does, not a permission. Before the command is advertised beyond this repository the user should read both sites' terms, and the command should be withdrawn or changed if they forbid it. The same holds for the editor's button.

**9. The solver does not offer a row that has no stock.** *(Amended twice: the stock was LCSC's for a few hours, and is now the hand-entered JLCPCB number again; a refresh never writes it.)* A row whose `stock` cell is `0` is not offered, as if the row were not in the file (an empty `stock` cell is unknown and is offered, as before; its other cells are still read, so a mistake in it is still reported). This amends item 6 of ADR 0022, which said every row is offered and a part that is not wanted is removed from the file. Without it a refresh that finds a part sold out would write `0` and the solver would go on choosing it; with it the refresh is safe to run, and a sold-out row comes back when a later refresh finds stock. A project that wants a row regardless can leave `stock` empty. The command says when it has written a `0`.

**10. A fixed column `price_breaks`.** `1:0.0019 1000:0.0015` (from a quantity, the price for one piece); nothing reads it, and no standard file has it yet. *(Superseded: it was written by the refresh from LCSC's price ladder; it is now a hand-entered column like `price`.)*

## The 2026-11-02 decision: JLCPCB is not asked

On 2026-11-02 the maintainer read the `robots.txt` of both sites. JLCPCB's disallows automated clients on the path its parts library is served from, which the request of item 2 used. LCSC's has no rule for the path of its product endpoint. Neither site's terms of service could be read (the pages are rendered by script). Both companies offer an official API (JLCAPI at api.jlcpcb.com; the LCSC API, free with an account and a review). The user decided for v0.1.0 to drop the JLCPCB endpoint and keep LCSC's only, to tell users that JLCPCB data is not fetched, and to take the official APIs (which need the user's own accounts) after v0.1.0.

What follows from it:

- **No request to a JLCPCB host or an `/api` path is ever made.** The code for the JLCPCB request is deleted, `NETSMITH_JLCPCB_URL` is no longer read, and the fetcher refuses an endpoint that is a JLCPCB host or under `/api` before sending anything, even if `NETSMITH_LCSC_URL` names one. A test shows the fake server was asked only `GET /lcsc?productCode=C...`, for every row of every standard file.
- **What LCSC's product record gives** (the captured answers in `tests/fixtures/catalog-refresh/`): `productModel` (the manufacturer's number), `encapStandard` (the package), `stockNumber` (LCSC's own stock) and `productPriceList` (`ladder` and `usdPrice`, the price from each quantity). It has no library type.
- **What a refresh writes now:** *(Superseded by the second 2026-11-02 decision below.)* `price` (LCSC's price at its first quantity break), `stock` (LCSC's `stockNumber`), `price_breaks` (if the file has the column) and `date`. The manufacturer's number and the package are checked (CONFLICT, MISSING and the 500 ms delay, the cache, `--offline` and `--dry-run` are as before). Never `library`.
- **LCSC's price and stock are not JLCPCB's.** *(Superseded by the second 2026-11-02 decision below.)* In the captured answers LCSC's stock for C25104 is 1,085,700 where the JLCPCB record of the same day said 2,059,008, and LCSC's first price break is at 5 to 100 pieces where the old rows have the one-piece price. The columns are a snapshot of whatever the refresh could fetch, and the documents say whose it is. This was a choice among three: write nothing and refresh only the checks; write LCSC's numbers and say so; or leave `price` and `stock` and add columns. The second was taken because the user's rule was to refresh what the LCSC response honestly contains, and it keeps the existing file format. A person reviews the diff, as before, and `stock` can be left empty in a project that does not want a row to drop out because LCSC has none.
- **A cell the tool cannot fetch keeps *(Superseded by the second 2026-11-02 decision below.)* its dated snapshot and is reported as `not fetched`.** The `library` is never fetched, so every row reports it, and the summary says how many rows (`resistor.csv: not fetched, kept as dated: library in 20 rows`). A `price` or `stock` that a record lacks (a changed or thinner answer) is not guessed and not zeroed: that cell keeps its value, the row says `price not fetched` or `stock not fetched`, and the `date` stays too, because moving it would make the old cell look fresh. The `date` is therefore the date of the price and stock, as the bill of materials has always shown it; the library's date is the one in the row's `source`.
- **Stock 0.** *(Superseded by the second 2026-11-02 decision below.)* A row with `stock` 0 is still not offered (item 9), and the stock is now LCSC's: a part LCSC has sold out but JLCPCB still stocks is dropped, and the note on the row says JLCPCB's stock is not fetched. If a record has no stock, the tool cannot find that the part is out of stock, and the bill of materials still shows the dated snapshot.
- **The output says it.** *(Superseded by the second 2026-11-02 decision below.)* The summary, the editor's result, its button (`Refresh prices from LCSC (not JLCPCB)`) and its tooltip say: JLCPCB data is not fetched, and why; what is refreshed; what keeps its dated snapshot; that LCSC's terms of use have not been read and a person must read them before the feature is advertised; and that official APIs are future work. The one text is `refresh::NOTICE`.
- **Still open:** reading LCSC's terms of use (item 8, now for LCSC alone); the official APIs, which would give the library, price and stock of JLCPCB and LCSC properly. `data/jlcpcb/README.md` tells a person to read the library from JLCPCB's parts page by hand when adding a part.
- The solver, the language and the checker are unchanged.

## The second 2026-11-02 decision: a check, not a data update

Later the same day the user decided that the board is assembled from JLCPCB's own parts library, and that LCSC's price and stock differ from JLCPCB's: for C25104 LCSC lists 1,085,700 in stock where JLCPCB lists 2,059,008, and LCSC's first price break is at 5 to 100 pieces where the rows hold the one-piece price. The solver, the bill of materials and the stock-0 rule read the `price` and `stock` columns as the board house's numbers, so writing LCSC's into them (the decision above, which chose that and said so) put the wrong supplier's numbers where the right one's are expected. So:

- **A refresh is a check against LCSC's record, nothing more.** For each row with an `lcsc` number it compares the manufacturer's number and the package (CONFLICT when they differ, MISSING when LCSC no longer lists the part, as before). A row that agrees is `VERIFIED`. Exactly as before: `--dry-run`, `--offline`, the cache, the 500 ms delay, the fetcher's refusal of JLCPCB hosts and `/api` paths, a stop on a refusal. The statuses `UPDATED` and `CONFIRMED` are gone with the only thing they described.
- **What it writes: one cell, `checked`.** A new fixed column, the day (UTC, `2026-11-02`) the refresh last found the row's manufacturer's number and package equal to LCSC's record; with `--offline`, the day the kept answer was got. It is written only if the file has the column (the thirteen standard files have it, empty, just after `date`); a file without it is not given one, the rows are still checked and reported, and the report says that nothing is recorded. A row that is not VERIFIED keeps its old `checked`. Nothing reads `checked` (the solver, the bill of materials and `catalog age` ignore it); it exists so a person can see in a diff and in `git log` which rows were last verified, and when.
- **What it never writes: `price`, `stock`, `price_breaks`, `library`, `date`, and every other cell.** They are JLCPCB's numbers, entered by hand from its parts page (`data/jlcpcb/README.md`). A test asserts that every cell but `checked` is byte-identical after a refresh of every row of every standard file, with a fake LCSC that lists a different stock and a different price for each.
- **Why a new column and not the `date` column.** `date` already means the day the `price` and `stock` were read: the bill of materials shows it under the price and marks a line stale from it, `catalog age` lists rows by it, and the first decision above defined it so. A refresh that verifies a part's identity says nothing about whether the price is current, so moving `date` would make a stale JLCPCB price look fresh, which is the bug the first decision took care to avoid for a missing field. One meaning for each column (ADR 0001), so the second date has its own column. The alternative of recording nothing was rejected: the check is the only part of the refresh that is of use, and a person wants to know which rows have been through it.
- **The stock-0 rule stands, on the hand-entered stock.** A row whose `stock` is `0` is not offered (item 9). A refresh cannot write that `0` any more. It reports instead, as a note and not as a finding (the exit code is unaffected), when LCSC lists stock 0 where the row has some or none entered ("LCSC lists stock 0 where the row has stock 5: the row is not changed; check JLCPCB's parts page by hand"), and when the row has stock 0 and LCSC lists some. LCSC's stock is only ever read for this note. LCSC's prices are no longer read at all: with a first break at 5 pieces they would differ for every row, so a note would say nothing.
- **Ages are the original snapshot's.** The bill of materials and `catalog age` take the age from `date`, which a refresh does not change, so a refresh never makes a row less stale; `catalog age` now says to read JLCPCB's parts page and edit the rows by hand. In the editor the stale mark, the tooltip and the chip say "read" for the day of the price and stock.
- **The words.** The one text is `refresh::NOTICE`: JLCPCB data is not fetched and why; the refresh is a check, and what it records; what is never written and that LCSC's price and stock differ; the stock-0 rule; the unread terms and the official APIs. The editor's button is "Check parts against LCSC" (it said "Refresh prices from LCSC (not JLCPCB)"); its result lists the rows that are a CONFLICT, MISSING or SKIPPED or carry a note, counts the verified ones, and shows the same notice. The route and the command keep their names (`refresh`).
- **Not decided, still open:** reading LCSC's terms of use; the official APIs (JLCAPI, the LCSC API), which would let a refresh fetch JLCPCB's own price, stock and library and write them; until then the three are read from JLCPCB's parts page by hand, as when the row was added.

## The editor

The bill of materials shows the date of each line's price and stock under the price, with the age in a tooltip, and marks a line older than 90 days (the same number as `catalog age`) in amber with a dot in front of its designators; a chip above the table counts them. `Bom` carries `staleAfterDays` and the project's own catalog files, and each `BomLine` its `date`, `ageDays` and `stale`, computed on the server (typed in `api.rs`, as everything is). "Check parts against LCSC" (first "Refresh prices") runs the same code over the project's own catalog files as `POST /api/catalog/refresh?dry=0|1&offline=0|1`, which needs the `X-Netsmith` header, reports each looked-up part over the WebSocket as `progress` of task `catalog`, and answers with a `CatalogRefresh` (the rows needing a look, how many were verified, whether the files were written, the command's summary, or the reason it stopped). The file watcher then builds again; the bill does not change, because only `checked` was written. "Preview only" is `--dry-run`; "offline" is `--offline`. A project that lists no catalogs is told so: the standard rows are in the binary and only a new release (or `catalog refresh` in the repository) changes them.

## Consequences

- No new way to say a price: it is still the CSV cell, entered by hand. A refresh is a diff of `checked` cells that a person reviews and commits.
- A new dependency, `ureq` (with rustls), in the `netsmith` crate only. The solver, the language and the checker have none.
- The tests never reach the network. A server on `127.0.0.1` answers from `crates/netsmith/tests/fixtures/catalog-refresh/`, the responses of twelve parts captured once from the live endpoints on 2026-11-02 (public data; the JLCPCB ones were deleted afterwards, see the 2026-11-02 decision) and reduced to the fields netsmith reads, because the full answers carry signed, expiring download links and images. Another test builds answers from the rows of every standard file and checks that a refresh changes nothing but the `checked` cell, byte for byte.
- *(Withdrawn by the 2026-11-02 decision.)* C25102 and C47339, which JLCPCB flags Preferred, were to change from `Extended` to `Preferred` on the first refresh. They no longer do: the `library` is not fetched, so they stay `Extended` until a person or an official API says otherwise.

## Not decided here

- Whether to refresh the standard catalogs on a schedule, or on a release, and who commits them.
- Showing a live price in the editor without writing a file, for a part of the standard catalogs.
- A second supplier (Mouser, Digi-Key, which have official APIs and keys), or the official JLCPCB and LCSC APIs. The code has one place that reads a record, which is where another would go.
- Price breaks in the bill of materials by quantity (the `price_breaks` column is there for it).
