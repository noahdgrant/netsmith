# Physical intent is written in a file of its own, apart from the circuit source

Meets tests 1 (a third file beside the `.nsm` source and the layout file, and a language form for it) and 3 (a `pcb { }` block and an editor panel over the same file are the obvious alternatives). I relied on the status line: "accepted (owner decisions 2026-11-04) for decisions 1 to 7 and 10 and for the syntax choices recorded under "Syntax decisions"". The status line also said that anchors, how a module file attaches, a physical file for a `system` or a `panel`, and the exact list of what leaves were open: the module layer is not built and they are under *Not built*. The text before the cut is `git show 3e54ce1:docs/adr/0048-physical-intent-has-a-home-of-its-own.md` (122 lines; it also has the migration list, the "Built" log and the provisional readings). Issue #52 builds it.

**Decision** (owner, 2026-11-04, the answers to the ranked decisions of `docs/research/durable-home-for-pcb-intent.md`, section 8):

1. **A file of its own.** Physical intent (the outline, openings, mounting holes, where a connector or antenna must be, a fixed spacing between two parts, the face of a module, a region with a height limit, keepouts a board draws) is requirements, never solutions. It is written in `<stem>.physical.nsm`, found beside the source by stem, as `physical for Board { ... }`. It is not a view of the circuit source and not a `pcb { }` block. The people who review a case revision and a circuit change differ, a file is the unit review already works on, and the circuit source stays strictly the circuit, so a person, an agent or the editor's source pane never meets a case number. The owner confirmed this after comparing a block with a second file on a fuller example (`docs/research/physical-file-syntax-options.md` section 1).
2. **Layered.** A part, a module and a board can each own physical intent. A part keeps the datasheet geometry it has (the keepouts it carries). The board's file is built first; the module layer is additive and nothing written for the board's file is thrown away.
3. **The enclosure is not a shared definition for now.** The case numbers live in a nested `case { ... }` section that lifts out unchanged if a shared `enclosure` definition is built (issue #46, held until the mechanical side can export data).
4. **Reach by path.** A board's file names a part inside a module by a plain path (`.radio.row_a.place.left &= 8mm +/- 0.2mm`), read-only: it may state physical intent about the part and change nothing the circuit means. This qualifies ADR 0004 for this file only and replaces, for placement, the handle through a module's interface of ADR 0042 and ADR 0045. A module may also declare anchor names (`anchor .dock = .row_a`), so that a rename inside it changes one alias; the owner allowed both ways to reach a part, though a second spelling is ADR 0001's refusal.
5. **What stays and what moves.** The circuit source keeps what a circuit check consumes (the process, the stackup, the plane nets, who assembles a part, the designator letters, currents, impedance, pairs). Local pours, openings, keepouts a board draws, faces and relations go to the physical file. The test is "would a circuit check consume it?".
6. **What the editor writes.** Requirements go to the physical file and solutions to the layout file (ADR 0032). This settles the editor's question in ADR 0045 and moves the places ADR 0029 and ADR 0045 section 9 used for requirements.
7. **The old form leaves, with no grace period.** A board's `.place`, `Outline`, `Cutout`, `Keepout`, `MountingHole`, `Fiducial` and `Label` in the circuit source are errors whose message says where each goes.
8. **Syntax** (each time the option the note leaned to): relations are equations, `.b.place.x - .a.place.x == 17.5mm +/- 0.05mm`; `.place.side` on a module is a hard requirement on all its parts; a `row .pads.tp1 .. .pads.tp12 along x pitch 2.54mm +/- 0.05mm` statement is a numbered run on a pitch, and numbers at the end of a path sort numerically; `.height` and `.pin_protrusion` are stated on the part and narrowed by a board.

**What this amends.** ADR 0020 item 7A (placement geometry in one place): requirements live here and solutions in the layout file. ADR 0045 section 3 and 8 (the home of `.place`; its semantics stand). ADR 0029 (a board's keepouts and the ones the editor draws are physical intent). ADR 0032 (entries that state a place the case fixes are requirements). The glossary's _Editor_ entry.

**Rejected.** A `pcb { }` block in the board (lower cost, but it keeps the clutter in the circuit's source and one diff for a case and a resistor). Intent among the circuit's declarations with an editor panel (it leaves the handle clutter, the reuse problem and the unease). A layout file that holds requirements (no expressions, no link to other members, a second expression language). A shared `enclosure` definition first.

**The cost.** A module's physical file must travel with the module or a board loses the geometry silently. A rename inside a module breaks every file that reaches it by path (the checker names the path and the line; an anchor limits it to one alias). A board's file must be paired with its board. There are three files for a board and a new kind of guide example. The checker reads across files and needs a read-only reach into modules.

**Where the rest went.** The built rules, the owner's syntax choices, the provisional readings and the costs, word for word: header of `crates/netsmith/src/physical.rs`. The `row` statement and the numbering: header of `crates/netsmith-check/src/row.rs`. The guide's "The physical file", `docs/research/physical-file-syntax-options.md`, and the tests `crates/netsmith-check/tests/physical.rs` and `crates/netsmith-lang/tests/physical.rs`. The migration of the repository's own examples is done and is in the history.

**Choices accepted as built by the owner, 2026-11-11.** The spelling inside the physical file stays `.place`. The six readings of the board level and the eight of the `row` statement and the natural order are accepted as the headers named above give them, among them: the case section's contents are refused outside `case { }`; the old form's ban applies to a board's source and not a module's; and `.height` and `.pin_protrusion` may be narrowed in the circuit source and in the physical file, both places staying. What leaves the circuit source is what decision 7 names.

**Not built.**
- The module layer (decision 2; issue #52): how a module's physical file attaches to its module (T1, by stem; T2, named by the board's file; or T3, a statement in the module; `docs/research/physical-file-syntax-options.md` section 8), what a board's file may override of it, and whether the module layer may state an overhang (ADR 0045 keeps "a module cannot state one"). Decided by the owner, 2026-11-11: T3, a statement in the module names its physical file, and the board's file may only narrow what the module states (V1); built under #52.
- Anchors (A1, `anchor .dock = .row_a`), which come with the module layer, and a `Region` carried by a part with a height limit (G2), a new type whose members are not decided (issue #52).
- A physical file for a `system` or a `panel` (ADR 0040): not planned until a board needs it. Mounting holes of a panel, mated-connector alignment across boards and a panel's rails are not designed.
- The shared `enclosure` definition: issue #46.
- Writing the keepouts the editor draws to the physical file; the editor writes them to the layout file (decision 6; issue #52).
- A start offset (`from`) in a `row`, a row of a module's parts addressed by the module, and a row whose parts are not one numbered run: not planned until a board needs it.
