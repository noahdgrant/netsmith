# The editor compares the project with a git ref and tells what changed in the circuit

In a code-first tool the design lives in git, so the question an engineer has about a branch is "what did it change in the circuit?" and not "which lines?". A text diff answers the second: a renumbered designator rewrites nothing in the source and renames half the parts in the schematic, and a changed `.current` rewrites one line and moves a resistor, an LED and a rail's headroom. The editor therefore compares the circuit: the project as it is at a git ref (the base) with the files on disk (the head), reduced to parts, nets, rails, ports, bill of materials and problems, and says what differs. This is the first view that is about two readings of the project; every other endpoint describes the last one.

**How the ref is read.** Through the `git` command line, as `std::process::Command`, never a library: libgit2 or gitoxide would be a large dependency for six commands, and none of them gives what the analysis needs, a folder of files. A ref is resolved to a commit (`git rev-parse --verify <rev>^{commit}`; a name that starts with `-` or has a control character is a `400`, a name that is no commit a `404`). Its files are written with `git archive --format=tar <hash> -- <project folder> | tar -x` into a scratch folder in the system's temporary directory (`netsmith-compare-<pid>-<n>-<time>`, mode 0700, removed when the comparison ends, however it ends), so the work tree, the index and the repository's refs are never touched. Every git command is run with `GIT_OPTIONAL_LOCKS=0`, so not even `git status` rewrites the index. The project may be a folder of the repository (`hardware/board`): only that folder is archived, and the paths in the answer are the project's. A project with no `netsmith.toml` (`netsmith editor file.nsm`) compares that file and the files beside it that start with its name (its physical file, its layout). `git archive` honours `export-ignore` in `.gitattributes`, so a project that excludes its sources from archives is read without them; that is the repository's choice and the cost of not using a checkout.

**What is analysed.** The scratch folder gets a `Workspace` of its own, which runs the analysis the live project goes through (`Workspace::analyze`: check, solve, lower, draw, modules) with the same catalogs, so a part is sourced as it is for the live board. The result is reduced to a digest (parts with their sourcing, nets, the power tree's nodes, the module and port instances, the bill of materials, the problems) and the workspace and the folder are dropped. The head is the live workspace as it is on disk now, uncommitted changes included, which is what "dirty work tree" means here: `compare?ref=HEAD` is the diff of the work tree. `GET /api/git` says whether the folder or the project's folder has changes (`dirty`, `projectDirty`).

**Identity.** What a tool numbered is not identity; what the design called is.

- *A part is its path in the board* (`stage.regulator`, `PartDigest.path`, the path the layout file keys parts by, ADR 0030). The designator is a field of the part, as the value is: it differs, and says so as `designator`. When the only field that differs is the designator the part is *renumbered* and is listed apart, because adding one capacitor renumbers every capacitor after it and that is not a change to the circuit; a board with only renumbering is `unchanged`.
- *A part that is gone from one path and new at another is the same part if its kind, value, package and the named nets of its pins are the same*: it moved (a module was renamed, or the part now sits in another). Among several alike, the one with the same last name in the path wins, then the one with the same designator; a pairing on nothing but the shape (every pin on a net netsmith named) is made only when the leaf name or the designator is the same. A moved part is a change whose fields include `path`, with `basePath` set. Two parts that merely look alike on other nets are an added part and a removed one.
- *A net is its name, and a renamed net is found by its pins.* Pins are named by the path of their part (carried through a move), so a net's pin set is comparable across the two sides without the colouring of graphs that ADR 0017 needs where nothing is named. Nets of one name are the same net. Of the rest, those with the same pins are the same net under another name; then those that keep at least half of the larger side's pins, the pair that shares most first, each net once. A rename is reported (`renamed`) unless both names are ones netsmith generated (`net-r1.1`, from the smallest pin the net joins: the name follows the pins, so the generated name of a net whose parts moved changes with no change in the circuit and is not listed). Pins that joined and left are listed with each side's designator and the part's declaration on that side.
- *A rail is the power tree's node for its net* (`GET /api/power`: `power::tree`, ADR 0007), matched by the net's name, or by the name the net's rename gives, so a renamed rail is one rail. What is compared is its voltage range, its demand, its capacity and its budget (`within`, `over`, `unlimited`, `unknown`); ranges are equal when both ends agree to a part in a billion. `headroomBase` and `headroomHead` are `capacity.hi - demand.hi` in amperes, where both are known, rounded to a nanoampere. A rail that appears or goes is listed apart.
- *A module and a port are their paths.* A module is an instance of kind module; a port is an interface instance whose parent is the board or a module (the rails and interfaces a module exposes; what is inside a part is the part's). An instance at the same path with another definition is `changed`; a module that moved is a module removed and one added, which the moved parts show.
- *A board is its name* (`BoardSummary.name`, `Demo/main` for a board of a system). A board only on one side is an added or a removed board, with all its parts, nets and rails in the lists as added or removed.
- *A bill of materials line is its kind, value, footprint, LCSC number, manufacturer's number and whether it is soldered by hand*, as `GET /api/bom` groups them; it changes when its quantity or its unit price does. The designators of a line are carried and are not a change. `totalUsdBase`, `totalUsdHead` and `deltaUsd` are the totals the bill states, when both are known.
- *A problem is its severity, stage, board, instance path and message.* New ones are on the head only, resolved ones at the ref only, each with the `at` of its own side, and the rest is a count; a message that names a designator is a different problem when the designator changes, which is the cost of comparing text.

**Where each change is in the source.** A part has `at` (its declaration on the head side) and `baseAt` (on the ref's), an added part only the first and a removed one only the second; a net change has `at` at the first part that joined it, else the first that left (on that side), and each pin carries its part's `at`; a rail has `at` and `baseAt` as `PowerNode.at` has. Nets are tied to parts, not to a line, as ADR 0019 says, so a net has no line of its own. `source` has the numbers of `git diff --stat` for the project's folder between the commit and the files on disk (`--numstat --no-renames`, with the untracked files counted as all added), per file and in all. `GET /api/git/file?ref=&path=` gives a file of the project as it is at a ref (a path inside the project that ends `.nsm`, `.toml` or `.csv`), so the page can show the base side's line.

**The contract.** All of it is in `crates/netsmith-editor/src/api/compare.rs` and `web/src/api.ts`, additive: a page written before it reads the rest as it did.

| Request | Answer |
|---|---|
| `GET /api/git` | `GitInfo`: `available` (and `reason` when not: not in a work tree, git not installed), `root`, `projectDir`, `branch`, `head`, `dirty`, `projectDirty`, `refs` (HEAD, the upstream, the default branch, up to 50 local branches by recent commit, up to 30 tags newest first, each once, with its commit) and the last 30 `commits` (hash, short, subject, author, ISO date). Needs no analysis. |
| `GET /api/compare?ref=<rev>&board=<name>` | `Compare`: `ref` as asked, `base` (the commit), `head` (`commit`, `dirty`, `errors`), `error` and `baseProblems` when the ref cannot be compared, `cached`, `elapsedMs`, a one-line `summary`, `changed`, `source`, `boards` (by name) and the `problems` that name no board. `404` for a ref that is not a commit, `400` for one that is not a name, `422` with `git_unavailable` for a project not in a work tree. `board` limits `boards` to one (`404` if neither side has it). Waits for the first analysis, as the views do, and is told `503` pending to a request that asks (`X-Netsmith-Pending`). |
| `GET /api/git/file?ref=<rev>&path=<path>` | `FileContent` with `readonly` set and the commit's hash as its stamp; `403` for any other path. |

Every list is sorted (boards by name; parts by path; nets by name; rails by net; problems by severity, board and message) and keyed by a path or a name the page already knows, so a drawing can be marked with it: `data-ref` by designator (`designatorHead`, `designatorBase`), and the PCB by `data-path`. The `summary` reads `3 parts added, 1 removed, 2 values changed, 1 rail's headroom shrank from 80 mA to 20 mA` (boards added and removed, parts, values, nets, modules and ports, rails, the BOM's cost, new and resolved problems, in that order; notes are listed and not counted in the sentence), and `No circuit changes` when there are none. While the files on disk do not build the sentence starts with `N errors on disk:`, because a file that does not build has no boards on disk and its boards would read as removed (a workspace that built them before keeps its last reading, marked `stale`, as the views do).

**Progress and what is kept.** The comparison is one request that is answered when it is done, as `fab` is, on a thread of its own: it holds no lock the other routes need, and the live state's lock only for the moment the head is read (the base is analysed by another workspace). While it runs the socket carries `progress` with `task: "compare"` and `board` the ref as asked, with `stage` (`extract`, then the analysis's `check`, `solve`, `lower`, `draw`, `modules`, then `diff`) and `done` of `total` of that stage, so the page says "solving TwoBoards, 1 of 1" as it does for its own analysis. A ref's reading is kept in memory by commit hash (8 refs, the oldest out), so a second compare of a ref, by whatever name, runs only the `diff` stage: 35 ms against 1.1 s for the small example, and about the seconds an analysis takes for a big board. A ref that failed to read is kept too (it will fail the same way). One ref is read at a time, so two requests for it analyse it once. The head is read each time, because the files move.

**A ref that does not analyse** is not a failure of the request: the answer is `200`, `error` is a sentence (`the project does not analyse at 453862b: 1 error, the first: unknown type 'Resistr' (src/main.nsm:93)`), `baseProblems` are the errors the compiler gave at the ref, and `boards` is empty. So is a ref where the project's folder or `netsmith.toml` did not exist yet, or lists a top-level file that is not there. A comparison with half the project missing would show boards that are not new, so any error at the ref is the whole answer. Only a fault of this machine (git or `tar` failing, no scratch folder) is a `500`.

**What reading a ref may do.** A ref is not trusted: its files are analysed, so what they can reach must be limited. After `tar -x` the scratch folder is walked without following links, and every symbolic link, every file that is not a regular file and every file over 8 MB is removed; the answer for a ref that then does not read says what was left out (`in the ref, files were left out as symbolic links, which are never followed: src/main.nsm`), so a link is never read and a link to a device cannot be opened. A ref whose project files add up to more than 256 MB (their sizes are read from the tree, before anything is written) is refused. Only the project's folder is archived, and a project at the top of the repository leaves out `out/`, `target/` and `node_modules/` (at any depth), the folders the tools and other programs write. The scratch folder is removed when the compare ends, and a server that is killed first (`kill -9`; Ctrl-C ends the process without destructors too) leaves it: when the editor starts it removes every `netsmith-compare-<pid>-...` folder in the temporary directory whose process no longer runs (Linux: no `/proc/<pid>`; where processes cannot be listed, a folder over a day old), and never the folder of a live process. No signal handler is installed, so there is no dependency for one. Compares wait for each other, and a fourth waiting one is refused with `429`. A panic in the analysis (of the files on disk, of a ref, of a board's drawing) does not stop the server: that analysis ends with the last good reading, marked stale, and an error problem that names the panic and asks for a report, so the page leaves "analysing" and later edits are analysed as ever. Untracked files that git does not ignore are counted line by line through a bounded read (500 files, 32 MB), never through a link.

**Rejected.** A text diff of the sources: it is `git diff` and the page can show it from the file endpoint; it cannot say that a rail lost headroom. Reusing `netsmith-netlist`'s comparison: it compares two graphs that share no names, by refining colours, which is what a port from KiCad needs; here the parts have paths on both sides and the net pairing is a few lines on top of them. A `git worktree add` or a checkout in a temporary folder: they write to `.git` (`worktrees/`, the index, hooks) and the checkout may run filters and hooks. Keeping the whole `Snapshot` of a ref: it holds the drawings and the models, megabytes per board, for what the digest holds in kilobytes. A start and a poll: the long jobs of the editor (`fab`, `route`) are one request with progress on the socket, and a compare is one more. Comparing two refs with each other: the page asks for a branch against the work, and two refs would be two readings and a longer wait; the digest cache is what it would take.

**Limits.** The head is the files on disk, never a second ref. Systems, panels, layout files and the PCB are not compared, only boards; the schematic of the base is not drawn (the page marks the head's drawing). The scratch folder of a server that is killed in the middle of a compare is left until the next editor starts. A project's folder that holds large trees under other names than those left out is archived with them, up to the 256 MB. The bill of materials is compared by what the bill groups parts by (value, footprint, LCSC number, kind, hand soldering), not by the manufacturer's number: a line whose number changed is a changed line, and the answer carries the new number only. A part moved into another board is an added part and a removed part. `at` lines of the base side are in the ref's file as it was at the commit, which `GET /api/git/file` reads; they are not shifted to where the line is now.

## Built in the extensions

The ADR left four things open under _Rejected_ and _Limits_: two refs against each other, the systems and the PCB, a part's kind, and the checker's warnings. They are built, in that order, as additive changes to the contract above (a page written before them reads the rest as it did). Where this ADR was silent the choices below are the defaults taken; the owner reviews them, and the status of the ADR is what it was.

### Ref against ref

- `GET /api/compare?ref=A&against=B` compares the commit `A` (the base) with the commit `B` (the head) instead of the files on disk. Without `against` nothing changes. Both names are resolved before anything is read, so a name that is no commit is a `404` (a hostile one a `400`) at once and the first ref is not analysed for it. `Backend::compare_against` is the new method; `compare` calls it with `None`.
- Each side is read as a ref is: by commit hash, kept in the same cache of 8 readings, one ref at a time, so `A` against `B` after `A` against the work tree runs only `B`'s analysis, and the answer's `cached` is true when both were kept. A `ref` that does not analyse ends the answer at once (`B` is not read for it); a `B` that does not analyse gives the same kind of answer (`error`, `baseProblems` are the errors of the side that failed, and the sentence names that commit).
- The answer has `against` (the name as asked, absent for the work tree) and `head`: `commit` is `B`, `dirty` false, `errors` the errors of `B` (a `B` with errors is the broken answer above, so this is 0 in a comparison that has boards). `source` is `git diff --numstat A B` for the project's folder, with no untracked files. The `N errors on disk:` prefix of the sentence is not written for two refs.
- The progress messages keep `board` the first ref as asked, and the stages are those of each ref's reading in turn (`extract`, `check`, ..., `modules` for `A`, again for `B`) and then `diff`; both readings are cancellable at the checkpoints they already have, a cancel between them keeps the first reading, and the scratch folder of each goes with it.
- **The page.** The picker has two slots, `Base` and `Against`; `Base` is on when it opens (the choice a person made before is unchanged), `Against` lists `the working tree` first (the default) and then the same refs. Choosing in a slot compares at once and keeps the other side. The button reads `vs main and feature`, the status bar's chip `vs main and feature: 10 circuit changes`. The choice of the second ref is kept per project in the browser, as the first is. In a comparison of two refs the views are not marked (they draw the files on disk): the switch of each view is off with a tooltip that says so, the Compare section has no switch, the status bar's source items and the file tab's menu are not offered, a row picks nothing in the views, and `Head` opens the comparison of the file at the two refs (read only, the second side labelled with the commit) instead of the source. The sentence about uncommitted changes is not shown.

### Systems and the PCB

The answer has `systems` (by name, the same for a ref against the work tree and for two refs) and each board has `pcb`. A system is a board's neighbour, not a board: the System view's nodes and joins, and the power tree of the system, are read once per side and compared; the PCB is the placed board, read through the same code the PCB view uses.

- **A system is its name** (`TwoBoards`). A system on one side is `added` or `removed`. On both it lists, by name: its boards (`SystemNode` of kind `board`, by member name: added, removed, another definition), the ports of its boards (`power.output`: added, removed, `voltage` or `current` that differ, as the System view prints the ranges), its joins (the `a ~ b` texts of the edges), its mates (by the two connectors' paths: added, removed, and for a mate on both sides each contact whose roles differ as `contact 3: ground to ground → signal to ground`, and the ports the mate joins), and its ground groups. The nets a contact is on are not compared: what a board calls a net is the board's, and a rename is said by the nets (a renamed net does not make a mate change).
- **A system's rails** are the nodes of the system's power tree, named `led:VIN` (the member and the net) and compared as a board's are. Only a rail that no board's own comparison already lists is listed under the system: a rail in `rails.added`, `rails.removed`, `rails.changed` or a renamed net of the board `System/member` is the board's, and the system does not say it again. What is left is what only the joins explain (the capacity a mate gives a rail, so its budget and headroom). _Decision for review_: the other choice, listing every system rail, repeats every rail change twice.
- **The sentence** has the systems after the modules and ports: `system TwoBoards added`, `N system boards added|removed|changed`, `N system ports changed`, `N system joins changed`, `N mates changed`, `N ground groups changed`, `N system rails changed`. A board asked for alone has no systems in its answer. `changed` is true for any of them.
- **The PCB of a board** is `Entry` after `pcb::place` (the placer, with the layout file beside the source), reduced to a digest: each part's place in millimetres from the outline's top left corner (rounded to the hundredth the layout file keeps) with its rotation, side, lock and `placement` (`derived` when the file has no entry, else who wrote it), the outline's size, the copper layers, and the keepouts and cutouts by name with their areas in the same frame. It is what `PcbScene` has, without the drawing. A board that cannot be placed (a footprint is missing, a layout entry names a part the board lacks, the placer panics, contained as the analysis is) is `Err` on that side; a PCB that places on both sides is compared, one that places on one side only is not and says so in `pcbError` (comparing half a board would list every part), and a board that places on neither (it has no process) says nothing.
- **What differs on the PCB** is `pcb.moved` (a part on both sides, paired as the part diff pairs them, so a part that moved in the source keeps its place: `position` as `5, 2 mm → 7.5, 2 mm`, `rotation`, `side`, `locked`, with both places and the distance), `pcb.outline` (the size changed), `pcb.layers` (the stack changed), `pcb.keepouts` and `pcb.cutouts` (added, removed, or an area that differs by more than 0.006 mm), and `unchanged`. A part is where the layout file says; a move of less than 0.006 mm is none. Three defaults taken, _for review_: (1) a part the placer chose on **both** sides (`derived`) is never listed as moved, because the placer moves it for every part that is added, and that is not something the design said; a part stated on one side only is compared (the first time a part is put by hand it moves from where the placer had it), (2) the outline is compared only when the design states it (`design.features.outline`, the case's or the board's own) on either side, since the outline of a board that states none is as big as its parts need and grows with every part, (3) parts that are only on one side are in the Parts tab and not repeated on the PCB.
- **The sentence**, after the systems: `N parts moved on the PCB`, `outline 30 × 20 → 32 × 20 mm` (`N outlines changed` for several boards), `layers 2 → 4` (`N layer stacks changed`), `N keepouts changed`, `N cutouts changed`. A board whose only change is its PCB is `changed`, and the answer's `changed` is true.
- **Cost and cancelling.** Placing is slow on a big board, and the head is read each time, so a compare places each board of the files on disk too; the ref's digest (with its PCBs) is cached by hash as the rest is. A compare is cancelled between boards (`job::checkpoint`, ADR 0062), as between the two refs. A PCB's digest is made while the compare reads, never under the live state's lock.
- **Layout files in the page.** `GET /api/git/file?ref=:worktree&path=` reads a file of the project from disk (a regular file in the project, never a link; the same paths as for a ref: `.nsm`, `.toml`, `.csv`), read only, with the stamp `worktree`. `:worktree` is no name a ref can have (git refuses a colon), so it cannot be mistaken for one. The editor does not list a board's layout file among its files, so `GET /api/file` answers 404 for it; the comparison of a file asks for the files it does not have through this route. (The Source tab already listed layout files, and they opened half empty.)
- **The page** has two tiles and two tabs, `Systems` and `PCB`, after `Modules and interfaces`; the tiles count rows, with the chips `+`, `−`, `~` and, for the PCB, how many parts moved. A system's rows carry the system's name where a board's carry the board's, a mate's contact change reads `contact 2` with the old and the new roles, and a PCB row's chips are its first field (`5, 2 mm → 7.5, 2 mm`) with the others under its chevron; `Base` and `Head` of a PCB row open the layout file at the ref beside the file on disk. A board chosen in the scope selector shows no system (as the server's answer for one board has none), so the boards' counts and the systems' add up to the whole. The chip in the status bar and the `N circuit changes` count the PCB's changes and the systems' (a system added or removed is one). The marks in the other views are unchanged: a part moved on the PCB is not marked in the PCB view (the marks say what the circuit is, and the PCB view draws the head's placement already); that is a limit, not a decision.
