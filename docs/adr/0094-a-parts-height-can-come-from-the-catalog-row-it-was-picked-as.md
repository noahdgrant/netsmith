# A part's height can come from the catalog row it was picked as

Refs issue #27 (heights: where part heights come from) and issue #66 (a height column). Amends ADR 0045 section 11, which left "a catalog column `height`" for later.

## The problem

A real 12 V automotive board has a 4 mm height limit for its 35 x 60 mm case. netsmith checks it with a `Keepout` that states `.max_height` and the `.height` of each part (ADR 0045 section 11, the placer and the editor respect both). A part's `.height` had to be written by hand, from a datasheet, for every part under the limit; a part with none is reported `unchecked`, which is honest and means every part of a real board is a warning. The numbers are in the manufacturer's documents that the catalog rows already cite for their ratings, and the owner's rule is that a height is read from data and never invented.

## Decision

A catalog row may have a `height` cell: **how tall the part's body stands above the face of the board it is on**, one length (`2.62mm`), as the document of the row gives it. The part's `.height` is that number when the design states none.

- **`height` is a fixed column**, like `assembly` (ADR 0024, ADR 0084): a column of the row, not of the part. A file may leave it out of its first line, and a row may leave the cell empty; an empty cell means the height is unknown, as today. Nothing in a `catalog` statement of `std/` changes, so no design that built stops building, and no row is ever refused or chosen because of its height. `Candidate::height` and `Pick::height` carry it, `Orderable::height` carries it for a generic part when `fab` resolves it to a row, and `Sourced::catalog_height` carries it to the build.
- **A project's own statement wins.** The order, from the strongest: the physical file or the source states `.height` (as ADR 0045 section 11 says), else the picked row's `height`, else the part has no height. A stated `.height` is never compared with the row's, so a design that knows better than a document (a part with a taller variant) is not argued with. See "Choices for the owner".
- **The cell is read once, one length.** A range, a tolerance, a negative number or a quantity that is not a length is an error that names the file, the line and the cell, as for any column. A part whose own `catalog` statement lists `.height` as a column of its own reads the column as it always did and ignores the fixed meaning, so a project's catalog that predates this still builds.
- **The number is the greatest the document allows.** A height is used as an upper bound against a limit, so the cell is the datasheet's maximum, or the nominal plus the tolerance the drawing prints; when a drawing prints both inches and millimetres and they disagree through rounding, the larger. The cell never holds a typical value. A document that gives no height for the part leaves the cell empty. For a through-hole part with a pin on both sides (a pin header) it is the whole height above the board with the long pin up, which is also the greatest of the two ways it can be mounted.
- **Where the height is applied.** `netsmith::heights::from_catalog_rows`, after the generic parts have their rows (`resolve_generics`, the same resolution `fab` makes), adds the row's height to `design.features.heights` for each part the design states none for, and records which parts in `Built::catalog_heights` (the part, the number, the row's LCSC and manufacturer's number). Everything downstream, the placer, the check (`TooTall`), `heights_unchecked`, the editor's PCB view and its hover, reads `design.features.heights` as before, so a part whose height came from a row is kept out from under a low zone and checked like one that states it.
- **Reporting.** For a board that has a height limit, `fab` writes to `fab-notes.txt` how many parts have a known height and how many of those came from a row, and one line for each part whose height is a row's, naming the row (the row's `source` cell says which document, revision and page). A board with no limit reports nothing, as before. The editor is not changed: a part's hover says how tall it stands, and from where is for a later change (the page is a built bundle, `scripts/web-bundle update`).
- **The rows.** `data/jlcpcb/README.md` says which rows have the cell and which document each was read from; a row with a `height` has a `height:` entry in its `source` (document, revision or version, page, table or drawing). A cell the engineer could not read from a document stays empty: the catalogs hold no estimate and no figure from a package's name.

## What is not built, and why

- **The footprint library.** A KiCad footprint file has no height. Its `(attr ...)` holds `smd` or `through_hole` and the flags `board_only`, `exclude_from_pos_files`, `exclude_from_bom`; its `(model "path" (at (xyz ...)) (scale (xyz ...)) (rotate (xyz ...)))` points at a 3D file and says where to put it, not how tall it is; its courtyard and fabrication outline are in plan, with no z (KiCad's file format documentation, "S-Expression Format: Common Syntax", the sections on footprint attributes and the footprint 3D model, read 2026-11-09). The only place a height could be read in the file is a free `(property "Height" "...")`, which KiCad's libraries do not set and which nobody can be asked to maintain. The height of a footprint would therefore be read from the 3D model's bounding box (a STEP or VRML reader, which section 5 of ADR 0045 and question 6 advise against: a STEP file is a CAD kernel's input, and the model's offset and scale would have to be applied) or from a table of packages. **The 3D bounding box is the later step and is not built.** It would give a height for every footprint, from the same file KiCad uses, at the cost of a reader that does not exist yet and a model that may be a drawing of the part and not its datasheet; it is the owner's to commission (see below).
- **A height from the package's name.** A package standard bounds a body (JEDEC MO-178 for the SOT-23-5, MS-012 for the SOIC-8) but a part in the package is often lower, and a catalog row's package is a loose word (`SOT-23` is `SOT-23-3L`, ADR 0043). A package table would put a number where no document of the part said it. Not built; the rows of the package's parts record the part's own figure.
- **A height from a DXF.** DXF has no height on a 2D loop and a layer name is not a measure (ADR 0045 section 9). Unchanged.
- **A catalog height in the editor's hover and a table of heights in the bill of materials.** Cheap in the language, not in the bundle.
- **A warning when a stated height is lower than the row's.** It is the check the owner may want to catch a typo; it would also fire where the design knows a lower variant is fitted.

## Choices for the owner

1. **A fixed column, or an optional column of every `catalog` statement (ADR 0078).** Taken: fixed. With an ordinary `.height optional` in `catalog resistor { ... }` and every other, the value is a field of the part like any other, which the solver would hold the rows to: a design that states `.c1.height &= 3mm` (the way the guide teaches) would be offered only rows whose cell is within 3 mm, and an empty cell would take a row out of every design that states a height (ADR 0078: "such a design is offered only the rows that record a value"). That turns "a project's statement wins" into "a project's statement picks the row", and breaks every board that states a height for a part whose catalog now has the column. The cost of the fixed column is one more name among the row's own (`lcsc`, `mpn`, `library`, `assembly`, `price`, ...), and a design cannot ask the solver for a part of at most 3 mm. A project's own catalog may still list `.height` as a column of its own part, and then it is that.
2. **The number: the greatest the document allows, or the nominal.** Taken: the greatest, because a height is used against a limit and the nominal would let a part that is 0.15 mm too tall pass. A person who wants the nominal states `.height` in the design. A row's notes say the nominal and the tolerance where the document gives them.
3. **Which wins, the design or the row, and whether to say when they differ.** Taken: the design wins and nothing is said. The alternative is a note when the design's number is lower than the row's.
4. **Reporting in `fab-notes.txt` only when there is a height limit.** Taken, as ADR 0045 section 11 says "a board with no height limit reports nothing". The alternative is a count on every `fab`.
5. **The 3D bounding box.** Whether a STEP/VRML reader (the `(model ...)` of the footprint, its `at` and `scale` applied) is wanted for the parts that are in no catalog, knowing that a model is a CAD drawing and not a datasheet and that the number would need its own marker (`height from the model of ...`) in every report.
6. **Package-standard heights** for generated footprints (SOT-23, chip sizes): not built because the number would come from a standard and not from the part (above); the owner may want a *limit* from the package (an upper bound, reported as such) rather than a height.
7. **The editor's hover and inspector saying where a height came from.**

## Cost and limits

- A project's catalog file may add a `height` cell to any row; the loader checks it as above, and a project's catalog that has a `height` column and a part whose `catalog` lists `.height` is read as before.
- A generic part (ADR 0047) has the height of the row `fab` resolves it to. Which row that is can depend on the stock a supply provider reports (`resolve_generics`), and `Built::catalog_heights` is made with the catalogs the build was given, so a stock that changes the row can change the height; the numbers differ only where two rows of one value differ in height.
- A bank (ADR 0052) gives each part of the bank the row's height.
- No standard catalog row had a height before this change: the effect on every existing board is none until a row has one, and the goldens that list a row do not change. Rows with a height are added in their own change, with their sources.
