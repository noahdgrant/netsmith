# A board asks a part for a pin by capability, and the pin file keeps the answer

The owner decided on 2026-11-04 and 2026-11-09 that a board may ask for "any GPIO" and let the tool pick the pin, that the answer lives in a file beside the source, that the answer is stable between runs, and that the tool must later be able to move pins itself because some boards will not route without it. This ADR records the spelling and the file, which are syntax and a file format and so hard to reverse. The owner accepted the first choice of each row of `docs/research/pin-assignment-options.md` section 6; this ADR is `proposed` because the owner may still amend them.

A request is a member declared with a function of a part as its type: `.status: .u.GPIO`. It is a pin of the board (`.status ~ .led.a` works as it does for any pin), and its name is its key. The type names the part (`.u`) and what the pin must offer: a function a row of the part lists, or a function of a peripheral offered on the pin (`.tx: .u.UARTE1_TX`). The `fn` lists and the request are all that says which pins are interchangeable: a request may have any pin that offers the capability, and a pin the source names never moves. The part declares nothing new.

The tool gives each request a pin before the nets are made, at the end of the check stage, by joining the request to the part's pin and choosing the function there, as if the source had said so. Every existing check then runs on the result unchanged: a function the pin cannot offer, a pin used twice, a function whose direction disagrees with its net, and `shared` limits. The search is depth first over the requests in the byte order of their paths and over the pins in the byte order of their paths, and takes the first solution. It never depends on the order of rows in a part's table, which would break "statement order never matters".

The file is `<stem>.pins.toml`, plain TOML, `version = 1`, one table for each board keyed by its definition name, one entry for each request keyed by its path, written the same way every time. An entry has `pin` (the pin's path in the part, not its pad), `function`, `lock` (written when true) and `source` (`hand` or `auto`), as ADR 0032 has `lock` and `source`. Only requests are in it. A run never changes an entry that still holds. An entry holds when its request exists and asks the same function, its pin offers it, nothing else holds the pin, and `shared` still allows it. A new request is served round the held pins. `build` and `fab` write the file when a run picks a pin, and `--locked` makes a run that would change it stop and list the change. A locked entry that does not hold is an error at its line. An unlocked one is a finding and its request is picked again. A stale entry (its request is gone) follows the same two rules. A request that needs a pin an unlocked entry holds fails and names the move; the run does not move the other pin.

The rule that one function sits on one pin of a part no longer applies to a class: a function that rows list and a peripheral is `on` (`GPIO`). Two requests for it are two plain pins.

Rejected: a `pin` statement that declares the request (one more statement kind beside `tie` and `shared` for what an existing declaration form says). A capability as a join target (`.led.a ~ .u.GPIO`): `~` joins what it names, so two such lines would put two loads on one net, and the request would have no name for the file to key on. Interchangeable sets declared in the part: it states a second time what the rows say, and the two can disagree. The tie-break by table order or declaration order, and a pin file that also lists the pins the source names, or the pad and the datasheet name: each repeats a fact that can go stale.

Cost. The first pin map is arbitrary with respect to routing, because pins are picked before any placement. A run now writes a file in the source folder, where every other file a run writes goes to `out/` or `fab/`, and the pipeline's rule that no stage reads back what netsmith wrote has its first exception. A request resolves a part in its own block only. Two requests for a function that is no class (`ANALOG`) still collide with the one-function rule.

Left open. What the map records for a class such as `ANALOG`: the channel firmware needs (`AIN1`) cannot be told from the other functions of the row without the part saying which is the channel. A request for the end of a bus (`.dbg: .u.Uart`), which must pick one instance and both its pins. The optimizer that moves unlocked pins when routing fails, its trigger and its bound. The firmware export. The editor's pin map.
