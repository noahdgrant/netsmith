# An enclosure is a case section lifted out, which a board's physical unit names with `case Name`

Refs issue #46. It meets test 1 (a definition kind that projects will write and that users' files will name) and test 3 (a member `.case: SnapCase` is the obvious alternative, below). The owner decided on 2026-11-15 that the shared definition is a new kind, `enclosure`, whose body is the contents of the board's `case { }` section lifted out unchanged (ADR 0048 decision 3), and that a board's physical file refers to one. How the file refers to it, where an enclosure may be written and what is refused were left open; an agent chose them while the owner was away, and they wait for the owner's review.

**What it is.** `enclosure SnapCase { ... }` holds what a `case { }` section holds: the outline, cutouts, mounting holes, fiducials, labels, keepouts and height limits a case fixes, and its STEP files (`CaseModel`, ADR 0109), with the statements about them. A board's physical unit says `case SnapCase`, and the checker reads the enclosure's statements as if they were written in the unit's `case { }` section, in the enclosure's own file: its imports resolve its type names, a finding points at its line, and a `CaseModel`'s `.file` is relative to its file. Its members become members of the board under the names the enclosure gives them, so the rest of the unit (`.plug.place.y >= .outline.height / 2`), the design stage, the placer, `fab`, the fit check and the editor see a board exactly as if the section were written in place. A panel or a system that places the board sees it too, so several boards, a panel's cell and a system's boards share one case (ADR 0045 C7).

**How a unit names it (chosen: a `case Name` line).** (A) `case SnapCase`, the keyword of the section it replaces followed by a name. It keeps every name the section had, so lifting a section out changes no other line, and it reuses the reading every later stage already has. (B) A member, `.case: SnapCase`, as `docs/research/durable-home-for-pcb-intent.md` sketched under architecture D. Rejected: the outline becomes `.case.outline`, so every statement that names a case member changes when a section is lifted out, which is not "unchanged"; and every stage that looks for the board's outline, keepouts, holes and case models would have to look inside a member. (C) `physical for Board in SnapCase { ... }`, a header form. Rejected: a second spelling of the unit's header for one line of content, and a unit that adds to the case still needs a section.

**What one board adds.** A unit names at most one enclosure. What a board adds to its case (a fiducial, a label) stays in the unit's own `case { }` section beside the line, and a name both declare is declared twice, the error any repeated member gets. Rejected: `case SnapCase { ... }` with a body of additions, a third form of the same section; and several enclosures for one board, which nothing needs yet (a base and a lid are two `CaseModel` members of one enclosure). An enclosure holds no `case` line or section of its own, so none can contain itself.

**Where it is written.** In a file of its own under `src/`, imported by name as any definition is (`import src::snap_case::SnapCase`), or in a physical file, for the units of that file. A file that defines a board, a system or a panel may not hold one: an enclosure is physical intent, and ADR 0048 keeps it out of the circuit source. An enclosure is not a type: `.case: SnapCase` is refused with the line to write instead. On its own (the editor or `check` opening its file) it is checked as the case of a board, so what a `case { }` section refuses it refuses.

**Cost.** One definition kind, one statement and four refusals. An enclosure is checked again for each board that names it, and an error in it is reported once per board. The editor moves and resizes only keepouts written in the physical file, so a keepout of an enclosure is shown and not edited there. Its numbers are the mechanical side's to own: `dxf import` and a later `case import` print source to paste into it, and nothing is read from a STEP file at build time (ADR 0109).

**Left open.** A physical unit for a `system` or a `panel` (ADR 0048, not built), which would let a carrier and its plug-in board state where each stands to the other rather than each to its own outline. Features a requirement can name instead of a number (architecture D's `.input.plug.place ~ .case.port`). Openings, connector mouths and a region over which a module hovers as types of their own.
