## Commands

`netsmith --help` and `netsmith <noun> <verb> --help` document every command and flag. The skill `netsmith-use-netsmith` is the map for an agent: the loop of commands, the files, the exit codes and which skill fits which job.

### The command line

The commands are grouped under nouns, each with its verbs (issue #1090): `netsmith <noun> <verb>`, so `netsmith --help` lists nine nouns and `netsmith board --help` the verbs of a board.

- `project`: the project as a whole: make one (`init`), bring its agent files up to this netsmith (`refresh`), refresh or check its pick lock (`lock`), report what is worth changing in its sources (`lint`), rewrite its sources in the language's one layout (`fmt`), make one of its orders (`order`), print what it is made of (`show`).
- `board`: what is done to the boards of a file or of the project: `check`, `build`, `fab`, `drc` alone, `explain` a pick, `compare` two designs or the project with a git ref, `swap` a part for another row, `pins` (show, lock, move), `copper` (the planes, pours, hand zones and teardrop fills), `fill` (how the fill of the pours joins each pad, and the copper islands), and the views of the solved design the editor shows, printed as text or `--format json`: `bom`, `power`, `system`, `panel`.
- `layout`: the layout file, where each part is.
- `routes`: the routes file, the copper fixed by hand or imported. `routes delete --net NAME` also deletes whole a record of a net the board no longer has (a net renamed: `fab` warns of it, by that name), locked or not, and says what it deleted.
- `schematic`: the schematic layout file (`<stem>.sch.toml`), how the schematic is arranged: `show` it, `set` an entry, `check` it against the board, `arrange` the sheets of a big board (issue #1093). It is `layout`'s counterpart for the drawing: a noun is the thing a file holds, so the PCB's solution is `layout` and the schematic's arrangement is `schematic`, and the picture of it is the verb `view schematic`.
- `view`: look at a board: `3d` draws it to a PNG, `schematic` writes its schematic as a PDF, an SVG or a PNG, `pcb` draws its copper in 2D to a PNG or an SVG, `gerber` draws the files of its fab package, `editor` serves the editor, `editor-3d` drives the 3D view of a running editor.
- `catalog`: the rows of the catalogs, checked against LCSC's record, and the parts a supplier has that the catalogs lack (`search`, then `add --from`).
- `import`: what comes into a project from outside: a DXF drawing (`dxf`), KiCad's library tables (`kicad-libs`), a footprint from a KiCad board or footprint file (`footprint`), a part from a symbol (`part`), a port of a KiCad board (`port`), a case's STEP model (`case`).
- `dev`: the tools for developing netsmith and checking ports: `route` routes a saved placed board with the router's tuning flags, `parity` compares a port with its original, `board3d` prints the 3D scene's report.

The names follow four rules:

- One name for one thing. A command is named by the noun it acts on and its verb, and one verb is never a second spelling of another. A command or flag of an earlier release is an error that names the one to write and prints the whole line rewritten (ADR 0001; `docs/MIGRATING.md`).
- `--out` is always a folder. A command that writes one file names the flag after the file: `view 3d --picture` and `view editor-3d --picture` (a PNG), `view schematic --picture` (the PDF, SVG or PNG), `view pcb --picture` (the PNG or SVG), `layout export --kicad-pcb`, `dev board3d --glb` and `--step`, and `--write` for the source an import writes.
- One way to choose a board: the source file (`FILE.NSM`; with none, the project's boards) and `--board NAME` for one board of a file with several. Where the command takes another file first (`routes import BOARD.KICAD_PCB`, `layout set PATH`), the source is `--file FILE.NSM`.
- `--format json` wherever there is output for a program to read: one JSON document on stdout, and nothing else there.

`netsmith layout check` (issue 1309) measures the parts the layout file places against each other, one list of findings (courtyards, keepouts, cutouts, the edge: `placement`), and `netsmith board fab` runs the same check before the placer starts. `layout check`, `board check`, `board build` and `board fab` also say, before any placing, each part the placer places that no free rectangle among the locked and pinned parts holds (issue 1283: `no_room`, naming the part and the largest free rectangle of each face), a warning that `--strict` makes an error, so that `fab` stops at it instead of spending its placing budget. A part nearer a part with a `soft margin` (issue 1310, `soft margin 3mm round .u1` in the physical file) than the margin asks is a warning too, `soft_margin` in `layout check` among the parts the file places, and `fab` says it where the parts are placed, an error with `--strict`.

`netsmith layout parts --format json` gives each pad's real shape (issue 1516): `shape` is `rect`, `round_rect`, `oval`, `circle` or `custom`, `bounds` is the box of its whole copper on the board, and a custom pad (a corner pad, a polygon pad) also has `polygons`, its copper on the board as pieces with an `outer` ring and `holes` of `[x, y]` points, with the part's turn and face applied; its `width` and `height` are its anchor's size only. The guide's "Each part's geometry, as data" has the fields.

`netsmith layout parts --as-laid-out` (issue 1308) answers for the parts that have a place: the board is made as the layout file has it, a part with no entry in the layout file and no requirement that pins it is not on it, and the document lists it as having none (`no_entry`, a `refdes` and a `path` for each; a line of text for each) instead of refusing the board, also when the part (or a module with one in it) is what a PATH names. The exit code is that of a placed board: 0 when the data is printed. A script that must know whether every part has a place reads `no_entry` (or runs `netsmith layout check`, whose notes say the same). Only an outline whose size is not stated exactly is refused, as the placing alone gives it. `layout fit --as-laid-out` still needs every part to have a place, since the part it fits is tried against all the others.

### The frame of the places

A board's places are in mm with y down, in one of two frames (issue #1588): the outline's, from the outline's top left corner, as the layout file and the routes file write their places, and the board file's, KiCad's sheet, on which netsmith puts the outline's top left corner at (20, 20) mm. A place in the board file's frame less (20, 20) is the place in the outline's. Each command that prints places as JSON keeps the frame it has always printed in, and its document's `frame` key names it (`outline` or `board-file`); `--frame outline` or `--frame board-file` asks for the other, and then every place of the document is in that frame, also `outline_at`, the outline's corner, which is `(0, 0)` in the outline's frame. What is in a part's own frame (a pad's `local`, `local_courtyards` of `layout parts`) stays as it is.

| Frame of its own | Commands |
|---|---|
| The board file's | `board nets`, `board drc`, `board fill`, `board rules` |
| The outline's | `layout show`, `set`, `check`, `summary`, `compare`, `regenerate`, `capture`, `fit`, `parts`, `export`, `import`; `routes import`, `show`, `add`, `route`, `join-pad`, `sites`, `tidy`; `board check`, `board build`, `board fab` (the boxes of the placement in their findings) |
| The 3D scene's | `dev board3d` |

The four commands of the board file's frame are the odd ones out: every file a person edits, the 2D pictures and the Gerbers are in the outline's frame. They keep it as their default, so that no document a script reads changes, and a script that joins the places of several commands passes `--frame outline` to each.

`dev board3d` prints in its scene's frame (docs/BOARD3D.md): y up, from the outline's bottom left corner, its `frame` key a sentence that says so. With `--frame`, its places in plan (the holes, the cutouts, the parts' bodies, courtyards and pins, the height limits' areas, the case findings' `at`, the case solids' boxes, and each part's `layout` place) are put in the frame asked for, y down, and `frame` is its name; z, and a case model's `rotation` and `offset` (a motion), stay the scene's. A system's scene (`--board System`) takes no `--frame`.

With text, `--frame` moves every place the text says, in every command that takes it. The places are moved in the data the text is made of, so a text and its JSON say one place:

- `board drc` (each finding's `at (x, y)`), `board rules` (a rule area's first corner), `board fill` (every place, and the outline's corner in the heading, which says the frame it is in), `board nets` (where the copper that is not counted in a net's length is), `routes show` and `layout show` (the places of the entries and the shapes) and `layout parts` (its heading says the frame).
- `layout set` (the entry's place), `layout summary` (the corner of the largest free rectangle of a face), `layout compare` (the two places of each part that moved), `layout regenerate` (the region and the two places of each part placed again), `layout fit` (the place it is near and each place it tries; the `netsmith layout set ... --at X,Y` it gives to write a place is still in the layout file's frame, as `--at` always is, so the place before it and the one in it can differ), `layout export` and `layout import` (the places of the findings; the two places of each part that moved on the KiCad board).
- `routes import` (the place of the first error of the design rules check in a net's copper), `routes tidy` (the place of each change), `routes route` (the narrowest place of the way, and the vias that wall a net in), `routes join-pad` (the ends of the track and the via), `routes sites` (each site, and the frame it says in its last line).
- `board fab` lists the origin and the body's centre of each part (its heading says the frame, and that a `.place.x` of the physical file still measures from the outline's corner: take the corner off a place of this frame).

The sentences of the stages are made once, in the frame their stage works in, and say their place inside a sentence: the placement check's (a courtyard or a body "from the board's top left corner", the positions of the courtyards that overlap, in the outline's frame), and the design rules check's lines (`error [rule] message at (x, y)`, in the board file's frame, as `board drc` and `routes` say them; `fab` says them in the outline's frame, as the rest of its text and its notes, issue #1614). A text moves each place of them where it stands, by the words the sentence is made of, and the words that say the frame say the one it is in then: the warnings, errors and notes of `board check`, `build` and `fab`, the findings of `layout check`, `export`, `regenerate`, `compare` and `fit`, the faults `layout set` warns of, the placement of `dev board3d`, and the refusals of `routes add`, `route`, `join-pad` and `tidy`. In JSON the same sentences move with `--frame` too, so that a place said in a sentence is the place of the data beside it: the `message` of a finding (of the commands whose document is in the outline's frame), the `text`, `said` and `why` of a finding or a change, the `refused` of `routes route` and `routes join-pad`, the `placement_refused` of `dev board3d`, the `appeared` and `gone` of `layout compare` and `layout regenerate`, and the `vias` of the `walls` of `routes route` (strings, `net X at (x, y)`). With no `--frame` they are as they were. The files `fab` writes (`fab-notes.txt`, `placement-failure.txt`, `routing-failure.txt`) are not moved: each says its frame in its own words, all of them the outline's.

`layout capture` says no place, and takes the flag as it takes any. `board drc --kicad-pcb` and `board rules --kicad-pcb` know no outline corner, so they take only `--frame board-file`. A system's scene (`dev board3d --board System`) takes no `--frame`, in JSON or in text.

`board check`, `board build` and `board fab` take `--frame` for their JSON. Their document is in the outline's frame, and so is each place in it: the boxes of the placement (`conflicts`, `placement`), the `x` and `y` of the `overlapping` pairs and the `parts` of `does_not_fit`, the `origin` and `body_centre` of the `parts` of a board (its `offset` is a distance and stays), and the `place` of a finding of the design rules check that `board fab --for-review` waived (the design rules check judges in the board file's frame, as `board drc` says it; `fab` puts the place in the document's frame, so that no place of the document needs the other). A place said inside a sentence is in the outline's frame too (issue #1614): the `at (x, y)` of the design rules lines that `fab` lists in `fab-notes.txt` (the warnings, the notes, the findings the layout file waives, the errors under `FOR REVIEW` or listed with `--allow-drc-violations`) and in its JSON as findings of code `fab`, the drill/place `origin:` ("mm from the board's top left corner"), and the errors `fab` stops with. The first line of `fab-notes.txt`, also a note of the JSON, names the frame: `fab-notes for <board>; places in mm from the outline's top left corner, y down`; with `--frame board-file` the text and the JSON say the notes' places, and that line's frame, in the board file's. A panel's notes say their places from the panel's outline. `board drc` prints the same finding in the board file's frame unless given `--frame outline`, and then the two say one place.

### The MCP server

`netsmith mcp` offers the command line to an agent host that speaks the Model Context Protocol (Claude Code, Claude Desktop, an editor), on stdin and stdout (issue #1106). The host starts it, and it serves until the host closes its stdin. It adds nothing the command line lacks:

- Each command is a tool, named by its words (`board check` is `board_check`, `view editor-3d` is `view_editor_3d`), with an argument for each of its flags and positional arguments, under the name of the field clap gives it (`place_seeds` for `--place-seeds`, `file` for `FILE.NSM`), and with its type, choices and default. The list is short, because a host sends all of it to the model (issue #1133): a tool has the first line of its command's help and an argument the first line of its help, except an argument that six tools or more take with the same help (`format`, `file`, `board`, the placer's flags), whose help is said once in the server's instructions. The whole `--help` of a command, what `netsmith board fab --help` prints, is a resource, `netsmith://help/board-fab` (the command's words joined by `-`), listed with the other resources, for an agent to read when it needs it. The tools and the help resources are read from the command line itself, so a new command or flag is a tool, an argument and a help resource with no change to the server. `view editor`, a server that never ends, is not a tool, nor is `mcp`.
- A call runs the command in the project's folder, `--project DIR` or, with no flag, the folder the server was started in, as a person runs it there: the commands that write files (`board build`, `board fab`, `layout set`) write them. Where a command has `--format json` the call asks for it unless its `format` says `text`, and the result is the command's JSON document, as text and as structured content; otherwise the result is the command's text. What it says on stderr follows. An exit code of 1 (what the command checked failed) or 2 (it could not run, a mistake in the arguments included) makes the result an error, with the code.
- Each line the command says on stderr is a progress notification when the host asks for progress, and `--progress json` is asked for where the command has it. A call the host cancels stops its command as Ctrl+C does in a terminal, and is not answered (ADR 0062).
- An argument of one value may be given a JSON object, a document, in place of a file's path: the command reads it on stdin, as `-`. `routes_add` takes its shapes so (issue #1472): `{"shapes": {"track": [{"net": "GND", "from": [1, 1], "to": [4, 1]}]}}`, as many as the batch has, with no file written and no limit of a command line's length.
- The resources are the project's files (`netsmith://project/src/main.nsm`: its source and the other text files netsmith reads and writes, from the nearest folder up from the project's folder with a `netsmith.toml`; a path outside it is not read) and the language guide (`netsmith://guide/LANGUAGE.md` and its chapters, `netsmith://guide/language/27-commands.md`). The prompts are the skills `netsmith project init` writes, one for each, with an optional `request` that follows the skill's text.

To use it from Claude Code, in the project's folder:

```sh
claude mcp add netsmith -- netsmith mcp
```

or, to share it with everyone who opens the project, a `.mcp.json` beside `netsmith.toml`:

```text
{ "mcpServers": { "netsmith": { "command": "netsmith", "args": ["mcp"] } } }
```

Another host that starts a server on stdio takes the same: the command `netsmith`, the argument `mcp`, started in the project's folder. A host that cannot say the folder (Claude Desktop's `claude_desktop_config.json` has no such key) gives it as `--project`, which works the same in every host:

```text
{ "mcpServers": { "netsmith": { "command": "sh", "args": ["-c", "cd /path/to/project && exec netsmith mcp"] } } }
```

```text
{ "mcpServers": { "netsmith": { "command": "netsmith", "args": ["mcp", "--project", "/path/to/project"] } } }
```

**Attached to a running editor** (issue #1108). An agent that works while a person has the editor open can share the person's page. `netsmith mcp --editor 8787` (the port `netsmith view editor` printed) attaches the server to that editor, and `--editor` alone finds the editor that is running for the project: it asks the ports from 8787 to 8796 which project each serves, and takes the one that serves this server's project. The tools that read or change what the page shows, the state of its 3D view, the selection, the highlighted parts and nets, the camera and the cut, are the commands of `view editor-3d`, and attached, the tool `view_editor_3d` has the editor's port filled in (a `port` in a call still wins): its change is made on the page the person looks at, with the editor's own events (the page draws it, as it draws a click), and its `picture`, the file the canvas is saved to, is also returned in the result as an image. No tool is added: the tools are the command line's, and the other tools run as before. The editor is looked for at each call that needs it, so the host may start the server before the person starts the editor; a call that finds none says so, and says to start one with `netsmith view editor` or to give the port. ### The editor's views on the command line

`netsmith board show`, `board bom`, `board power`, `board system` and `board panel` (issues #1096 and #1137) print the views of the solved design that the editor draws, as text or, with `--format json`, as the document the editor's own route answers: `GET /api/board`, `/api/bom`, `/api/power`, `/api/system` and `/api/panel`. They are made by the code those routes call (`netsmith_workspace::Workspace`'s `Backend`), so the command line and the editor cannot differ, and each is read-only: it writes no file and needs neither `fab` nor a browser.

```sh
netsmith board show --board main          # the parts with what the solve left them, the nets with their pins, the pick lock
netsmith board bom --offline              # what the bill costs: lines, price, stock, total
netsmith board power --board main         # the current on each rail, what each supply leaves
netsmith board system --format json       # a system's boards, joins, mates and grounds
netsmith board panel                      # a panel's grid, size and checks
```

- `board show` prints the board's parts and nets as the editor's inspector shows them: each part with its designator, kind, value, package, path, sku (its number in the supply channel that buys it), whether it is assembled, the declaration that made it and the scopes round it, what the solver worked out for it (effective capacitance and bias, tolerance, ratings, the catalog row), the pins its pin requests got and where its package came from; each net with its pins (the pad, and the datasheet's name and the function the board chose); the board's notes; and whether the pick lock beside the source is current (what `project lock --check` says, which it only reads).
- `board bom` prints the lines the board house assembles (grouped as `bom.csv` is) and those soldered by hand, each with the supply channel that buys it and its sku there (a consigned line says so), its price, stock and the day they were read, and the total of the priced lines; a line whose price is unknown says why, and a generic part no catalog row stands for says what is wanted. `--offline` asks no supplier, as `board fab --offline` does (ADR 0047).
- `board power` prints each rail with its voltage, the supplies and loads on it with their currents, what the loads add up to against what the supply can give, the converters between rails with their efficiency, and the power issues (an overdrawn supply, a rail nothing supplies, a load or an efficiency not settled). It exits 0 with issues: `board check` and `board build` are the commands that fail on them.
- `board system` prints a `system`'s members with their ports, the joins between them, the mated connectors with each board's role and net at each contact, and the grounds the mates join; named after a board, the members of that board and the nets between them.
- `board panel` prints a `panel`'s board, grid, cell and panel size, rails and the panel checks; the drawing is only in the JSON (`svg`).

`show`, `bom` and `power` take the source file (or, with none, the project's boards) and `--board NAME`; `system` and `panel` take `--name NAME`. A name is as the editor names it, `System/Board` for a board of a system, and `Board` alone when no other board has that name. With one board (one system, one panel) the name may be left out; with several, the command exits 2 and lists them. The exit code is 0 when the view is printed, 1 when the source does not build (with its errors), and 2 when the command cannot run.

### The project as the editor's tree shows it

`netsmith project show` (issue #1138) prints what the editor's project tree is made of, as text or, with `--format json`, as the documents the editor's own routes answer, in one: `{"project": ..., "analysis": ..., "orders": [...]}` for `GET /api/project`, `GET /api/analysis` and `GET /api/orders`. It is made by the code those routes call, and it is read-only: it writes no file and builds no board.

```sh
netsmith project show                     # the boards, systems, panels, files and orders
netsmith project show --format json       # the same, for a program
```

It prints the project (its title, folder, the version of netsmith, whether KiCad was found and where), the boards with their definition, file, system and counts of parts and nets, the systems with their boards, the panels with the board they repeat and their grid, the modules with the boards that use them, the files with their roles (top level, module, dependency, manifest, physical, schematic layout) and the definitions in them, and the orders of `netsmith.toml`. The names are the ones `board bom --board`, `board system --name` and `board panel --name` take, so an agent need not read them out of the sources. The files of the standard library are counted in the text and listed in the JSON. A mistake in a source is counted (`board check` lists the problems), not an error of this command: the exit code is 0 when the project is printed and 2 when the command cannot run. A project with no `top_level` file shows its files and orders.

### Every editor route has a command

An agent must be able to drive and read everything a person does in the editor (issue #1098). A test holds the editor to that: `crates/netsmith-cli/tests/editor_routes.rs` reads the routes of the editor's server (`crates/netsmith-editor/src/server.rs`, the `.route("/api/...")` table) and has a row for each method of each route, which says one of three things:

- the command (or commands) that does the same through the same code, by the words clap's model names it by (`board pins lock` for `POST /api/pins/lock`). The test fails when a command named there does not exist;
- the command that is still to come, with the issue that builds it (`GET /api/pcb/pours` is `view pcb`, issue #1086, which draws the 2D picture of the copper). The test accepts the row until a command of that name exists and then fails, so that the row is changed to name it;
- why the route is an affordance of the page and needs no command, in one line: the previews of a track being drawn (`/api/pcb/walk`, `/api/pcb/shove`, `/api/pcb/reroute`), the socket (`/api/events`) and the progress post (`/api/progress`), the page's reads and writes of the files of the text editor and the project tree (`/api/file`, `/api/fs/...`), the cancels (a command stops with Ctrl+C, an MCP call with the host's cancel), and the choice of the page's analysis (`/api/analysis/run` and `/api/analysis/auto`).

A route of the server with no row fails the test, and so does a row with no route, so a pull request that adds a route to the editor adds its command, or the reason it has none, in the same change. The audit that made the first table found two routes whose command was not there: the board's parts and nets as the inspector shows them (`GET /api/board`, issue #1137, which is `board show`) and the project's boards, systems, panels and files (`GET /api/project`, issue #1138, which is `project show`); both are commands now.

### The editor

`netsmith view editor` serves the editor on `127.0.0.1` and prints the address to open: a project tree, the source with the compiler's and solver's messages beside the lines they are about, and views of the selected board (schematic, power tree, system, bill of materials, PCB) with buttons for `build` and `fab` (ADR 0019). A board of more than 16 parts is drawn in a box for each module instance, and the boxes, and the cards of the overview of all modules, are set out by how the modules connect: modules joined by nets come one after the other, the same way every time. A card of the overview dragged onto another takes that card's place: the editor writes the sheet's place to the schematic layout file below (`at = [x, y]` in the sheet's table, the top-left corner of its box in millimetres), and the sheets never moved are set out by their connections round it (ADR 0139). A rail is drawn with the ground and supply symbols at its pins. Errors and warnings are listed first, and the notes (relations not evaluated, balances left incomplete) in a closed section. It checks the text as you type without writing it, saves with `Ctrl+S`, reads a file again when it changes on disk, and with no file acts on the project like `build`.

In the schematic, a part can be dragged on the grid, nudged with the arrow keys, turned with `r` and mirrored with `m`. The editor writes where it was put to `<stem>.sch.toml` beside the source file (`src/main.nsm` has `src/main.sch.toml`), so the drawing stays as arranged across edits; the file never holds a wire or a net, an entry that no longer matches the design is listed in the problems and ignored, and deleting the file gives the automatic drawing back (ADR 0061). The editor can also compare the project with a git ref, or with a second ref, and say what changed in the circuit (parts, nets, rails, systems, the PCB, the bill of materials, problems) and not which lines (ADR 0059; `netsmith schematic` reads and writes the same file from the command line (`show` lists its entries and the boxes of the sheets, `set stage.output_cap --by 2.54,0 --rotate 90` writes an entry and keeps the file's comments, `set stage --at 101.6,0` places a sheet, `check` lists the entries that name nothing or that the drawing could not honour, `arrange --write` keeps the arrangement of the overview as `at` entries)). `netsmith board compare --ref <GIT REF>` does the same from the command line, with the editor's code: it finds the project from the current folder, reads the ref as the editor does (all the project's files, its catalogs and its dependencies' lock), and prints the changes as text, or as the editor's own `GET /api/compare` document with `--format json`; `--against-ref` takes a second ref in place of the files on disk, and `--board` one board. It exits 0 when the circuit is the same, 1 when it differs and 2 for a mistake (not in a git work tree, a ref that does not exist, a project that does not build at the ref). An analysis, a comparison, a build and `fab` can be cancelled with their Cancel button; a cancelled analysis leaves the last reading (ADR 0062).

The editor's bill of materials marks the lines whose price and stock are old (as `netsmith catalog age` lists them), says `unknown` for the rest, and has a "Check parts against LCSC" button for the project's own catalogs.

### The design rules check alone

`netsmith board drc [file.nsm]` runs netsmith's own design rules check (ADR 0037), the one `fab` runs and the editor's PCB view shows, with nothing routed and no package written. It checks the board as `fab` has it before the router: the placement with the copper of the routes file on it, so a connection the file does not make is an `unconnected_items` error (a board with no routes file has one for each), and the design's requirements on where parts go are measured as for `fab`. `netsmith board drc --kicad-pcb board.kicad_pcb` checks a KiCad board instead (the `.kicad_pro` beside it is its rules, and the process's rules that `fab` writes into the `.kicad_dru` beside it, below, are read too), such as one `layout export` wrote or one that came back before `layout import` or `routes import`; it has none of the other extras that `fab` adds (the fiducials, the stackup, the via rules), so it can find less than `fab` does of the same board. The findings are the lines `fab` lists (its `fab-notes.txt` has the warnings of the same board), errors first; the exit code is 1 when there is an error and 0 when there is none, whatever the warnings. With `--format json` each finding has its `severity`, the `code` `drc`, the `rule` (`clearance`, `shorting_items`, `pad_to_pad`, ...: each is in the tables below and in the long help of `netsmith board drc`), the `place` (`x`, `y` in mm in the frame of the board file, y down, and the `layer`), the `nets` and the `parts` it names, and the board's `outline_at` says where the outline's top left corner is in that frame (a place less it is in the frame of the layout and routes files), so that the places can be drawn as markers on a picture of the board.

**When copper is joined** (issue #1334). Copper of a net is joined where it runs into other copper of the net, as KiCad's connectivity has it: a track's end joins a pad, a via or another track when it lies nearer to it than half the track's width. So a track whose end lies on a pad's edge, or whose round end runs into the pad, is joined; one whose round end only touches the edge, half the width short of it, is not, in KiCad 9 as here, nor is one that misses by a hair. A track that ends on the middle of another track, of the same width or not, is joined by the same rule (issue #1542): its end must lie nearer to the other's centre line than the two half widths together, whichever track is the wider and from whatever side or angle it comes, so a narrow track whose end lies on a wide one's edge is joined and one whose round end only touches the edge is not. An arc is the exception: KiCad counts its edge as on it, so an end whose round end only touches an arc's copper is joined, and the distance is to the arc itself, not to straight pieces near it. The ratsnest, the router, `routes tidy` and the design rules check all count it so, and the check says it: the `unconnected_items` and `track_dangling` findings of copper that only touches add `it only touches ...`, and of copper that misses by less than 0.01 mm `it misses ... by 0.0050 mm`, so run the track into the pad. `crates/netsmith-fab/tests/touching_copper.rs` holds KiCad's check to netsmith's on each case, the tees of two widths and the ends on an arc among them.

#### The process's rules for KiCad

A KiCad project file holds one least clearance, one hole clearance, one space between holes and one annular width for every item, and a process states more: on JLCPCB's two-layer board copper keeps 0.1 mm from other copper but a surface-mount pad keeps 0.15 mm from a pad of another net, so KiCad, given the project file alone, is silent on two pads 0.1448 mm apart, of one footprint or of two parts, that netsmith refuses. `fab` (and `board fab --save-placed`, and the editor's "Also ask KiCad") writes a `<Board>.kicad_dru` beside the `.kicad_pro`: KiCad's custom rules, one for each rule of the process that asks more than the project file, named for netsmith's rule that holds it (issue #1185):

```text
(rule "netsmith pad_to_pad"
	(constraint physical_clearance (min 0.15mm))
	(condition "A.Type == 'Pad' && B.Type == 'Pad' && (A.Pad_Type == 'SMD' || ...) && (B.Pad_Type == 'SMD' || ...) && A.NetName != B.NetName"))
```

The rules are `pad_to_pad` (surface-mount pads of different nets, `.min_pad_to_pad`), `hole_to_track` (a track to a via's or a non-plated hole, `.min_hole_clearance`, and to a plated pad's hole, `.min_plated_hole_clearance`), `pad_hole_to_hole` (two holes when one is a pad's, `.min_hole_to_hole`), `npth_drill` and `slot_width` (the least non-plated hole and the narrowest slots), `plated_ring` (the copper round a plated pad's hole, `.min_annular_ring`) and `silk_over_copper` (a silkscreen text to an opening in the mask, `.min_silk_to_pad`, issue #1186: KiCad's `silk_clearance` on the mask layers, for a `Text`, leaving out a pad or a via as the other item, which KiCad's test of silkscreen against the mask layer's pads would report a second time as `silk_overlap`; the project file's `min_silk_clearance` is the space between silkscreen and to the edge, `.min_silk_to_silk`). **KiCad checks the pads of one footprint as it checks those of two parts** (issue #1229, measured with KiCad 9.0.0: a footprint with pads 0.14 mm apart and two parts with pads 0.14 mm apart each give one `pad_to_pad` finding to KiCad and to netsmith, the first marked `(within U1's own footprint)` by netsmith). What KiCad's check does not do is use a `clearance` rule where a pad or its footprint states a clearance of its own (`(clearance 0.05)`, which KiCad's own footprint libraries give to fine-pitch pads) or where the pads are in a net tie group of their footprint: a custom `clearance` rule is silent there, whether the pads are of one footprint or of two, and only only the project's, the board's least, which a pad's own clearance cannot go under, is checked. That is why the rule of the pads' space is a `physical_clearance`, the constraint a pad's own clearance does not override, and the rule's condition leaves out two pads of one net, which `physical_clearance` would check (netsmith's rule does not). The rules for the space from a hole to a track (`hole_to_track`) are `physical_hole_clearance` rules for the same reason (issue #1231): KiCad's `hole_clearance` yields to a pad's own clearance in the same way and was silent on a track near the hole of a plated pad that states one, and `physical_hole_clearance` reports it, with the pad's own clearance and without (measured with KiCad 9.0.0). It also reports a track of the hole's own net, which KiCad's `hole_clearance` and netsmith's check leave alone, so the rule's condition leaves out a hole and a track of one net (a hole with no net is judged against every track). `pad_hole_to_hole` is a `hole_to_hole` rule, which a pad's own clearance does not override (measured), and stays one. KiCad's `physical_clearance` also reports two pads that touch, the short that netsmith reports as `shorting_items` alone, and the cross-check counts that second finding as the short's. A net class that keeps more than the pads' space needs no rule of its own: KiCad's own `clearance` of the class reports beside the rule's. KiCad's check then reports each as a violation of its own rule, `Clearance violation (rule 'netsmith pad_to_pad' clearance 0.1500 mm; actual 0.1448 mm)`, where netsmith's says `pad_to_pad`; the cross-check reads the rule from that text and compares the two. netsmith's check of a KiCad board (`board drc --kicad-pcb`, the cross-check) reads the file back, the rules named `netsmith ...` only, so it judges the board to the same numbers. What no KiCad rule can say stays netsmith's alone: the space from a solder mask opening to a track (`mask_to_track`), a via in a pad (`via_in_pad`), the width and the vias a net's current or impedance needs away from its pads (`track_current`, `via_current`, `track_impedance`), the bends (`track_angle`, `acid_trap`), the fiducials and test points, the stackup and the blind and buried vias. The file is written again on every `fab`; a rule a person adds to it is KiCad's, and netsmith does not read it.

### The rules a board is checked to

`netsmith board rules [file.nsm]` prints the rules `board drc` holds a board to (issue #1513), so that a tool that draws copper of its own (a script, a router written for one board, its copper written with `routes add` or `routes import`) keeps the spaces the check asks and not the spaces it guessed from the findings. The numbers are read by the function the check reads them with (`netsmith_geom::drc_rules_of`, beside `drc_check`), from the same board, project file and process extras, so a track drawn at a net's `least_width`, a net's `clearance` from another net's copper, and a mask opening's margin plus `mask.to_track` from it passes the check, and a hair less fails it. The board is the one `board drc` checks: placed, with the routes file's copper on it; `--kicad-pcb board.kicad_pcb` reads a KiCad board instead, with the `.kicad_pro` and `.kicad_dru` beside it and none of `fab`'s other extras (no width a current needs, no via rules), as `board drc --kicad-pcb` checks it.

The text is a line for each kind of rule, then the net classes, the clearance between each two, the nets and the rule areas. `--format json` is one document: `board`, `outline_at` (the outline's corner in the frame of the board file, as `board drc` gives it), `clearance` (the board's `least`; `pairs`, the clearance between nets of each two classes, the larger of the two; `pads`, a pad's own clearance where it states one), `classes` (`Default` first, each with its `clearance`, `priority`, net `patterns`, and the `track_width`, via sizes and diff pair gap it draws its copper at), `nets` (each net's `class`, `clearance`, the `width` it wants, its `least_width` on an outer and an inner layer, the board's or its current's, the `impedance_widths` by layer, the `vias` side by side it needs), `widths` (`least` and `neck_reach`, how near its pads a track may be narrower than its current asks), `mask` (the board's `margin`, the `web`, `to_track`, and each footprint's `margin` with its pads that differ), `holes` (to copper, to a track, between holes, the least drill, slot and ring), `pad_to_pad`, `copper_to_edge`, `vias` (the least diameter, drill and ring, the micro via's, the default class's size, `in_pad` and the blind and buried `spans`), `rule_areas` (each with its `name`, the `part` that carries it or null, its `layers`, `outlines` and `holes` as `[x, y]` points in the frame of the board file, and the kinds it `forbids`) and `layers` (the copper layers, the thickness, the stackup and the `pours` with their nets, layers and clearances). Lengths are in mm; a rule the board is not checked to is null. `netsmith board rules --help` lists every field.

### A board with findings: `--for-review`

An error of the design rules check stops `board fab` and writes no package. The first line of its message says so: `design rules check: N errors: no package written (the KiCad board is in <folder>); --allow-drc-violations packages the board anyway and says in fab-notes.txt that it is not clean; --for-review writes the files to look at`. With `--format json` the same sentence is the message of a finding of code `fab`. The two flags are for two different things. `--allow-drc-violations` makes the package to order from; `fab-notes.txt` says the board is not clean. `--for-review` (issue #1189) makes the files a person needs to look at a board with a finding the board house accepts, or a clearance to fix later: the KiCad board and project, the Gerber zip as `<board>-gerbers-REVIEW.zip`, the SVG, the `.glb`, the `.step`, the schematic PDF and `fab-notes.txt` with the findings, each marked `FOR REVIEW, NOT FOR ORDER`, and no `bom.csv` and no `cpl.csv`. The run exits 1 while the check has errors, and `project order` takes no such package (it makes the board again, and the check stops it). `--for-review` waives the findings about where parts go as well, which `--allow-drc-violations` never does, and takes neither `--allow-drc-violations` nor `--cross-check`. A board that passes the check is packaged as usual.

It waives the board's own limits too (issue #1212), which stop a plain `fab` at placement, before anything is routed: a part taller than a height limit or a keepout's `.max_height` allows over it (`too_tall`, chapter 23, _Height limits_), a part or a pad in a keepout (`in_keepout`, `pad_in_keepout`), a part over pins that protrude (`over_pins`), a collision with a case model or a fit it cannot check (`case_collision`, `case_unchecked`), a part of unknown height under a limit when constraints are strict (`height_unchecked`), and the requirements on where parts go that the placer's own arrangement does not meet. These are limits of the case a board can break and still be made and assembled as drawn. What says the parts do not fit the board itself still stops `fab` with `--for-review`: courtyards that overlap, a part outside the outline or over a cutout, a pad off or too near an edge or a cutout, holes too near each other, a cutout outside the outline, a keepout or cutout with no place, a case model that cannot be read, and the lines of the physical file proved unable to hold together before placing (`--constraints warn` makes those warnings for one run). A board with a finding waived is packaged for review even when the design rules check passes: it is never packaged to order from.

`fab-notes.txt` of a package made for review begins, after its title, with the heading `FOR REVIEW, NOT FOR ORDER: `--for-review` waived N findings, each listed below, ...` and then every finding it waived, one to a line: those before routing first, then the errors of the design rules check (a requirement not met among them), each with its rule, the part, the numbers and the place (`error [too_tall] `tall` (J3) stands 9.00 mm tall on the top face, and the keepout `lid` allows 3.00 mm there (6.00 mm too tall), where its body is, around (5.0, 13.3) mm from the board's top left corner`). The line of the design rules check says `no errors, and the package is FOR REVIEW, NOT FOR ORDER` when the check itself found none. With `--format json` the run's error is a finding of code `fab`, and each finding waived is a finding of its own of code `fab` with `waived: "for-review"`, its `rule`, and its data: a fault of the placement check has `placement` (the kind, the parts with their courtyards, the height and the limit), a finding of the design rules check its `place`, `nets` and `parts`.

The package has the pictures of its copper too (issue #1213), so that a person sees the copper with no second command: `<board>-top-REVIEW.png`, `<board>-inner<n>-REVIEW.png` for each inner signal layer (an inner plane has none) and `<board>-bottom-REVIEW.png`, seen from below and mirrored as a person holds the board. Each is the board `fab` just routed drawn as `netsmith view pcb --layer <layer> --drc --islands` draws it, byte for byte: the design rules check's findings as numbered rings and the copper islands the fill took out. `view pcb` draws the same bytes when it draws the same copper, which is the router's copper `board fab --reuse-routes` keeps (without it `view pcb` draws the routes file's copper alone). The pixels carry no mark; the names end `-REVIEW`, as the zip's does, so that nobody orders from them. The notes' heading names them. `--no-pictures` leaves them out (it needs `--for-review`), and a package that is not for review has none: the pictures an earlier run left are removed, as the zip marked REVIEW is.

A finding the board house accepts for good, of a part's own footprint (a land pattern whose pads are nearer than the process asks), is waived in the layout file instead, one finding at a time with a reason and a source (chapter _The shape of a board_, _The layout file_): it is listed `waived` in `board drc` and `fab-notes.txt` and stops nothing, and the rest of the check still holds. In `--format json` it is a finding of code `drc` with the `severity` `waived` and the waiver's `waiver`, `reason` and `source`, which is not `--for-review`'s `waived: "for-review"` (an error the run went past): a package made for review lists such a finding under `design rules waived:`, as a package to order from does, and not under its `FOR REVIEW` heading.

### The schematic as a document
`netsmith view schematic [FILE.NSM]` writes the schematic the editor draws, with the schematic layout file beside the source honoured, as a file to hand on (issue #1091): `--format pdf` (the default), `svg` or `png`, `--board NAME` for one board of a file with several (a system's name writes the system), `--sheet NAME` for one sheet, and `--picture FILE` for the file (by default `<board>-schematic.<pdf|svg|png>` in the current folder; the path is printed). netsmith writes it itself, with no KiCad and no browser, and the same source gives the same bytes:
- **PDF.** A page for each sheet: a module's box of a board drawn by module (`power`, `stage (2/3)`), or the whole drawing of a board of 16 parts or fewer, named for the board. Each page is sized to its sheet, with a title block that names the sheet (with `Rev A` beside it at the right when `netsmith.toml` has `revision = "A"`, chapter 26), the board, the project and the release of netsmith, and `Sheet 3 of 7`. It is vector drawing with the text in Helvetica (Courier for a note's relation), which every PDF reader has, so no font is in the file and its text can be searched. A system's PDF begins with the system's own sheet, its boards and the joins between them, then has each member's sheets.
- **SVG.** The drawing the editor shows, or with `--sheet` the same drawing framed on that sheet.
- **PNG.** The drawing filled by netsmith's own rasterizer at 10 pixels a millimetre (fewer for a drawing longer than 8192 pixels), its text in netsmith's stroke font: a picture an agent can look at.
`board fab` writes the PDF into each board's package as `<board>-schematic.pdf`, beside the `.glb` and outside the Gerber zip, and a system's as `<System>/<System>-schematic.pdf`; `--no-pdf`, or `pdf = false` under `[project]` in `netsmith.toml`, leaves it out and removes an earlier run's. A schematic that cannot be drawn is a warning in `fab-notes.txt`, never a failed `fab`. The editor's schematic has `PDF` and `SVG` buttons, and the commands "Export schematic as PDF" and "Export schematic as SVG", which save the same bytes.

### The copper as a picture

`netsmith view pcb [FILE.NSM]` draws a board's copper in 2D, as the editor's PCB view does, to a PNG or an SVG (`--format png|svg`, the same drawing in both; issue #1086), with no editor, no browser, no GPU and no KiCad; the same board and flags give the same bytes. It is the picture for routing by hand or by an agent: where the tracks, vias and pours of a region are, which connections are still open, and what is in their way.

- **The copper** is the copper of the routes file beside the source and the router's copper the editor keeps (`.netsmith/routes/`) for every net whose pads have not moved since it was routed: what `board fab --reuse-routes` starts from, with the teardrops the router draws on the finished board (no file keeps them; the Gerbers have them). Nothing is routed unless `--route` is given, which runs the router first from that copper (`--route-timeout`, as for `fab`); the picture is the only file written. A pour is drawn as the Gerbers fill it, on each layer it is on: the clearances round the copper of other nets, the thermal reliefs round the pads of its net with the spokes that cross them, and the holes.
- **The open connections** are what that copper leaves, the connections `routes show` lists as left to route: bright straight lines from pad to pad, printed after the path (`open: net GND: D1.1 to J1.2`). `--only-open` lights their nets and fades the rest; `--highlight net:GND,R1` lights nets and parts (a part by its designator or its path) as `view 3d --highlight` does, and `--highlight module:reg` the parts of a module (its path in the design, as `layout summary` names it): each part's box filled and outlined in the module's colour and a dashed box round them all, each module named in its own colour (issue #1129).
- **A layer, a side, a region.** `--layer top|bottom|inner1|...|all` (all by default, the layer nearest the eye drawn last); `bottom` is seen from below, mirrored left to right as the editor's Side switch shows it, and `--side top|bottom` says the side for any layer. `--region X,Y,W,H` draws only that rectangle, in mm from the outline's top left corner (the frame of the layout file and the routes file, seen from above also when the board is drawn from below), and `--scale` is the pixels a millimetre (20 by default; a picture is at most 16384 pixels a side).
- **More marks.** `--courtyards` and `--designators` draw the parts' courtyards and designators (of the face of an outer layer drawn alone, else of every part); `--drc` runs the design rules check of the board drawn (`board drc`'s) and marks each finding's place with a numbered ring, red for an error and amber for a warning, and prints the findings by number (`marker 1: error [clearance] ...`). A missing connection is no marker: it is an open connection. A pad the fill of a pour starves (fewer than two spokes and tracks join it to the pour, the `starved` pads `board fill` lists) is the check's `starved_thermal` finding, so `--drc` marks it with the rest (`marker 2: error [starved_thermal] ...`).
- **The rule areas.** Every picture hatches and outlines, dashed and in the keepouts' red, the rule areas of the layers drawn that are not keepouts of the physical file (those are drawn as keepouts): the keep-out zones of the footprints, such as a library's area round an RF module's antenna, where their parts are placed, and the board's own (the areas that keep a pour off a sense pin's copper). They are the `rule_areas` of `board rules`, each with a tip in the SVG naming what it forbids there (`tracks`, `vias`, `pads`, `copperpour`, `footprints`), and each is printed after the path (`rule area: antenna of U1 forbids tracks, vias, copperpour on F.Cu, B.Cu`), so a track drawn by hand keeps off them before `board drc` says so. The editor's PCB view hatches the same areas, its tip naming the kinds, and `Rule areas` in its Layers menu hides them (issue #1543).
- **The stitching the export will have.** `--stitching` draws, in a cooler grey than the other vias, the stitching vias of the pours (a pour with a `.stitch_pitch` and another layer of its net) that the export will have and the routes file does not, and prints how many (`stitching: 24 via(s) the export will have that the routes file does not`). They are computed by the stitching `board fab` runs, on the copper drawn: the stitching vias the router already laid there, then those the stitching would add. They are put on the board drawn, so the fill clears round them and `--drc` checks them. On copper not routed yet (no `--route`) the router's tracks may still move a via within a third of the pitch, or take its place; with `--route` they are the vias `fab` writes. The editor's PCB view draws the same vias, a dashed disc in their own tone, and `Stitching` in its Layers menu hides them (issue #1489).
- **What the fill took out.** `--islands` hatches and outlines, dashed and in near white, the copper islands the fill of each pour took out (copper of the pour that touched no copper of its net, so the Gerbers have none there: the `removed` islands `board fill` lists), each labelled `I1`, `I2`, ... on its layer, and prints them (`removed island I1: bottom GND at (12.000, 3.500), 2.150 mm2`, a corner of it in the frame of the layout file, and its area). The editor's PCB view marks the same (issue #1188), and rings each pad the fill starves or joins by nothing (`starved_thermal` and `unjoinable_thermal`), its tip saying how many spokes join it or why none does.

```sh
netsmith view pcb --region 10,5,20,15 --scale 40 --only-open   # main-pcb.png: a region, its open connections lit
netsmith view pcb --layer bottom --designators --drc            # main-pcb-bottom.png: the bottom seen from below
netsmith view pcb --route --format svg --picture routed.svg     # route first, then draw the result
netsmith view pcb --layer bottom --islands --drc                # the bottom pour, what its fill took out and the pads it starves
netsmith view pcb --stitching                                   # the stitching vias fab will lay, in a tone of their own
```

### The lengths of the nets and the pairs

`netsmith board nets [FILE.NSM]` (issue #1223) measures the copper `view pcb` draws (the routes file and the router's kept copper, routed first with `--route`, `--route-timeout` as for `view pcb`) and prints a table of it, with no KiCad and no picture. For each net that no zone pours and that has copper: its routed length (the length of its connection, the copper that takes its pads to each other: a second way of one connection and a dead stub are left out and listed on a line of their own, with their lengths and layers; chapter _The shape of a board_, "Diff pairs", issue #1487), its straight length (the shortest tree of straight lines between its pads' centres) and their ratio, its vias, its layer changes (the vias where its tracks meet on two layers or more) and its layers; by name, or longest first with `--lengths`. Then each diff pair (chapter _The shape of a board_, "Diff pairs"): both lengths, the skew against the pair's limit (its `.skew`, or the router's 0.1 mm), the length of the first net that runs coupled (the other within 0.5 mm, centre to centre) and its share, the least and the largest gap edge to edge over it (the two are equal for a pair at one pitch), and both nets' vias with how many stand side by side. Then each length group: each net's length and the group's spread, against its tolerance. Then `track drop` (issue #1540): each power net's drop along its routed tracks, as `board fab`'s `track drop` guideline measures it (chapter _The shape of a board_, "The voltage a power track drops"), in mV against its budget (1 % of the rail's voltage) with the share of the budget, the two pads of the path, its length and narrowest track, the largest share first, and under a net at half its budget or more the path's pieces, the one that drops most first, each with what it drops and the width it needs; `board drc` notes each net over the budget with `fab`'s message (`track drop guideline: ...`, `track_drops` in its JSON), so widening a rail is a loop of `routes` and `board nets` with no `fab`. With `--currents`, a `currents` section follows (issue #1584): each net's one current, the number `track_current`, `via_current` and the track drop all read, with where it comes from (`sum`, the rails and parts on it with every load on at once; `analysis`, what the DC analysis finds into it; `carrier`, one rail or part on it that draws more than the analysis finds, such as a diode's stated `.current`), `at least` where a current on the net is not known, the words the findings say it in, and the least track (outer and inner) and the vias side by side it needs (chapter _The shape of a board_, "Track width against current"); it is listed whether or not the board has copper, and it is what the copper carries, not `board power`'s `demand`. The numbers are the router's: a track is measured along its centre line, an arc by its chords, as the meanders measure it, so a pair the router matched has the skew `fab` says it left. `--format json` prints `board`, `nets` (each with `copper`, the length of all its tracks, and `not_counted`, the runs its length leaves out, each with its `kind`, `layer`, `length`, a point `at` one end and its straight `pieces`), `pairs`, `groups`, `currents` with `--currents` (each with `net`, `current`, `from`, `lower_bound`, `source`, `least_width`, `inner_least_width`, `vias`) and `track_drops` (each with `net`, `drop`, `allowed`, `share`, `over`, the path, `width_for`, the `.min_track` that brings a net over the budget within it, and `path`, for a net at half its budget or more, the path's tracks and vias the one that drops most first, each with `step`, `track` or `via`, `layer`, `from`, `to`, `length`, `width`, `current`, `drop` and `needs`, the width it needs, issue #1610) as data. It is a sibling of `board fill`, not an option of `board drc`: the check fails a board and the table judges nothing; `board drc` notes each pair whose skew is over its limit (`pair skew: ...`, a note that does not fail the check, and `pair_skews` in its JSON) and each length group whose spread is over its tolerance (`length group: ...`, `group_spreads`). The editor's PCB summary tab shows the same table (`GET /api/pcb/nets`), with a line for each net whose length leaves copper out, and its 2D view draws that copper dashed over its tracks (`Not counted` in the Layers menu; a click on it picks the routes file's track, issue #1495).

Last comes the `quality` section (issue #1481). Its first lines are the totals and the router's quality objective of the nets of the table (issue #1517: their length over their straight length, vias, layer changes and the nets over twice their straight length; chapter _The shape of a board_, _The router's quality objective_; `quality.objective` in the JSON), then a line for each power net, a net whose current needs vias side by side that no zone, pour or plane fills (issue #1532: its current, the layers its tracks are on, its layer changes, each a group of vias its tracks meet on two layers, its vias and groups, and the groups short of its current's count; `quality.power` in the JSON, each with `net`, `current`, `vias_needed`, `layers`, `vias`, `groups`, `layer_changes` and `short_groups`). Then the defects of routed copper that the design rules check finds nothing of, counted for each net no zone pours, the nets with the most first, and the totals. **Crossings** are two straight tracks of one net on one layer whose centre lines cross away from their ends (a loop of the net's own copper). **Duplicates** are second ways between the same two places of a net (a way is a run of tracks and vias between a pad or a place where other than two tracks meet), as `routes tidy` finds them. **Unneeded** copper is each track and via that ends in nothing (a dead stub, each track of a dead branch, a via joined to its net on fewer than two layers, itself or through a via of its net whose copper it overlaps, as a group of vias side by side is), each nudge (a track from a pad's or a via's centre to a point still inside it) and each track inside, or overlapping along its line, another track of its net and layer. **Short** tracks are straight tracks shorter than two of their widths. Each track and via is counted once: as unneeded, else in a duplicate way, else as short. **Via pairs** are two vias of one net whose copper is no more than the group gap apart (the process's least clearance, or the board's `.process.via_group_gap`: the rule by which `via_current` and the router group vias, issue #1505), each via taken once; a group of vias side by side no larger than the net's current needs is not one. The detectors are `routes tidy`'s, so a count tidy can bring down is one it removes. With `--gate` the exit code is 1 when a total is over its limit, 0 of each unless `--max-crossings`, `--max-duplicates`, `--max-unneeded`, `--max-short` or `--max-via-pairs` gives another, and each kind over is said on stderr; the JSON's `quality` has `totals`, `nets`, the `limits` and the kinds `over` them. `board drc` notes the totals (`routing quality: ...`, with the worst three nets, and `quality` in its JSON) when there is a defect.

```sh
netsmith board nets --route --lengths     # route, then the nets longest first and each pair's skew
netsmith board nets --format json         # the copper as it stands, for a program
netsmith board nets --currents            # and each net's current, with where it comes from
netsmith board nets --gate --max-short 4  # exit 1 when the copper has a defect (four short tracks allowed)
netsmith board nets --power-stage        # each switching regulator's input loop, boot and feedback routes, foreign copper
```

`board nets --power-stage` (issue #1585) prints, instead of the table, each switching regulator's power stage, from the same copper. A **switching regulator** is a part that provides the standard library's `BuckIc` (`std::parts::regulator`: every standard buck IC, and a project's own buck IC that `Buck<Ic>` takes), and its pins are recognised by the roles the generic gives them, which every provider has by name: `vin.pos` is VIN, `vin.neg` its ground, `sw.pos` the switch node and `fb` the feedback pin; a pad of the IC on one of those nets is of that role too (a second VIN or ground pin). The parts round it are found by their nets and their kind (`#[kind(capacitor)]`): an **input capacitor** has a pad on VIN and one on ground; a **support capacitor** has a pad on the net of another pin of the IC (a bootstrap pin `BOOT`, `BST` or `CB`, an internal supply `INTVCC` or `VCC`, a soft start), and is a **boot** capacitor when its other pad is on the switch node. For each regulator it lists: each input capacitor, nearest first, with the distance from its VIN pad to the IC's nearest VIN pad and from its ground pad to the IC's nearest ground pad, centre to centre, and the routed length and vias of the shortest way through each net's tracks between them (joined as a net's connection is; `no track` where a pour or a plane carries the net, or it is open); each support capacitor with the same from the IC's pin; the feedback net's routed length and vias; and the copper of other nets near the switch node or under the IC, the `switch_node_copper` notes of `board drc` (their rule, in the table of _The design rules check against KiCad's_). With `--format json` it is `board` and `power_stages`, each with `regulator`, `path`, `vin`, `gnd`, `sw`, `keepout`, `input_caps` (each with `cap`, and `vin` and `gnd`, each with `from`, `to`, `distance`, `routed` and `vias`, null with no track), `support` (each with `pin`, `net`, `cap`, `boot` and its `leg`), `feedback` (`net`, `length`, `vias`) and `foreign` (each with `kind`, `net`, `layer`, `at`, `gap` and `under_body`); lengths in mm. Not covered: a part that states `dc switching_regulator` without providing `BuckIc` (a buck-boost IC that states the balance on its own output rail) has no pin the model calls a switch node, and is not listed; nor is the inductor's loop or the output capacitors'.
`netsmith view gerber PACKAGE` reads the Gerber (RS-274X) and Excellon drill files of a fab package and draws them as the board house will get them, with netsmith's own reader and no KiCad (issue #1105): the files `board fab` wrote (the zip, or `board fab`'s output folder of a board, which opens as its `<board>-gerbers.zip`), or a package another tool made, zipped or in a folder. Each file's function is taken from its X2 attribute (`%TF.FileFunction`), or else from its name (KiCad's `<board>-F_Cu.gbr`, `-In1_Cu`, `-Edge_Cuts`; Protel's `.GTL`, `.GBL`, `.G1`, `.GTS`, `.GTO`, `.GTP`, `.GKO`; Eagle's `.cmp`, `.sol`); a file neither names is drawn only with `--layer all`. A file with a construct the reader does not support (a step and repeat `%SR`, a block aperture, an arc routed in a drill file) is never drawn: it is named on stderr with its line and command, the rest is drawn, and the exit code is 1.
- `--layer top` (the default) draws the top copper, the mask's openings, the paste, the silkscreen, the outline and the holes, as a person sees the top; `bottom` the same of the bottom, mirrored as a person sees it; `inner<n>` that inner copper layer with the outline and the holes; `all` every layer, seen from the top. Each file is drawn in the colour of its function, the objects of each combined as its polarity says (a clear object takes away from what is under it in its own file, not from the other files).
- `--layer` also takes one function alone (issue #1143), with nothing else drawn: `top-copper`, `top-mask`, `top-paste`, `top-silk`, `bottom-copper`, `bottom-mask`, `bottom-paste`, `bottom-silk`, `outline` and `drill` (and `inner<n>` as above). The flag can be repeated to stack layers (`--layer top-mask --layer top-paste --layer drill`): each file is drawn once, in the order of the lists above, copper first and the holes last, and the copper is see-through when a stack has more than one copper layer. A stack of things of the bottom alone (`bottom`, `bottom-*`, with the outline and the drill) is drawn mirrored, as the bottom is; with anything of the top, an inner layer or `all` it is drawn from the top. A word the package has no file for, or no layer at all, is refused with exit code 2 and the words the package has (`--format json` lists them). The default file of a stack is `<package>-<layer>+<layer>.png`.
- `--region X,Y,W,H` draws that rectangle, in mm from the outline's top left corner, y down (the frame of the layout and routes files: the corner is the box of the outline file's centrelines), and `--scale` the PNG's pixels a millimetre (20 by default, fewer for a picture longer than 8192 pixels). With no region it draws the box of the outline's centrelines and of what the layer's other files draw, with a millimetre round it: for a board netsmith made, the outline with a millimetre round it, the region `view pcb` draws (with no outline file, everything the layer has with a millimetre round it). So `view pcb` and `view gerber` with the same `--layer`, `--region` and `--scale` draw one grid: pictures of the same size, pixel for pixel over the same place of the board, the bottom turned over the same way. Their copper is compared on every layer of the examples, from the zip `board fab` wrote and the board `view pcb` draws after `board fab --reuse-routes` (`netsmith_fabricate::gerber_compare`, issue #1142): where they differ, the writer or the reader of the Gerbers has a fault, and the places are `--region` boxes to draw with both.
- `--format png` (the default) or `svg` writes the picture to `--picture FILE` (by default `<package>-<layer>.png` in the current folder) and prints its path. The PNG is the SVG filled by netsmith's own rasterizer, and the same package gives the same bytes.
- `--format json` prints a summary of every file instead: the `origin` of the frame in the files' coordinates, the `board`'s size (the outline's), the `extent` of everything drawn, the `views` `--layer` can draw, the `layer_names` (every word `--layer` takes for this package: the views, then each function it has a file for, by its own word), and for each of the `layers` its `file`, `format`, `function` (`copper`, `mask`, `paste`, `silk`, `outline`, `drill` or `other`), `layer`, the `alone` word that draws it by itself (`top-paste`, `drill`), how it was `identified_by`, its X2 `file_function` and `polarity`, whether it was `read`, its `extent`, and for a Gerber its `apertures`, `flashes`, `strokes`, `regions`, the objects drawn `clear` and the `area` it covers; for a drill file its `holes` and `slots`. Then the `holes` of the package by size (`diameter`, `plated`, `holes`, `slots`), the files not read (`unread`, with the `line` and the `message`), and the files that are neither Gerber nor Excellon (`skipped`).
The exit code is 0 when every file was read, 1 when one could not be, and 2 when the command cannot run (no such package, a layer the package has no file for or does not know, a picture of more than 16384 pixels a side).

The editor draws the same (issue #1107): `Gerber` in the PCB view's `2D | 3D | Gerber` switch shows the package `fab` last wrote for the board, or one opened with Open package…, through the same reader, so its picture is the SVG `--format svg` writes. Each file can be turned off, the views are the ones `--layer` takes, a ruler measures in mm in the same frame, and the files the reader did not understand are listed with their line. Copy command gives the `netsmith view gerber` that draws the view shown.

### A self-contained KiCad project: `--portable`

`netsmith board build --portable` and `netsmith board fab --portable` (issue #1198) write the board's KiCad files as a project that opens in KiCad anywhere: move the folder to another machine, a desktop or an email and nothing in it points outside it. Without the flag the library tables of a board list the project's own libraries by a path that may leave the folder (`../../libs/acme.pretty`), the library entries of KiCad's install are left to KiCad's own tables, and each footprint's `(model ...)` names a variable of KiCad's (`${KICAD9_3DMODEL_DIR}/...`), which is a path of the machine that wrote it. The flag changes nothing else, and `project order` does not take it.

The folder of a board then holds, besides the schematic (and with `fab`, the board and the rest of the package):

- `libs/<Library>.kicad_sym` and `libs/<Library>.pretty/`: the symbols and footprints the board's parts use, one file each, from the project's libraries (`kicad.toml`, `[[library]]`) and from KiCad's libraries (the entries the project's rows reference; a footprint a generator makes is written the same way, as the build read it). netsmith's own library (ADR 0087) stays as it always is, `netsmith.kicad_sym` and `netsmith.pretty/`.
- `models/`: the 3D models. A footprint's model in KiCad's model folder is copied to the place it has there (`models/<Library>.3dshapes/<file>`); a STEP file of the project goes to `models/project/<file>`: a part's `.model.file` (ADR 0108) or a row of the project's model table (`[models]`, `[[model]]`), which `fab` gives to each part that has one, in the `.kicad_pcb`, in place of the library's model, with the offset and rotation the design states (they are the numbers of a KiCad `(model ...)` line). KiCad's model folder is `$KICAD9_3DMODEL_DIR` (or `KICAD8_3DMODEL_DIR`, `KICAD_3DMODEL_DIR`) when set, else the `3dmodels` folder beside the `footprints` folder of the install; the 3D models are a package of their own that KiCad's installers often leave out.
- `sym-lib-table` and `fp-lib-table`: every library above with a `${KIPRJMOD}/...` path, and every `(model ...)` is `${KIPRJMOD}/models/...` (`${KIPRJMOD}` is the project's folder). No path outside the folder remains: a model that cannot be found (a project file that is gone, a KiCad model folder that is not installed) is a warning, on stderr and in `fab-notes.txt`, and its footprint is written with no `(model ...)`.
- `LICENSES.md`, when an entry or a model of KiCad's libraries was copied: KiCad's libraries are licensed CC-BY-SA 4.0 with an exception that frees the designs made with them. The design itself (the schematic, the board, the Gerbers) is not bound by the licence; the copied library files are, so whoever passes them on keeps the notice and the credit, says they were changed (netsmith rewrites each footprint and symbol it copies, so its text is laid out afresh and its model lines name the models inside the folder; the models are copied byte for byte), and passes them on under the same licence. The notice lists every copied symbol, footprint and model. netsmith's own library, the symbols it draws and the footprints its generators make are not KiCad's and are not in the list.

A test builds an example and a project with libraries of its own into a folder, walks the library tables and the `(model ...)` of every footprint and board file, and checks that each path resolves under the folder and names a file that is there (`crates/netsmith-pipeline/tests/portable.rs`, `crates/netsmith-cli/tests/portable.rs`); it needs no KiCad.

### The cross-check of `fab`

`netsmith board fab --cross-check` (and `project order --cross-check`) checks the Gerbers against the board, in up to two ways (issue #1158):

- **The viewer comparison needs no KiCad (ADR 0097) and always runs.** For each copper layer of the board it draws the board `fab` routed, with the teardrops it adds, as `view pcb` does, and the zip it has just written as `view gerber` does, both over the outline with a millimetre round it at one scale, and compares their copper pixel by pixel (`netsmith_fabricate::gerber_compare`, which says how copper is told from the rest). The limits are the cross-check with KiCad's: 40 pixels a millimetre (coarser for a board that would be more than 8192 pixels a side), at most 1% of the copper pixels differ, and at most 0.1% have no copper of the other picture within 0.05 mm. A difference stops `fab` (the files are written all the same): the error and `fab-notes.txt` list each layer and each place the two differ as a `--region X,Y,W,H` box in mm from the outline's top left corner, with the side that has copper there (`only the board model`, `only the Gerbers`); draw it with `netsmith view pcb --layer <layer> --region ...` and `netsmith view gerber <zip> --layer <layer> --region ...` to see it. With `--format json` each line of the notes is a finding of the code `fab`, a note when the files agree and the error that stops the run when they differ. It finds a fault of the Gerber writer, or of the viewer's reader, that the board model does not show. A panel has no board model of its own, so the viewer comparison does not cover a panel.
- **The KiCad cross-check runs when KiCad is installed.** The board is plotted with KiCad as well and its files compared with netsmith's, and KiCad's design rules check is compared with netsmith's (ADR 0034, ADR 0037); `cross-check-<file>.png` shows each layer that differs.

With KiCad installed both run, and `fab-notes.txt` has `cross-check against netsmith's viewer: ...` and `cross-check against KiCad: ...`. With no KiCad (not installed, or `NETSMITH_NO_KICAD` is set) only the viewer comparison runs, and `fab-notes.txt` says `cross-check: ran netsmith's viewer comparison alone`. The cross-check of a panel is KiCad's alone, so it stops with a message when there is none. There is no flag to choose between them.

### Power findings

The power model's findings come from `netsmith`, not from the editor's page: `build`, the editor's analysis (its `power` stage, the Problems dock's `Power` group) and the power tree it draws all carry the same ones. A rail that can draw more than the supply that states what it can give (`max_current`, or `max_output_current` for a buck converter's IC, which `board power` shows as the rail's capacity, issue #1316) is an error that stops the build, where the solver had no relation to check it against; `--strict` is not needed. The notes do not stop it, with or without `--strict`: a rail nothing supplies (`V5 has no source: nothing supplies it`), a rail with loads whose current the solver has not settled, and a converter whose efficiency it has not settled. The Problems dock lists the notes of a board grouped by their cause, with a count for each (the server says it for every note: `not_stated`, `part_model`, `unjudged`, `circular`, `supply`, `pick`, `track`, `other`), so a long list of notes reads as the few things to do about them: a rail nothing supplies and a load not settled are `supply`, a level or an input current a part's definition leaves out is `part_model`, a value nothing states is `not_stated`.

### The JSON of the other commands

Every command that prints data for a program takes `--format json` (issue #1110): one JSON document on stdout and nothing else there, the exit code the text run has, and what the text says on stderr (progress, an error that stops the run) still on stderr. The shapes below are a contract: a field is added, not changed. Each command's `--help` lists the same fields.

- `board explain PATH --format json`: `command` (`explain`), `ok`, the `path`, the `boards` that have something at it, the `findings` (a path with nothing there is an error of the code `explain`; a board that does not build has the findings `board check` gives) and the count of the `notes`. A board is its `board` name, `failed` when its solve failed, and the `picks`, `unpicked` and `members` at the path or inside it, and the `pin_budgets` of the hosts there when there are some, in the shape of `board build --emit-solved` (_The solved values_); without `--all-rows` a part lists its first 20 rows `passed` over and `passed_more` says how many it leaves out.
- `project lock --update|--check --format json`: `command` (`lock`), `ok` (the exit code is 0), the `mode`, the `files` and, for a project with a dependency by `git`, the `dependencies`. A pick lock in `files` is its `file`, its `status` (`wrote` or `updated` by `--update`, `current`, and by `--check` `not_current` or `missing`), its `changes` (the lines the text prints for the parts whose row changed) and, when the file holds rows that no longer pass, `no_longer_pass`, what the solver says of them, and, when there are some, `held` (the rows a person holds on purpose with `held = "reason"` in the lock: each with its `board`, `part`, `row` and `reason`) and `not_judged` (the parts `--check --except` left out: each with its `board`, `part` and `row`). The `dependencies` have the same `file`, `status` and `changes`.
- `project order --format json`: `command` (`order`) and `ok`. With no name, the `orders`, each its `name` and its `boards` (`name`, `quantity`). With a name, the `order` made, its `dir`, its `boards` (the `board`, the `quantity`, its `dir` and whether it was `reused` from a plain `fab`), the `files` of the order, how many boards were `reused`, the `stages_run` and the `summary`, the text of `order.txt`. An order that cannot be made has `ok` false and the error as `findings`.
- `catalog refresh --format json`: `command` (`catalog refresh`), `ok` (false when an offer is a `conflict` or `missing`), `dry_run`, the `requests` made to LCSC, the `files` and `unknown_lcsc`. A file is an offers file of LCSC (ADR 0143) and has its `file`, its supplier as `catalog`, the counts `looked_up`, `verified`, `conflict`, `missing`, `skipped` and `without_lcsc` (rows of the catalogs read with no offer in it), whether it was `written`, its `notes` and the `rows` the text names (an offer that changed, is not verified or has a note): the `line`, the sku as `lcsc`, `status`, `why`, the `changes` (`column`, `from`, `to`) and the offer's `notes`.
- `catalog add --format json`: `command` (`catalog add`), `ok`, the `lcsc` number, the `mpn`, the `package`, the day it was `read`, `written` (the `file` and `line` of the row, null with no `--to`), `offer` (the `file` and `line` of the LCSC offer, null with no `--to`), the columns `filled` and `to_fill`. A number LCSC does not list, one the offers have, or a part the file has, is `ok` false with a `findings` error of the code `catalog` and exit code 1.
- `catalog add --from <supplier> <number> --format json`: `command` (`catalog add`), `ok`, `from` (`supplier`, `number`), the `provider`, the `manufacturer`, `mpn` and `package` as the record spells them, the named supplier's `sku`, the day the record was `read`, the `part` (as `catalog search` gives one), `written` (the `file` and `line` of the row, null with no `--to`), the `offers` written (`supplier`, `sku`, `file`, `line`), `not_written` (the record's offers that were not, and why), and the columns `filled` and `to_fill`. A record that does not name exactly one such part, or a part the catalog file or the supplier's offers file already has, is `ok` false with a `findings` error of the code `catalog` and exit code 1; no provider set up is exit code 2.
- `catalog search --format json`: `command` (`catalog search`), `ok`, the `provider` (`nexar` or `digikey`), the `query`, the day the answer was `read`, `cached`, `stale`, `requests`, `hits` and the `parts`: each its `manufacturer`, `mpn`, `description`, `package`, `values` (`name`, `shortname`, `value`), `datasheet`, `url`, `offers` (`supplier`, `seller`, `authorized`, `sku`, `stock` or null with `stock_note`, `packaging`, `moq`, `price_breaks` of `from` and `price`, `currency`, `updated`) and `other_sellers`. With no provider set up it asks nothing, says how to set one up on stderr and exits 2.
- `catalog age --format json`: `command` (`catalog age`), `ok`, `today`, `days`, `rows`, the `old` rows (`file`, `line`, the sku of the row's offer as `lcsc`, `date`, `days`) and the `unknown` ones (`file`, `line`, `lcsc`, `why`).
- `dev route --format json`: `command` (`route`), `ok` (every connection is routed), the `board`, the `left` connections as the text lists them, `connections_left`, the `tracks` and `vias`, the `seconds`, the `tries`, `stopped` (the route timeout ended the run) and the `written` files.

### The solved values

`netsmith board build --emit-solved <file>` also writes what the solve left each member of each board with, as JSON: the range of current an inductor carries (`reg.inductor.current`), the voltage a chain leaves at a node, the power in a resistor, and the values of the row each part was picked as. The file is an array with one object per board (`board`, and `System/Board` for a board of a system) and its `members`, each with its `path` from the board, a quantity's `unit` and its `range` in that unit (`[lo, hi]`, `"inf"` for an open end), a text's or an enum's `value`, and `shown`, the value as a message prints it (`5.047mA..50mA`). A member nothing gave a value is left out. A board that is built also has its `pin_budgets`, one for each host processor (_The pin budget of a host_, in the chapter on pins): its `host` path, `kind` and `refdes`, the `pins` that list a function, how many are `used` and `left`, the `modules` that use it (each its `module` path, `""` for the board itself, and the `pins` by the datasheet's names and the serial `blocks` it uses) and its serial `blocks` (each its `name`, the `bus` it is an end of, `used`, `left` and the `modules` that use it). A board that fails before the solve (a name that is not defined) leaves no record, so nothing is written for it; a board whose solve fails is written, as below.

The same file says why each part has its row. Each board has its `picks`, one for each part the solver chose a catalog row for, in the order it chose them: the part's `path`, the `catalog`, the `row`, a bank's `count` when it is more than one, and `passed`, the rows passed over before it. First come the rows before it in catalog order that do not fit what the design states (`unfit`, with the column and what the design states of it), then the rows the part's turn tried, in the order it tried them: `refused` with the first relation the row failed and `at`, the `file:line` of that relation; `later` when the row was accepted and the parts after it in its group could not all be chosen with it; `same` when it is the same as a row passed over before it for every relation; `skipped` when the search found without a trial that a trial would refuse it; `partly` when a bound that waits for a part still to be chosen holds for only some of its values. The turn is the one that made the pick, with the rows the parts before it have. A part a pick lock holds to its row has `held` (`the pick lock buck.lock.toml`) and nothing passed over, as no other row was tried: delete the lock, or run `netsmith project lock --update`, to see the rows the solver would take now. The solver keeps this record only for `--emit-solved`, so a build that does not ask is not slower.

A board whose solve fails has a record too, so a group that fails can be read and not only its error. Its object has `"failed": true`, the `members` and `picks` the solve got to (the parts of the groups that were chosen, and what the DC analysis wrote for the rest), and `unpicked`, one entry for each part of the group that failed: the `path`, the `catalog`, `held` as for a pick, `with`, the choices of the parts before it in the group that its turn was made with (`["a = 100 1%"]`; left out for the first part), and `passed`, every row its first turn passed over in the shape a pick has (a row `later` for a part that is not the first means the parts after it could not be chosen with it). A turn is the first one the search made when it reached the part, with the parts before it at the first rows that fit: what other choices of those parts would have tried is not there. A part that has no row that fits what the design states, or that every row is refused for whatever the other parts are, has its rows tried one at a time. With `--emit-solved` the file is written when a board fails if some board left such a record, and the exit code stays 1; `--emit-design` still writes nothing.

`netsmith board explain <path> [file.nsm]` prints the same record as text (or, with `--format json`, as the document _The JSON of the other commands_ has), for one part, module or member: `netsmith board explain reg.inductor buck.nsm` prints the row `reg.inductor` was picked as, what held it, the rows it passed over with why and where (`refused (at std/parts/regulator.nsm:602): reg.inductor.inductance must always be at least reg.ic.min_inductance, ...`), then each member at the path or inside it with the range the solve left it (`reg.inductor.current  5.047mA..50.06mA`). For a host processor at the path or inside it, the record has its pin budget before the members: the pins used and left, a line for each module with the pins and serial blocks it uses, and the serial blocks by bus (_The pin budget of a host_, in the chapter on pins). The path is a part, a module (`reg` is every part inside it, and `re` is nothing) or a member. It lists the first 20 rows a part passed over and counts the rest; `--all-rows` lists them all, and `--board` keeps one board of a file with several. When a board fails the error is printed as `check` prints it and the record of the failed group follows, with the exit code 1; it also exits 1 when nothing is at the path, and says which parts the solver chose rows for. Like `check` it writes nothing. A part the pick lock holds to a row has no rows passed over, as no other row was tried; run `netsmith project lock --update`, or delete the lock, to see the rows the solver takes now.

`netsmith board swap <part> [file.nsm]` is the editor's swap of a generic part that no catalog row stands for (_Catalogs_, issue #1094): it lists the nearest rows, each with what the board's checks say with it in the part's place and the change to the source that chooses it, and `--apply <row>` writes that change (a hand pick, ADR 0122), with the rest of the file as it was and the part picked again in the pick lock if the source has one. The part is a designator (`R1`) or a path (`r1`); the row is its name, its LCSC number or its number in the list. It reads the project as the editor does and asks the editor's own swap, so `--format json` is what `GET /api/swap` answers, and with `--apply` the row written and what `POST /api/swap` answers. It exits 1 when the board does not build or the part has nothing the swap can do (a row stands for it, or its value is stated where one edit would change other parts too).
